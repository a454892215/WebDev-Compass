# 1.1.2.4 表单提交、method、action 与 enctype

> [← 返回 HTML 目录](./README.md) · [知识地图](../../../knowledge-map/01-foundation-stages-0-2.md)

## 一句话理解

原生表单按 action、method、enctype 生成请求；Fetch JSON 是另一种由脚本显式构造的协议。

## 工作方式与使用规则

原生表单的默认方法是 GET，默认 action 是当前文档地址。GET 将编码后的字段放入查询串，适合搜索等读取操作，敏感内容不能放进去。POST 把数据放进请求体，修改状态仍需服务端授权和 CSRF 防护；POST 不等于加密，传输依赖 HTTPS。

| 编码                              | 用法                                                  |
| --------------------------------- | ----------------------------------------------------- |
| application/x-www-form-urlencoded | 默认 POST 表单编码，键值转义后由 & 连接               |
| multipart/form-data               | 包含文件；浏览器生成 boundary 和各分段                |
| application/json                  | 不是原生 form 的 enctype；用 fetch 序列化并与后端约定 |

`new FormData(form)` 是提交数据集，不自动执行验证。用 `form.requestSubmit()` 模拟提交按钮，可触发原生验证和 submit 事件；`form.submit()` 会跳过这两步。submitter 的 name/value 需要 `new FormData(form, event.submitter)` 才会包含在手工构造的数据集中（示例未给按钮设置字段）。

发送 FormData 时不要手设 Content-Type，否则可能丢失浏览器的 boundary。把 FormData 转 JSON 前需处理重复键和 File；Object.fromEntries 会把重复键压成单值。

## 最小示例

```html
<form action="/profile" method="post" enctype="multipart/form-data">
  <label for="avatar">头像</label>
  <input id="avatar" name="avatar" type="file" accept="image/*" />
  <button type="submit">保存</button>
</form>
<!-- 若脚本接管提交：preventDefault 后用 fetch(url, {method:'POST', body:formData})；
     不手写 multipart Content-Type，且仍需处理服务端错误。 -->
```

## 📱 移动端对照

类似 Retrofit/Dio 的 @FormUrlEncoded、multipart 和 JSON body；Web 额外有浏览器原生导航式提交，以及 Cookie/同源/CSRF 约束。

## 常见误区

- 看到 enctype="application/json" 就认为浏览器会发送 JSON：原生表单不提供这种编码。
- 设置 multipart 请求头却不带正确 boundary：服务器可能无法解析。
- 将 GET 视为不会泄漏：URL 会进入历史、日志，不能放密码或 token。
