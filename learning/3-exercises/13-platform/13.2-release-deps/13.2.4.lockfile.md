# 13.2.4 锁文件政策：固定工具、冻结安装与供应链检查边界：独立练习

## 动手任务

在隔离临时workspace制造一次manifest/lock失配，记录具体错误和恢复前后锁内容；再列npm/pnpm/Yarn三种命令适用条件，不把失败重跑成“自动成功”。

## 验收标准

- [ ] 冻结负例必须是明确锁配置/manifest错误，而非DNS、超时或下载失败。
- [ ] 恢复后冻结成功且锁不被暗改；区分开发重解析、CI拒绝、缓存与安全策略。

## 排错任务

只改package.json后在CI使用普通可更新安装，会生成新的解析结果并掩盖未审锁变化。改为冻结失败，回开发环境审阅manifest/lock后重试；不能删lockfile后称“修复CI”。pnpm CI=true时已有锁默认冻结，实验需要更新时显式声明。

## 参考要点

manifest给版本意图，lockfile记录解析图/完整性及配置结果。固定packageManager/运行时并提交对应锁文件；CI使用冻结命令，拒绝不一致而不偷偷重解析。npm ci、pnpm install --frozen-lockfile与Yarn immutable是各自工具约定，不应混用锁文件或给所有包管理器写同一命令。

offline限制归档下载不等于整条安装绝不访问网络。本轮pnpm11.4在外部依赖manifest变化时会先做supply-chain元数据验证，沙箱DNS重试已停止；没有关安全检查或把ETIMEDOUT计作冻结拒绝。锁文件不能单独证明上游无漏洞/构建脚本可信/跨OS原生依赖可用，缓存命中也不是安全保证。

先独立记录输入、实际失败和恢复结果再看参考；只改隔离副本，不动旧阶段或真实registry。
