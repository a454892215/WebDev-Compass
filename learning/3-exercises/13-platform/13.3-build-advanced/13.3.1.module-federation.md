# 13.3.1 Module Federation故障定位：远程入口、共享版本与发布缓存：独立练习

## 动手任务

在federation-review.json的隔离副本把oldRemote改成提供./Panel，并比对host alias；再设计一个remoteEntry HTTP200却是业务JSON的故障，解释为何“网络200”不足以初始化。

## 验收标准

- [ ] 正确区分静态包、普通dynamic import与MF container/share协商，不把本地JSON审查说成运行MF。
- [ ] 诊断至少覆盖入口/manifest/expose/shared/cache五类，列出fallback负责人和不放宽安全策略的处理。

## 排错任务

给定host请求catalog/Panel、remote exposes只有./Legacy，定位旧manifest/名称错；先核实际发布版本与官方RUNTIME-014适用前提，再恢复准确expose。若远程未真正启动，只记录配置推演，不伪造runtime控制台错误。

## 参考要点

Module Federation把远程模块加载、container初始化和共享依赖协商交给构建插件/runtime，不等于普通dynamic import，也不要求所有代码在同一仓库。代码在host执行上下文中运行，微前端名称不会自动建立安全沙箱、认证或数据隔离。先明确为什么需要独立部署，再决定是否值得承担运行期版本/网络复杂度。

shared singleton/requiredVersion/shareScope只是协商规则，不能保证所有产物永远使用相同Vue实例；import:false还需真实provider。hash chunk应保留旧版本，manifest更新/缓存需协调；fallback必须是匹配模块契约的本地安全行为，不以关闭CSP/CORS或执行任意远程URL恢复服务。SSR渲染上下文与远程模块代码缓存分开，不把用户状态放进进程级runtime。

先预测与操作，再对照参考；只改隔离副本，不污染主工程或旧阶段。
