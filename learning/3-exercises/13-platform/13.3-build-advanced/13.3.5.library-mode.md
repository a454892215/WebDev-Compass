# 13.3.5 库模式双格式与声明：真实import、require和类型消费者：独立练习

## 动手任务

在隔离副本将require错误指向不存在的.js，保存Node错误并恢复；再把.d.cts入口错误指向ESM-only复杂声明进行静态审查，解释为何不能靠改后缀解决依赖图。

## 验收标准

- [ ] Node import与require分别消费实际.mjs/.cjs公开入口，.mts/.cts类型检查均有真实证据。
- [ ] 声明生成与JS输出分开，写清当前无相对声明图限制；不把链接消费说成npm发布。

## 排错任务

package type=module时把CJS内容放index.js并让require引用，会与加载语义冲突；使用明确.cjs与正确条件导出，再通过消费者。若types缺失导致any，@ts-expect-error会失去预期约束，应恢复真实声明而非关闭noImplicitAny。

## 参考要点

库的格式、扩展名、package type、exports和types是一组消费契约。ESM/CJS不是简单把同一个.js文件换名字；条件导出需让Node与TypeScript分别选对入口。Vite library mode负责JS，tsc/vue-tsc或合适工具负责声明，产物必须由仓库外形态消费者验证。

临时消费者是本地包目录链接，不是registry安装或远程发布。复制.d.cts只对本例简单无模块图声明成立，复杂库需分别生成/验证。双包若各初始化全局状态可能产生双实例风险；本例纯函数无共享状态，不推导所有状态库都可安全双格式。主core若只发布ESM不应误称已有CJS。

先预测与操作，再对照参考；只改隔离副本，不污染主工程或旧阶段。
