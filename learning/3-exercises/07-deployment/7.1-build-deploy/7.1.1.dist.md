# 7.1.1 Vite dist 与 Nuxt .output：识别可部署产物 — 独立练习

先按理论与操作卡理解机制，再关闭示例完成变体，不要求复制整套工程。

## 动手任务

在副本新增一个公开课程页，分别决定是否纳入SSG路由列表；列出每个profile交付到哪里以及还需要什么运行进程。

## 验收标准

- [ ] SSR保留server/public并从server入口启动；静态profile仅托管public且不能依赖同包API。
- [ ] 新增路由直接访问和刷新都验证；内容摘要/清单能对应源提交和profile。

## 排错任务

把artifacts/ssr/public当静态站部署后访问/api/private失败：这是没有Nitro进程，不是修改前端API URL就能补回认证。恢复正确SSR托管或明确更换外部服务。

保留失败请求/状态、具体原因、修正后同一输入结果，不用“检查配置”代替证据。

## 参考要点

部署的输入是构建产物，而不是开发服务器或源码目录。Vite默认dist是静态文件；Nuxt Node SSR的.output包含server入口及public资源，只上传public会丢失请求渲染与API。Nuxt generate输出静态public目录，没有可执行的私有服务端；CSR和SSG都能静态托管，但原始HTML内容不同。

资源hash用于内容寻址和缓存失效，不是版本号、加密或部署成功证明。发布应保存代码提交、锁文件、构建命令、Node/包管理器、profile及产物摘要。不要把打包后的JavaScript当秘密存储；Source Map控制发布可见性但不替代服务端权限。

综合应用：对主工程三个profile保存可交付目录清单，解释不能混用的入口；对照lab中合成hash而非宣称lab重新实现Nuxt构建。
