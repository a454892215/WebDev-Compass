## 动手任务

1. 切换目标状态，确认无需动画也能理解。
2. DevTools模拟reduced-motion后检查transition-duration为0。
3. Tab聚焦操作按钮，在宽窄视口检查焦点轮廓。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：交互样式应尊重减少动态效果、键盘焦点和触控能力，而不只优化鼠标hover。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `transform`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：手机一定没有hover，桌面一定没有触控。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“reduced-motion就隐藏所有交互结果。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- prefers-reduced-motion:reduce表示用户希望减少非必要动态效果；可直接取消位移/缩放，同时保留明确状态。
- 触控目标、按钮标签和文本放大同样需要检查；CSS媒体查询不能判断人的全部需求。
- 与系统动画偏好、FocusNode和触控尺寸关联；浏览器环境需显式保留键盘路径和用户缩放。
- 此例的完整偏好验收需模拟reduced-motion并Tab聚焦目标，不能仅点击切换判断。
