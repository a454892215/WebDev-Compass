# 1.2.4.6 练习：把移动布局经验迁移到 CSS

## 动手任务

1. 切换行/列布局并解释轴变化。
2. 保留HTML源顺序，Tab观察阅读与操作顺序。
3. 用长文案和缩放验证约束，而不是固定高度。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：复用“约束、内容、对齐”的思维，但需重新学习浏览器的文本流和最小尺寸规则。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `flexDirection`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：rem永远等于16px或某个dp。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“页面只要看起来像设计稿，就忽略焦点和文字缩放。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- Row/Column/RN Flexbox与CSS Flex有共同轴模型；CSS默认收缩、内在最小尺寸和书写方向不能直接照搬。
- Web保留DOM阅读和键盘顺序；不能仅为了布局美观用order打乱交互顺序。
- 已有移动开发经验可以帮助判断布局目的，但不能把CSS当另一套Widget属性字典；应测量实际盒模型。
- 验收记录需要实际修改与观测，不把一次自动检查等同于所有浏览器/辅助技术验收。

## 关联综合实践

将 .fields/.actions/.cards 分别映射到熟悉的Row/Wrap/Grid思维，再写出CSS不等价之处。

- [ ] 实际解释一个min-inline-size或正常流差异
- [ ] 不改DOM源顺序来追求视觉排列
