# 1.2.2.9 练习：层叠上下文与 z-index

[返回理论](../../../1-notes/01-web-fundamentals/1.2-css/1.2.2.9.stacking-context.md) · [打开实验](../../../2-examples/01-web-fundamentals/1.2-css/1.2.2.9.stacking-context-demo.html)

## 动手任务

1. 观察高z-index的内部标签仍被相邻层覆盖。
2. 切换父上下文z-index，让整个上下文提升。
3. 在 DevTools 中找出真正创建上下文的祖先。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：z-index 只在所属层叠环境内比较，子元素不能靠一个巨大数字逃出父上下文。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `zIndex`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：z-index:999999可以解决所有遮挡。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“把overflow裁剪、层叠顺序和包含块混成同一问题。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- 定位元素的非auto z-index、transform、opacity小于1等可建立新的层叠上下文，条件需按规范核对。
- dialog等顶层元素与普通文档层叠不同；不要用全站z-index递增代替正确浮层/焦点策略。
- 与Stack绘制顺序相关，但CSS嵌套上下文、合成和顶层行为有独立规则；不是所有“层”都是GPU层。
- 验收记录需要实际修改与观测，不把一次自动检查等同于所有浏览器/辅助技术验收。
