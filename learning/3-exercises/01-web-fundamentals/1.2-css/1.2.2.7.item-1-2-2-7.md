## 动手任务

2. 切换column-count:2，检查列数计算值。
3. 缩到手机宽度并评估正文是否仍易读。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：CSS 多列把同一连续内容流排入若干列，适合文章而非任意交互卡片网格。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `columnCount`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：用columns构建复杂表单，造成阅读/焦点跳转难以理解。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“把column-count当保证固定列宽。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- column-count 给出列数目标，column-width 给出理想宽度；浏览器结合可用空间决定实际列。
- 交互内容的视觉跨列顺序可能难于理解；长文阅读注意窄屏回到单列。
- 与多列正文排版相近，不等价于Flutter GridView；一段内容会被浏览器分割到多个列。
- 验收记录需要实际修改与观测，不把一次自动检查等同于所有浏览器/辅助技术验收。
