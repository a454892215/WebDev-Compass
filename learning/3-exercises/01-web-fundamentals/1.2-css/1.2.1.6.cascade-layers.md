# 1.2.1.6 练习：完整层叠：来源、重要性、层与权重

[返回理论](../../../1-notes/01-web-fundamentals/1.2-css/1.2.1.6.cascade-layers.md) · [打开实验](../../../2-examples/01-web-fundamentals/1.2-css/1.2.1.6.cascade-layers-demo.html)

## 动手任务

1. 初始两个普通分层规则比较颜色。
2. 切换 important 变体，观察早层颜色反而获胜。
3. 在 DevTools 核对规则来源，不凭样式文件位置猜。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：先决定声明属于哪一优先级区间，再比较该区间内的特异性和顺序。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `color`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：把未分层样式视为永远最低。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“给所有规则加 important；会使用户偏好和覆盖关系更难推理。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- 先过滤选择器/媒体条件，再比较来源及 important、层、特异性，必要时比较作用域接近程度和出现顺序。
- 提前声明 @layer 顺序可稳定第三方和本地样式关系，不要以引入 BEM 代替理解层叠。
- 类似配置来源的优先级，而不是进程级样式单例；CSS 的重要性和层反转在移动主题系统中没有直接等价物。
- 验收记录需要实际修改与观测，不把一次自动检查等同于所有浏览器/辅助技术验收。

## 关联综合实践

把综合页主题、组件与工具样式按明确 @layer 顺序组织，单独制作一次!important层序反转对照后移除冲突。

- [ ] 最终页不依赖全局!important争抢状态
