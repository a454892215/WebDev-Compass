## 动手任务

1. 观察相同颜色的不同语法计算值。
2. 切换为HSL表达，确认浏览器计算后颜色相同。
3. 把背景改为深色并重新评估文字可读性。

在独立副本中修改目标规则，先写下预测，再运行和测量。不得仅复制切换后的CSS并宣布完成。

## 验收标准

- [ ] 用自己的话解释：不同语法可以表达相同颜色；真正的UI决策还需考虑背景、对比和非颜色提示。
- [ ] 执行对照操作后，从目标元素的 Computed 面板读出 `color`，解释原因，而非只复述输出。
- [ ] 完成一次与原例不同的条件变化，记录预期与实际结果；保留键盘焦点、可读文字与必要滚动。
- [ ] 能复现并修正本页下一节的排错任务；没有对应工具链或真机证据时不声称通过。

## 排错任务

故意制造这个问题：透明背景意味着文字也透明。

按“元素是否匹配 → 声明是否生效 → 参照/约束是否正确 → 最终尺寸/绘制”的顺序定位，截取或抄录关键计算值，并用最小修改修复。不要用全局important或overflow:hidden掩盖现象。

## 思考题

为什么“把颜色编码转换当作无障碍对比验证。”会造成误判？它在综合项目中可能影响哪些内容或用户操作？

## 参考要点

- 命名色、HEX、rgb()/rgba()、hsl()/hsla() 都能表达颜色；现代rgb/hsl可用空格和斜线alpha语法。
- 状态不要只用红绿区分，还需文字/图标/结构说明；生产主题应验证文字与实际背景的对比。
- 与Color、ARGB颜色值相似；CSS alpha合成依赖底层背景，主题对比不能只看单一色值。
- 验收记录需要实际修改与观测，不把一次自动检查等同于所有浏览器/辅助技术验收。

## 关联综合实践

为 --accent 和 --focus 写出等值HEX/RGB/HSL表达，并分别检查深浅主题文字/背景对比。

- [ ] 颜色换语法不改变语义状态
- [ ] 错误/收藏不只依赖红绿差异，仍有文字反馈
