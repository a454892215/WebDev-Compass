# 14.5.4 Prisma schema 与迁移：读懂约束，保护 API 兼容性

## 前置、目标与问题

会读JSON接口契约和TypeScript可空类型即可开始。本点面向数据库协作者，不要求把数据库运维作为前端入门门槛。 完成本点后应能解释下面机制、运行对应实验、定位练习中的故障，并说明不能从本地证据推出哪些生产结论。

## 原理与最小上下文

关系数据库schema定义列类型、主键、唯一约束、可空、索引和关联；ORM模型是应用映射，不等于公开API。Prisma ORM 7示例中String?表示可空，@id标识主键，@unique表示唯一；关系字段与实际外键标量分工要区分。数据库约束可能使写入失败，客户端类型检查无法代替服务器校验，也无法解释已部署旧客户端的行为。

下面是同点示例data-lab/schema.prisma的模型声明，需Prisma DSL阅读；不是JavaScript或完整数据库工程。

~~~prisma
model User {
  id          Int     @id @default(autoincrement())
  legacyName  String
  displayName String?
}
~~~

schema.prisma是版本化阅读fixture，省略连接配置，不是完整可部署数据库工程。当前官方还展示Prisma 8新契约/命令且发布状态需核对；本点明确讨论ORM7语法，不把Prisma 8文档中的命令混用到旧项目。执行前必须先查实际package/lock、数据库引擎和匹配主版本文档，不使用无版本latest一键迁移生产。

## 使用场景、边界与误区

迁移采用expand→backfill→contract：先新增可空字段兼容旧应用；后端双写并分批回填；验证数据与旧客户端退出后切换DTO，最后收紧约束/删除旧列。schema改名工具可能生成删列重建，必须检查SQL及数据影响。增加非空、唯一或索引也可能失败或锁表。API DTO应显式投影，不能直接返回ORM实体中的passwordHash等内部字段。回滚应用代码不自动恢复已删数据，需备份和恢复预案。

未安装Prisma CLI、未生成客户端、未执行SQL。数据库版本、锁表/大表性能、回填并发及生产恢复不在本轮实测范围。对外DTO变更仍需14.2.6契约测试和旧客户端兼容评审。

## 与移动端经验对照

类似移动端本地数据库升级，但服务器数据库被多个版本客户端与服务同时使用；App本地一次升级完毕的假设不成立。前端发布可回退，不代表数据库破坏性迁移可逆。

## 先预测再验证

阅读schema.prisma和migration-plan.md，再运行第六项测试：displayName=null时严格DTO拒绝，回填后映射为{id,name}且passwordHash不会外露。测试证明DTO切换前置条件，不是Prisma生成、SQL执行或真实数据库迁移。 先写预测，再运行并解释实际值；独立练习改变输入与故障，不能仅复制通过截图。
