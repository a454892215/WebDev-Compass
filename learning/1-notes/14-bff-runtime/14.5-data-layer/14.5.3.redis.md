# 14.5.3 Redis 的协作边界：会话、TTL、原子限流与故障策略

## 前置、目标与问题

先会14.2会话和限流，以及14.1多进程。先解释为什么单进程Map在多副本部署下不能提供全局一致策略。 完成本点后应能解释下面机制、运行对应实验、定位练习中的故障，并说明不能从本地证据推出哪些生产结论。

## 原理与最小上下文

Redis是独立数据服务，多个BFF副本可访问共享的会话状态与计数。会话cookie携带随机不可猜的session id，服务端以它查询身份、有效期和撤销状态；Redis连接凭据留在服务器。TTL限制存活时间，但滑动过期、最长绝对时限和主动撤销需业务定义。缓存不自动成为身份真相源，访问控制仍在每次请求执行。

下面片段依赖同点示例data-lab/lab.mjs的导出；不是可直接粘贴到浏览器的完整程序。

~~~js
const model = new ExpiringStoreModel()
model.set('session:opaque-A', { tenant: 'A' }, 10, 100)
model.get('session:opaque-A', 110) // undefined
~~~

计数限流需要把增加计数与设置首次窗口TTL作为一个原子操作（例如匹配版本的Redis脚本/事务设计），不能在INCR后假定EXPIRE必达。单独多条命令在崩溃或竞争中可能形成永不过期计数。key包含正确的租户/主体/策略维度；不信任未经代理信任链校验的X-Forwarded-For，不把IP直接当用户身份。固定窗口边界会出现突发，需要时选滑动窗口/令牌桶并核对代价。

## 使用场景、边界与误区

可复用每进程有界Redis连接池，但每请求用户状态不放池对象；连接数由副本数与池上限一起预算。超时、重试上限、TLS、ACL、日志脱敏及Redis故障时fail-open还是fail-closed应按接口风险说明。会话查询故障常应拒绝而不是默认登录，普通非关键读缓存可以降级。Redis分布式锁另有持有者token、超时与失效语义，不应顺便拿“SETNX成功”当跨系统事务保证。

没有安装或连接Redis，不依赖Docker/Colima，不宣称跨进程限流实测。生产选型需要由维护服务的一方给出版本、集群和持久化/SLA，再运行集成/故障测试；这里只要求前端/BFF开发者能读懂角色和失效边界。

## 与移动端经验对照

移动端SharedPreferences是单设备存储；Redis是服务器共享服务，不让浏览器/App直连。Redis连接复用类似网络连接池，不能把业务用户上下文混在连接单例上。
