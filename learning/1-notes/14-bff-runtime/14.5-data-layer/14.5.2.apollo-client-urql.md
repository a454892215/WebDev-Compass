# 14.5.2 Apollo / urql：规范化缓存、SSR 隔离与登出清理

## 前置、目标与问题

先理解14.5.1请求上下文和阶段4的Nuxt SSR/hydration，区分服务端loader、客户端查询缓存和HTTP缓存。 完成本点后应能解释下面机制、运行对应实验、定位练习中的故障，并说明不能从本地证据推出哪些生产结论。

## 原理与最小上下文

查询客户端维护操作状态与结果缓存。Apollo InMemoryCache把对象按__typename和标识字段规范化，再由查询根引用；不同查询可指向同一实体。身份字段若只在租户内唯一，keyFields要纳入tenant等真实业务标识。fetchPolicy决定先读缓存还是网络；cache-first、network-only、no-cache并不等义，network-only通常仍写缓存，no-cache不写入结果。

下面片段依赖同点示例data-lab/lab.mjs的导出；不是可直接粘贴到浏览器的完整程序。

~~~js
const serverCache = newCache()
writeViewer(serverCache, 'A')
const browserCache = newCache().restore(serverCache.extract())
~~~

SSR时每请求创建client及其cache，必要凭据仅用于服务端到上游请求；不要把其他用户缓存或token序列化到HTML。extract/restore是状态转移，不负责安全HTML嵌入，Nuxt应使用框架序列化路径而非把JSON直接拼进script。客户端切换身份时清空旧结果再挂载新身份请求，处理正在进行的旧请求避免晚到响应重新污染；resetStore可能自动重新拉取活跃查询，clearStore不自动重拉，选择应符合登出时序。

## 使用场景、边界与误区

urql默认cacheExchange主要是文档/操作级缓存；需要规范化能力时另配Graphcache，不能默认等同Apollo实体缓存。SSR使用每请求client和ssrExchange，提取本请求结果供客户端恢复；Vue可用@urql/vue或Vue Apollo等适配，不要求引入React。官方React SSR文档只能作为生命周期对照，不能把React hook直接搬到Nuxt。本lab真实运行Apollo缓存核心API，不运行urql适配器或Nuxt插件。

测试覆盖缓存核心和手工状态转移，不代表Apollo Vue / urql插件、HTML序列化、登录切换请求竞态已经集成完成。新项目先按现有REST与useFetch需求决定是否需要GraphQL客户端，避免为缓存概念重复引入库。

## 与移动端经验对照

与移动端本地实体缓存相似，但服务端Nuxt进程同时服务多个用户；“App启动创建一次client”只适合浏览器单身份生命周期，不能直接套到SSR模块。
