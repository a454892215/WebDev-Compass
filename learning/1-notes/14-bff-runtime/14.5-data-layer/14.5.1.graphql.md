# 14.5.1 GraphQL：Schema、N+1、DataLoader 与持久化操作

## 前置、目标与问题

先会14.2的鉴权、错误映射与接口聚合，再理解GraphQL字段执行；不要求先学React。 完成本点后应能解释下面机制、运行对应实验、定位练习中的故障，并说明不能从本地证据推出哪些生产结论。

## 原理与最小上下文

GraphQL由schema定义字段及参数类型，执行器验证操作并调用resolver。一次HTTP请求可以触发很多数据读取，不能把“只发一次请求”误认为“只访问一次数据库”。N+1常见于列表每个元素单独查关联对象；DataLoader收集同一调度批次的load并对重复key去重。批量返回数组必须与输入key一一对应，查无数据按契约返回null或Error，不能直接返回数据库随意排序的rows。

下面片段依赖同点示例data-lab/lab.mjs的导出；不是可直接粘贴到浏览器的完整程序。

~~~js
const context = requestContext('A')
const result = await execute(context)
console.log(context.stats.calls) // 1，而不批处理为3
~~~

本例每次调用requestContext都创建新loader，tenant由已验证身份传入。缓存仅限该次执行，不是共享Redis。只把tenant加进缓存key也不能替代权限查询；更新同一请求内已加载对象后还需clear/prime或重新加载。GraphQL field级权限、输入上限、查询深度/复杂度、超时与成本预算仍须设置。

## 使用场景、边界与误区

Schema Stitching是在网关组合多个子schema并委派字段，除了类型重名还涉及身份传播、关联字段、错误和超时，不是拼接SDL文本。本lab只一个schema，未实现stitching。Persisted Query可以是预注册hash白名单，也可以是APQ的hash未命中后回传全文；后者为网络优化，不天然限制任意查询。本lab采用前者并拒绝未知hash。生产需版本化发布白名单，保留旧客户端需要的操作，并对允许的操作继续鉴权和限流。

这是内存fixture和真实GraphQL执行器，不访问数据库，不实现远程stitching或APQ网络握手，也不代表已经过高并发或恶意查询压测。

## 与移动端经验对照

类似移动端Repository批量读取与请求内memoization，但GraphQL resolver由执行器按字段调用；loader不是进程级Repository单例，也不保证任意await前后都合成一个batch。

## 先预测再验证

运行pnpm test，第一项真实graphql-js执行同一操作：原始路径3次作者读取，DataLoader路径1个批量，输出相同且作者顺序1、2、1正确。第二项并发执行A/B请求，名字分别带A/B，stats独立。第三项拒绝未知hash。修改lab.mjs中loader为模块级共享后，用A先请求再B的变体观察泄漏；仅在隔离副本实验。 先写预测，再运行并解释实际值；独立练习改变输入与故障，不能仅复制通过截图。
