# 14.5.5 WebSocket / SSE：心跳、重连、游标与连接资源

## 前置、目标与问题

先会阶段2的浏览器异步、阶段5实时接口基础及14.1背压。本点从“连得上”推进到断线与资源管理，不能据本地成功宣称生产可靠。 完成本点后应能解释下面机制、运行对应实验、定位练习中的故障，并说明不能从本地证据推出哪些生产结论。

## 原理与最小上下文

SSE是服务器到客户端的UTF-8文本事件流，Content-Type为text/event-stream，事件以空行结束；冒号注释可作心跳，id可作为恢复游标。浏览器EventSource通常自动重连并携带Last-Event-ID，手工fetch读取则要自己处理分帧/重连。WebSocket是双向消息连接，浏览器原生API不能发送协议ping帧，应用心跳与服务端协议ping/pong应区分。

下面片段依赖同点示例data-lab/lab.mjs的导出；不是可直接粘贴到浏览器的完整程序。

~~~js
const delay = backoff(3, () => 0.5) // full jitter: 2000ms
const missing = replay('A', 1) // 仅A的id=3，不重放B数据
~~~

断线后使用有上限的指数退避加随机抖动，鉴权失效不应无限重试。原生EventSource的retry字段是重连间隔提示，不等于本lab的full-jitter算法；若自行调度EventSource重建，先close旧实例避免双连接。游标必须绑定已授权流/租户、检查保留窗口；过旧游标应明确重新拉快照，不能承诺永不丢消息。事件需要稳定id并在客户端去重；断线重放通常是至少一次，不能凭游标宣称恰好一次。

## 使用场景、边界与误区

代理可能缓冲SSE或断开闲置连接，需核对超时、压缩、CDN规则与可观测指标。心跳不是永久存活保证。关闭时清理timer/subscription，服务端慢消费者要有队列上限/背压或主动断开并恢复。所谓连接池要区分浏览器多页/多组件复用、BFF到数据源连接池和每用户长连接；不能把A/B私有流无权限地合并。WebSocket升级、扩容广播和负载均衡另需真实部署测试。

未运行浏览器EventSource或真实WebSocket握手/ping，未经过CDN/移动网络/长时运行。Node fetch测试验证SSE字节/重放/关闭，不等于浏览器原生自动重连验证；生产需另测鉴权、游标过期、队列上限与扩容。

## 与移动端经验对照

类似App前后台重连，但Web标签页可被节流、冻结与销毁；重连不只靠固定timer，须处理页面生命周期、网络恢复与取消。组件卸载后持有连接也会泄漏资源。

## 先预测再验证

第七项确定性测试backoff范围和A/B游标过滤。第八项真实Node回环HTTP SSE：发送心跳、Last-Event-ID=1时只收到A-two/id=3，读取真实Response.body直到目标事件，再cancel并验证服务端close清理心跳。身份A在测试服务器固定，仅用于协议fixture，不是认证接口。 先写预测，再运行并解释实际值；独立练习改变输入与故障，不能仅复制通过截图。
