# 14.1.3 Worker Threads：CPU卸载、输入上限与生命周期

前置：阶段2的异步/事件循环、阶段3的模块与测试。先完成14.1.1，再学习Stream与Worker；配置和进程管理用于运行边界，之后进入14.2的Nitro接口。目标是能解释调度、实现有界工作并判断哪些状态能跨请求/进程共享。

## 解决的问题与机制

worker_threads在同一进程中创建有独立V8隔离实例和事件循环的线程，可以并行执行CPU密集JavaScript。它不是libuv内部I/O线程池，也不等于child_process独立进程。异步网络/文件I/O通常先用Node现成异步API；给每个普通HTTP请求创建worker可能因启动、序列化、内存开销而更慢。

本例用workerData传有界整数，worker计算1到n之和，再parentPort.postMessage返回数字。默认消息采用结构化克隆；ArrayBuffer可转移所有权、SharedArrayBuffer可共享，但后者需要Atomics等同步设计。父级要同时处理message、error和exit，并对请求设截止时间和容量上限。终止worker是生命周期操作，不能当作回滚外部副作用；重复结算必须避免。

## 最小例子与实际观察

下面片段以操作卡中的node-lab目录为运行上下文；导入模块、输入与完整清理代码均随该目录提供。

~~~js
// cpu.mjs通过相对模块URL创建worker，与当前工作目录无关
import { Worker } from 'node:worker_threads'
const worker = new Worker(new URL('./worker.mjs', import.meta.url), {
  workerData: { n: 100000, mode: 'sum' },
})
worker.once('message', value => console.log(value))
worker.once('error', error => console.error(error.message))
// 完整退出、超时、输入验证与清理见cpu.mjs
~~~

verify真实启动worker得到5000050000。负数输入在创建线程前拒绝；crash模式抛出fixture-worker-crash由父级收到error；hang模式保持定时器，父级100ms截止后terminate并拒绝worker-timeout。cpu.mjs正常、错误和超时都等待terminate完成，不留下教学线程。该用例验证控制流程，不宣称比同步求和更快。

## 场景、边界与误区

适合计算、解析或转换的大块CPU工作，先测量瓶颈并限制输入。生产通常建立有界worker池、排队长度、取消与过载拒绝；本lab是一次性线程，不是生产线程池。不要把JWT验签或任意请求都机械卸载，也不要无限增开线程吃满机器。

## 移动开发对照

与Dart isolate的消息通信有可类比处，但Nodeworker线程属于同一OS进程，支持的共享/转移对象和错误生命周期不同；不把Flutter compute接口直接移植。浏览器Web Worker也没有完整Node内建模块。
