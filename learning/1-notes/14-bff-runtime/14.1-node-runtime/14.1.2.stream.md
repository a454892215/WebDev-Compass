# 14.1.2 Node Stream背压：write返回值、drain与pipeline清理

前置：阶段2的异步/事件循环、阶段3的模块与测试。先完成14.1.1，再学习Stream与Worker；配置和进程管理用于运行边界，之后进入14.2的Nitro接口。目标是能解释调度、实现有界工作并判断哪些状态能跨请求/进程共享。

## 解决的问题与机制

Readable产生数据，Writable消费数据，Duplex有双向通道，Transform在读写之间转换。背压让快生产者等待慢消费者，避免把全部输入堆入队列。普通字节模式highWaterMark以字节计，objectMode以对象计；它是触发暂停请求/返回false的阈值，不是整个进程的严格内存上限。单块过大、其他缓存、实现细节都能超出它。

Writable.write返回false表示该块已被接收，但继续生产应等待drain；不能误以为写入失败而重发该块。end只表示不再写入，finished或pipeline的Promise完成后才能确认收尾。生产代码优先stream/promises.pipeline连接源、变换和目标，错误会传播并清理参与的流；HTTP响应等资源要另外考虑头已发出时无法再改状态。Node Stream和浏览器WHATWG ReadableStream是不同接口，跨边界要使用相应适配器，不能把getReader放到Node Writable上。

## 最小例子与实际观察

下面片段以操作卡中的node-lab目录为运行上下文；导入模块、输入与完整清理代码均随该目录提供。

~~~js
import { Writable } from 'node:stream'
import { once } from 'node:events'
import { finished } from 'node:stream/promises'
const sink = new Writable({ write(chunk, encoding, done) { done() } })
const completion = finished(sink)
if (!sink.write(Buffer.from('hello'))) await once(sink, 'drain')
sink.end()
await completion
~~~

stream.mjs向延迟回调的Writable写32块各1024字节，阈值2048。尊重背压时16次等待，writableLength峰值2048；忽略false时峰值32768。两者最终字节数都32768，所以只看输出文件相同发现不了内存风险。另一用例让sink在写入时callback(Error)，验证pipeline拒绝且源和目标均destroyed。峰值只指本例Writable队列长度，不是RSS或真实网络吞吐基准。

## 场景、边界与误区

用于上传、下载、压缩、日志或代理大响应；同时控制总大小、并发与超时。把所有chunk先收进数组再Buffer.concat通常取消了流式节省内存的收益。手写事件管道要处理错误和取消，不能只监听drain。

## 移动开发对照

类似受控生产/消费通道，但不是Dart Stream监听后就天然具有相同的Node写侧背压语义；暂停、缓冲单位、取消和错误传播要分别核对。移动端读小文件常不暴露的问题，在服务端并发上传时会放大。
