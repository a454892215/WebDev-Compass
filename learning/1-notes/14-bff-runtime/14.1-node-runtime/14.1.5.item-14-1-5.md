# 14.1.5 进程管理与cluster：状态边界、优雅退出和PM2取舍

前置：阶段2的异步/事件循环、阶段3的模块与测试。先完成14.1.1，再学习Stream与Worker；配置和进程管理用于运行边界，之后进入14.2的Nitro接口。目标是能解释调度、实现有界工作并判断哪些状态能跨请求/进程共享。

## 解决的问题与机制

cluster创建多个Node子进程，各自有独立堆与事件循环，可在支持的服务器场景共享监听端口；worker_threads是同进程线程，两者不能混称。PM2是可选进程管理器，可做重启、cluster配置、日志和reload；容器或平台已有进程监管时不必叠加第二套管理器。CPU核数不是无限开实例的理由，还要核内存、数据库连接和上游配额。

进程级Map适合存只读配置或可丢失的局部缓存，但单机多进程和多副本之间不共享。会话、限流和任务去重若要求全局一致，需要合适外部存储或平台机制，不靠sticky路由修复所有一致性问题。优雅退出通常先标为未就绪、停止接新请求、排空在途请求与队列、关闭外部连接，最后退出；应有最长截止时间和强制结束兜底。崩溃重启要退避与上限，避免坏配置触发无穷重启风暴。

## 最小例子与实际观察

下面片段以操作卡中的node-lab目录为运行上下文；导入模块、输入与完整清理代码均随该目录提供。

~~~js
// pm2-observe.config.cjs是配置观察，不代表本轮运行PM2
module.exports = { apps: [{ name: 'bff', script: '.output/server/index.mjs',
  exec_mode: 'cluster', instances: 2, kill_timeout: 5000,
  env: { NODE_ENV: 'production' },
}] }
~~~

processes.mjs真实cluster.fork两个进程，通过IPC各自increment一次；报告有两个不同pid且count均为1，证明局部变量没有合并为全局2。收到shutdown后各自disconnect，主进程观察两个exit且code0，设置4秒失败兜底。实验没有监听HTTP端口、连接数据库或运行PM2，因此不能把IPC正常退出当成生产无损reload证据。

## 场景、边界与误区

需要多核并发和服务生命周期控制时评估；先问部署平台是否已管理实例、自动扩缩容和滚动发布。WebSocket等长连接要独立设计排空/重连，内存会话不能靠“只有一个仓库”保证共享。仅改PM2 instances不等于完成高可用。

## 移动开发对照

移动App进程通常服务当前设备会话，服务端同一版本可能有多个进程/副本同时服务多用户。Android进程被杀或Flutter热重载经验不等于服务器滚动发布；要处理在途请求、外部连接和跨副本状态。
