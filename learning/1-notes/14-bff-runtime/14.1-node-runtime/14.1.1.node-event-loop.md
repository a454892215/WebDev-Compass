# 14.1.1 Node.js事件循环：I/O阶段、nextTick与ESM差异

前置：阶段2的异步/事件循环、阶段3的模块与测试。先完成14.1.1，再学习Stream与Worker；配置和进程管理用于运行边界，之后进入14.2的Nitro接口。目标是能解释调度、实现有界工作并判断哪些状态能跨请求/进程共享。

## 解决的问题与机制

浏览器的任务、微任务与渲染机会不能直接替换成Node阶段图。Node通过libuv驱动I/O，JavaScript回调通常在当前隔离实例的主线程运行；异步I/O还可能由操作系统或libuv线程池完成。简化阶段包括timers、pending callbacks、idle/prepare、poll、check、close callbacks；这是一张循环示意图，不能拿画图起点推导所有代码的绝对顺序。Node20/libuv1.45起，每次循环的timer处理位置调整到poll之后，同时保留进入循环前的兼容处理。定时器阈值是最早可调度条件，不是准点承诺。

process.nextTick不是一个libuv phase，递归填充会推迟I/O。Promise.then与queueMicrotask进入微任务队列。在本lab的CJS顶层，nextTick先于Promise微任务；ESM模块求值自身处于异步加载/微任务上下文，本例Promise和queueMicrotask先于nextTick。不能背成nextTick永远最先。I/O回调内安排setImmediate和setTimeout(0)，本例check阶段的immediate先执行；顶层同时安排两者不作稳定先后承诺。

## 最小例子与实际观察

下面片段以操作卡中的node-lab目录为运行上下文；导入模块、输入与完整清理代码均随该目录提供。

~~~js
// loop.cjs的核心；完整I/O和输出见真实文件
const order = ['sync']
process.nextTick(() => order.push('nextTick'))
Promise.resolve().then(() => order.push('promise'))
queueMicrotask(() => order.push('queueMicrotask'))
setImmediate(() => console.log(order))
~~~

先预测loop.cjs与loop.mjs的前四项，再运行总验证。CJS得到sync→nextTick→promise→queueMicrotask；ESM得到sync→promise→queueMicrotask→nextTick。CJS读取本文件成功后的immediate-in-io在timeout-in-io之前。测试只断言这些有上下文的关系，不断言poll全局耗时或顶层timer竞速。

## 场景、边界与误区

适合定位SSR或BFF里的长同步回调、nextTick饥饿和“为何日志顺序与浏览器不同”。有耗时CPU任务先控制输入和测量，再分块或转worker；异步函数中没有await的长循环仍会阻塞。

## 移动开发对照

Android Handler/Looper与Dart isolate也有事件调度，但没有同一套libuv阶段和nextTick规则；Flutter帧调度知识不能推导Node定时器顺序。Node服务被阻塞会同时拖慢多个用户，浏览器还额外面临渲染和输入延迟。
