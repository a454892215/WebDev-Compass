# 14.3.4 SSR Cookie/Header：入站身份与上游转发白名单

## 目标与前置

本节衔接阶段4 Nuxt数据获取、阶段5身份/API和本阶段14.1–14.2；读后应能解释边界、复现具体故障，并把结论用于实际BFF审查。Next为选修，其余按14.3.2→14.3.3→14.3.4→14.3.5学习。

## 原理与取舍

有三段不同的传播：浏览器到 Nuxt、Nuxt SSR 到本地 API、BFF 到外部上游。浏览器依据 Cookie 的域/路径/SameSite/Secure 策略发送 Cookie；SSR 中普通 $fetch 并不自动代表浏览器当前用户。Nuxt useFetch 访问相对本地路径会使用请求上下文；useRequestFetch 专门帮助 SSR 转发当前请求，避免硬编码整站绝对 URL导致身份丢失。绝对 URL 的转发限制必须核当前 Nuxt 版本，不把通用 fetch 当透明代理。

对外部 API 则明确允许哪些头。不能直接展开全部入站 headers：Cookie、Authorization、Host、Connection、X-Forwarded-* 等有不同信任边界；用户传入的 X-User-Id 或代理头不能替代服务端身份校验。固定上游地址来自服务器配置，而不是任意 query URL，减少 SSRF；重定向也可能改变目标，需单独限制。服务端验证 Session 后，根据需求换成面向目标服务、权限受限的凭据，发送最小 DTO。

上游 Set-Cookie 不会因服务器 fetch 自动安全地进入浏览器。若确有代理登录需求，应专门处理每条 Set-Cookie 的域、路径、安全属性和允许来源；本课默认不把外部 Cookie透传。HttpOnly 防止 JavaScript直接读 Cookie，不阻止浏览器发送；SameSite/CORS 也都不等于完整授权。生产 Cookie 用 HTTPS/Secure，单域适用时优先 __Host- 前缀；本地HTTP实验的命名/标志例外必须明确。

## 最小例子与观察

runtime-lab 的 upstreamHeaders 丢弃入站 cookie、authorization 和 x-forwarded-for，只接受有长度/字符边界的 accept-language，并使用函数参数中的服务端 fixture token。测试输入包含伪造授权和 CRLF；结果不得包含这些入站值。fixture token 是公开测试字符串，不是生产密钥。

~~~ts
// Nuxt app setup 中，只请求固定相对路径的本地 API。
const requestFetch = useRequestFetch()
const { data } = await useAsyncData('account-summary', () => requestFetch('/api/summary'))
~~~

这个片段说明官方上下文传播用法，不承诺主项目必定用相同路由名。切换登录用户时，应按主项目的明确动作清理/刷新旧状态；仅改 key 不能替代 Session 校验。

## 移动开发对照与误区

移动 HTTP client常由 App 显式注入 token；浏览器 Cookie有自动发送和同站策略，SSR服务又是一跳独立客户端。复用移动端HTTP拦截器设计时，要明确每跳目标和身份来源，不能把一个“全局带所有头”的拦截器搬到服务器。
