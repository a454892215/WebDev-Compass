## 原理与取舍

前置是14.1的进程与14.2的请求鉴权。Nuxt 的 Nitro 负责服务器端请求处理；server/api 文件映射到 /api，server/routes 不加该前缀。server/middleware 在服务器路由前执行，适合校验请求和扩展 event.context；它与 app/middleware 的页面导航守卫职责不同。页面守卫不能保护别人直接调用的 API。Nitro plugin 用于运行时钩子，初始化通常属于进程/实例生命周期，不能当作“每用户登录一次”。

一次请求有自己的 event 和 context，身份校验后把最小 principal 放在该 context，异步调用显式传递它。模块顶层可保存不可变配置、连接池或经过设计的共享存储客户端；不能保存 currentUser、某用户 token 或一个会被覆盖的全局 ref。单个 Node 实例会交错处理多个用户，await 不是事务锁。请求 A 挂起时 B 改了模块变量，A 恢复就可能读到 B 的身份。

页面用 useState 在 Nuxt 上下文中创建 SSR 友好状态，但它会序列化到 payload；密钥和完整 Session 不能放进去。服务端 runtimeConfig 的私有字段留在 server，public 字段可发送给浏览器。部署环境变量覆盖需符合 Nuxt 的 runtimeConfig 命名约定，不能将“变量名没写 public”当作任何代码都不会泄露的保证。连接池共享与用户状态共享要分别分析。

## 最小例子与观察

本节 runtime-lab 的 requestView 使用函数调用内 context，并用人为闸门使 A/B 交错：A 暂停、B 完成、A 恢复。断言两次输出各自身份，展示请求局部数据原则；它是 Node 模型，不是 Nitro 实际路由验证。主 Nuxt 综合项目另做真实双会话 HTTP/SSR 验证。

在 Nuxt server API 中，可采用以下最小模式；authenticate 是上下文依赖，示意不等于本仓库已存在的函数：

~~~ts
export default defineEventHandler(async (event) => {
  const principal = await authenticate(event) // 必须先实现 Session/权限校验
  event.context.principal = principal
  return { displayName: principal.displayName } // 最小可见 DTO
})
~~~

完整运行入口以阶段14综合实践 README 为准；不要把上面未定义的 authenticate 原样粘入并声称可运行。

## 移动开发对照与误区

移动 App 的进程通常属于当前安装/用户会话；服务端进程同时服务多个人。可借鉴移动端分层和依赖注入，但服务端请求作用域需独立建立；不因为不能全局保存 currentUser 就禁止连接池。浏览器里的状态也要在退出/切账号时清理，SSR隔离不会代替客户端状态管理。
