# 14.3.3 SSR 数据获取：识别 waterfall 与安全并行

## 目标与前置

本节衔接阶段4 Nuxt数据获取、阶段5身份/API和本阶段14.1–14.2；读后应能解释边界、复现具体故障，并把结论用于实际BFF审查。Next为选修，其余按14.3.2→14.3.3→14.3.4→14.3.5学习。

## 原理与取舍

先画数据依赖图。两个请求无依赖时先发起两个 Promise，再统一 await；如果订单查询依赖身份中的 userId，则身份校验必须在前，不能为了并行而先请求任意用户订单。SSR 的 waterfall 可能来自页面串行 await、父子组件串行加载、BFF 聚合或数据库 N+1；只把两个组件放在同一页面不会自动证明消除了链路。

Nuxt useFetch/useAsyncData 把服务端结果装入 payload，使 hydration 可复用；在 setup 直接裸用 $fetch 容易服务端和客户端各请求一次。处理函数应返回可序列化、非 null/undefined 的有效结果，参数、key 和客户端状态应匹配实际页面语义。key 相同的调用可能共享状态，不能依赖任意 key 隐藏跨用户缓存问题；服务端响应缓存必须独立设计。

Promise.all 适合任一必要分支失败就整体失败；Promise.allSettled 或分支捕获适合允许可选模块降级，返回结构要标明 partial 状态。取消不会由 Promise.all 自动传给另一个网络请求，必须把 AbortSignal 传入实际 fetch，并为整个预算、单分支预算和客户端断开制定策略。并行不能无限放大：有上游限流和连接池时应限并发；还要减少非必要数据和序列化体积。

## 最小例子与观察

runtime-lab 的 aggregate 测试让两个 loader 都在同一个 gate 等待，并在放行前断言两者已经启动。该方法验证调度关系，不靠“总耗时恰好小于100ms”等易抖阈值。实验只演示调度，不声称模拟真实服务器吞吐。

~~~js
const profilePromise = loadProfile()
const catalogPromise = loadCatalog()
const [profile, catalog] = await Promise.all([profilePromise, catalogPromise])
~~~

Nuxt 页面应在 setup 中结合 useAsyncData 包装真实 BFF 入口；不要把需保密的上游 token 放在 handler 返回值。真实故障/预算由主 BFF 的接口测试验证。

## 移动开发对照与误区

Flutter 的 Future.wait 可类比独立异步任务汇合，但 Nuxt 还要考虑 SSR payload/hydration、共享请求上下文和响应缓存。CPU 密集工作不是简单加 Promise.all 就能利用多核，需参考14.1 Worker 与隔离边界。
