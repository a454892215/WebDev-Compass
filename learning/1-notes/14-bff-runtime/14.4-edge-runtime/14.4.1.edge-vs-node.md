# 14.4.1 Edge 与 Node：按平台、数据位置和 API 选运行时

前置：14.1 Node 运行时、14.2 BFF。目标是为一个具体接口比较运行时，而不是认为“Edge”这个名字必然更快。

## 原理与选择

Edge 描述计算靠近访问者的部署方式；Node 描述 JavaScript 运行时，两者不是完全相反的分类。CDN 在边缘缓存静态内容，也不等于整套 SSR 已经运行在边缘。端到端耗时还包括冷启动、函数到数据库往返、聚合、序列化和响应传输；靠近用户却远离数据库，可能增加总耗时。

先列依赖的 API 与部署产物，再查特定供应商/兼容日期：原生扩展、文件系统、TCP、动态代码、包体积、CPU 时间、内存、请求时限和连接配额。CPU 时间不是墙钟时间；等待网络和消耗 CPU 的计费/限额需分别核对。不要把平台营销中的“无冷启动”当成所有依赖、区域和负载下的零延迟保证。

Cloudflare 当前 Node 兼容文档按 compatibility_date 区分行为：2026-08-04 起默认启用对应 Node 兼容能力；旧日期可能需要显式标志。可导入模块也可能只是部分实现或会抛错的 shim，必须逐 API 核查。其文件系统支持也不表示可把本地文件作为跨实例持久数据库。Vercel Edge 的支持表不同，不能从一个平台推断另一个。

## 最小例与适用边界

本组 policy.mjs 使用 Request、Response、URL、Web Crypto，便于解释可移植处理逻辑；用 Node 成功运行，只证明本地 Web API 路径成立，不能证明 cloudflare binding、平台打包或限制通过。主 Nuxt 项目采用 Node/Nitro，选修 Edge 是独立的部署评估，不能直接把实验文件当适配器。

## 移动端对照与误区

类似选择 Android 后台工作与前台线程时先看任务约束，但 Edge 不是“Web 的后台线程”。同一个函数可能在多个隔离实例运行，内存全局变量不保证共享、顺序或持久；不要用它保存用户会话、全局限流额度或上传进度。与移动端进程不同，服务端实例同时处理多个用户。
