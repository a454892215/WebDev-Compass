# 14.4.2 Vercel Functions 与 Cloudflare Workers：入口、适配与部署核对

前置：14.4.1。目标是看懂平台入口和 Nuxt 的部署责任，避免照搬过时模板。

## 当前产品与入口

地图保留 Vercel Edge Functions 历史名称以保护链接。当前 Vercel 文档将其纳入 Functions，并推荐 Node.js 运行时。该页还明确 Next.js 16.3 起页面/路由不再支持 runtime='edge'；这属于 Next 分支的版本约束，不是 Nuxt 的配置方式。不要将旧 App Router 片段当通用部署脚手架。

Cloudflare Worker 的模块入口常见为 export default { async fetch(request, env, ctx) { ... } }。env 是平台注入绑定，不是浏览器公开变量；ctx.waitUntil 可延长被允许的后台工作，但不等于可靠任务队列或无限后台进程。Vercel 的入口、生命周期和限制另查对应文档，不能只把导出名字改掉就迁移。

## 从纯逻辑到真实适配器

本地 createHandler 接收 resolveSession、catalog 等依赖，测试构造 Request 并读取 Response。真正部署时，适配器还要负责受信元数据、会话存储、密钥绑定、超时、日志脱敏与平台缓存。Nuxt SSR 应按该版本 Nitro preset/平台官方集成构建，不能将 app 的 server 目录直接上传成一个独立 Worker。

选择顺序：先确认 Node/Nitro 能否满足业务，再为明确的全球低延迟/平台绑定需求比较 Worker；接着固定兼容日期与依赖，检查构建产物、绑定、预览和撤销路径。配额及免费额度会变化，本文不固定一个永久有效数值。

## 最小观察与误区

运行实验的 GET /catalog、POST /catalog、GET /unknown，分别观察200、405、404，理解路由契约。此处没有安装 Wrangler、没有生产发布、没有测试真实冷启动，官方部署核对卡是下一步，不把静态配置片段标成部署完成。

## 移动端对照

类似同一业务逻辑可有 Android/iOS 平台适配层，但云平台的身份、生命周期、网络和存储语义仍需逐项测试；用一个通用 API 不意味着所有平台插件都兼容。
