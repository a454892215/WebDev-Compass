# 14.4.4 Workers KV、D1 与 Global Config：一致性决定用途

前置：14.4.3。目标是按读写和一致性需求选择存储，不把“边缘存储”当同一种数据库。

## 三类职责

Workers KV适合读多写少、可接受延迟传播的键值配置。它是最终一致存储：其他位置可能继续看到旧值，连“不存在”的负查找也可能被缓存。官方描述传播可达60秒或更久，这不是严格60秒上限；同位置读到新值也不应当作保证。不要用普通get再put组合实现全局原子计数、立即注销或库存扣减。需要更强协调时评估Durable Objects或合适的数据库，而不是增加一个本地Map。

D1是SQL数据库；通过env绑定使用参数化prepare/bind，避免把输入拼进SQL。batch内语句按顺序作为事务执行，某条失败会回滚该batch；不能由此推断跨数据库/跨外部服务也有同一事务。开启读副本时需理解Sessions API和bookmark提供的会话顺序一致性；它不是Web登录session，也不是无需约束的全球任意读都最新。主库写入、只读副本和业务授权分别处理。

地图中的Vercel Edge Config当前官方入口重定向Global Config，定位为低延迟读取配置。适合少变的开关/路由规则，不默认作为订单或会话可变数据库；密钥与可公开配置应分开。更名和功能以当前官方为准，项目不要盲目替换旧SDK导入名。

## 参数绑定观察片段（未连接 D1）

下面的db是调用方提供的D1绑定，name是外部输入；占位符负责值绑定，仍须另做身份/租户授权。

~~~js
async function findProduct(db, name) {
  return db.prepare("SELECT id, name FROM products WHERE name = ?").bind(name).all()
}
~~~

这不是本轮执行过的数据库查询，不能用Node的Map测试代替D1事务测试。

## 最小模型

createEventualStore固定两个位置：region-b先读revoked=false；主存写true后旧副本仍false；显式refresh后才true。这是用可控时序解释最终一致，不模拟真实传播延迟、不调用KV/D1/Global Config，也不是它们的SDK。把它用来写出注销业务需要的保证，然后选择真实存储。

## 移动端对照与误区

类似离线客户端可能读旧数据，但云副本一致性由服务契约决定，不因某一次读写测试成功而升级。D1 session是读顺序上下文，不是Android单例或登录态；不能把所有“session”混成一件事。
