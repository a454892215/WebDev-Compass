# 14.6.1 分片上传：断点续传、并发与最终完整性

## 前置与目标

先掌握阶段5 HTTP/鉴权与阶段10安全，以及14.2 BFF身份和请求校验；本组按14.6.1 → 14.6.2 → 14.6.3阅读。能解释机制、运行反例并为Nuxt上传模块制定可验证边界。无需为普通小文件强制引入分片或云平台。

## 核心原理

上传任务需要身份、uploadId、文件总长、分片大小、整体摘要、已收分片集合和状态。uploadId是资源标识，不能代替鉴权。每次列举、写分片、完成、取消都按服务端会话解析出的owner查所有权。分片可乱序传输，完成时必须按序组装，核对总长和整体摘要；每片hash只证明传输一致，不能代替整个文件或权限验证。

## 从一次请求到可恢复任务

小文件先用单次上传；当重传成本或网络波动值得额外状态成本时才选分片。流程是init → list/put parts → complete → 检查/扫描 → ready；取消走abort。客户端保存uploadId和文件指纹，恢复前重新向服务端列举已经确认的分片；仅靠localStorage里的“进度100%”不能证明服务端已收到。用户重新选文件时对照大小/摘要，名称相同不足以确认同一内容。

浏览器File是Blob子类，可用file.slice(start,end)得到片段；end不包含末字节。上传进度应按已确认字节累计，重试同片不要重复累加。页面刷新不能自动保留文件访问能力，往往需要重新选文件；不要许诺浏览器后台永不暂停。大文件计算摘要需增量算法/Worker等方案评估，不能直接crypto.subtle.digest(await file.arrayBuffer())后声称内存恒定。

## 并发不是无限Promise.all

队列只允许N个工作者取片，本例N=2、最大允许8。传输失败后先等待本轮已在途工作者结束，再报告失败，避免恢复与遗留写入交叠。下一次list跳过已确认分片；重复相同片内容幂等，重复相同索引但不同内容拒绝。生产环境还需每用户/任务/总磁盘配额、超时、过期任务回收、可取消请求及合理退避；不能无限重试413/401等永久错误。取消在途fetch不必然撤销已落盘分片，最终状态以服务器为准。

## 最小例与源码入口

upload-lab中的uploadMissing(store,owner,id,bytes,chunkSize,concurrency,transfer)展示有界队列；UploadStore.put校验索引、预期长度和每片SHA-256，complete再次验证完整文件。先读test的“resume only missing chunks”，预测sent不含0，再运行观察peak=2；这里是真实异步并发控制，存储和网络是本地内存接口，尚未实现HTTP或持久化。

## 使用边界与移动端对照

Android后台任务调度和浏览器页面生命周期不同，不能把WorkManager保证搬到H5。该实验每文件上限1MiB，故意用Buffer.concat简化完成校验，不适用于GB文件；生产应流式读取/存储并限制解码资源。S3 Multipart有自己的part大小/数量/ETag规则，本例8字节片是算法教学，不能直接作为S3分片配置。整体SHA-256不是“任何S3 ETag都等于MD5”的证明。

## 自足最小调用

在示例的upload-lab目录以node --input-type=module运行下列代码；命令路径见配套示例。不需要浏览器或云账号。

~~~js
import { UploadStore, uploadMissing, digest } from './upload.mjs'
const bytes = Buffer.concat([Buffer.from([137,80,78,71,13,10,26,10]), Buffer.from('demo-data')])
const store = new UploadStore()
const id = store.create('alice', bytes.length, 8, digest(bytes))
await uploadMissing(store, 'alice', id, bytes, 8, 2,
  async (i, part, hash) => store.put('alice', id, i, part, hash))
console.log(store.list('alice', id)) // [0, 1, 2]
console.log(store.complete('alice', id, 'image/png')) // quarantine
~~~
