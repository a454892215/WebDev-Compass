# 9.3.5 HTTP/3、103与历史Server Push：区分协议层证据

前置：阶段3构建、阶段6资源/缓存基础与阶段7托管；先读机制再跑操作卡。性能进阶以真实资源发现、协议和缓存维度为重点，不重复只看一张优化截图。

## 解决什么问题与原理

HTTP/3使用QUIC，可降低部分连接/传输阻塞成本，但丢包、拥塞、握手复用、服务端与浏览器支持决定结果；应用依赖瀑布不会因升级协议消失。103是最终响应前的Informational Hints，让支持的浏览器更早发现子资源；不是最终200，也不是服务器主动推完整资源。HTTP/2 Server Push是另一机制，Chrome已移除支持，不应按老教程作为默认方案。

## 最小机制片段

```javascript
// lab server /early-hints：
response.writeEarlyHints({link:"</noncritical.css>; rel=preload; as=style"});
// 工作完成后另发送最终200；必须保留HTML里的正常资源声明。
```

## 实际实验与边界

lab Node客户端实际先收到103 Link后收到最终200；它运行HTTP/1.1，只验证信息响应机制。浏览器实际利用103通常需支持的H2/H3部署链，反向代理可能吞103；本轮无真实TLS/H3/CDN/ServerPush或线上TTFB改善。

## 误区与移动端对照

先优化资源发现与依赖链，协议实验在真实支持环境重复采样；不复活已退场的Push当万能加速。

移动端也关注资源字节与缓存；Web还受HTML发现链、CSS阻塞、字体/图片选择、共享HTTP缓存和浏览器提示策略影响，不能把App资源打包或原生图片缓存经验直接等同。
