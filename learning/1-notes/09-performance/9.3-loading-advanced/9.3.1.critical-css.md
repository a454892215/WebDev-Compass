# 9.3.1 Critical CSS：按首屏提取与非关键样式边界

前置：阶段3构建、阶段6资源/缓存基础与阶段7托管；先读机制再跑操作卡。性能进阶以真实资源发现、协议和缓存维度为重点，不重复只看一张优化截图。

## 解决什么问题与原理

关键CSS不是全部CSS都内联，而是当前页面/视口首屏呈现必须的样式集合。内联可减少请求链，却增加HTML体积、重复传输与CSP管理成本；拆分需按路由/断点/状态覆盖，不能只在一张截图上提取。焦点、错误和必要布局不能被误归为非关键。CSS media拆分和延后激活是不同机制，预加载也不会自动应用样式。

## 最小机制片段

```javascript
const sheet = document.querySelector("#noncritical");
sheet.addEventListener("load", () => { sheet.media = "all"; }, {once:true});
// 完整lab还处理已加载状态；关键焦点样式始终内联。
```

## 实际实验与边界

lab首屏layout/focus内联，600ms延迟的noncritical.css以media=print下载，模块等load再切all；实际FCP早于CSS responseEnd。这里只延迟离屏装饰，没有运行自动Critical提取器，也没有证明业务LCP改善。无JS时装饰不激活，但正文/链接/焦点仍可用。

## 误区与移动端对照

先证明资源链/样式依赖，再减少关键路径；不要所有路由重复内联整站CSS。

移动端也关注资源字节与缓存；Web还受HTML发现链、CSS阻塞、字体/图片选择、共享HTTP缓存和浏览器提示策略影响，不能把App资源打包或原生图片缓存经验直接等同。
