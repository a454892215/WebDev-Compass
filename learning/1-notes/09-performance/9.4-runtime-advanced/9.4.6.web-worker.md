# 9.4.6 Worker任务池：有界队列、转移所有权和取消

前置阶段2异步/浏览器、阶段3测试和阶段4–8 Vue/Nuxt/状态/边界；先观察真实瓶颈，再选择策略。

## 解决什么问题与机制

Worker不直接操作DOM，也不是无限吞吐；启动、消息、结构化克隆和内存有成本。按任务id匹配结果、限制活动数/队列、处理error与dispose。transfer list转移ArrayBuffer所有权，发送端buffer detach，不能继续读取或假定可复用；TypedArray的buffer才是可转移对象。终止Worker会中断当前工作，需要拒绝待处理Promise并清理队列；合作式取消需任务主动检查，不能靠主线程标志改变Worker同步循环。

## 最小片段

```javascript
const worker = new Worker(new URL('./worker.mjs', import.meta.url), {type:'module'});
const values = new Uint32Array([1,2,3]);
worker.postMessage({id:1,buffer:values.buffer}, [values.buffer]);
console.log(values.byteLength); // 0：原buffer已转移
// 生命周期结束时worker.terminate()；池的Promise拒绝逻辑见lab。
```

片段上下文与完整可运行机制见操作卡，不把可选 API 当所有浏览器都支持。

## 实验与使用边界

lab为1活动+最多2排队的单Worker池，第四项立即Queue full。真实transfer后主buffer.byteLength=0、三个结果正确；cancelAll拒绝活动和队列并terminate，下次submit按需新建成功。不是多worker伸缩/跨标签调度或生产吞吐证明。

线程池数量须依据任务/设备和预算，navigator.hardwareConcurrency只是提示，不是应全开线程数。

## 移动开发对照

移动端也关注UI线程、生命周期和列表窗口；浏览器的task/微任务/DOM/Worker/GC与框架原生线程不同，不能把移动API名字套为同一机制。
