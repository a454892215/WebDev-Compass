# 9.4.2 INP排查：输入延迟、处理和呈现不能混成一项

前置阶段2异步/浏览器、阶段3测试和阶段4–8 Vue/Nuxt/状态/边界；先观察真实瓶颈，再选择策略。

## 解决什么问题与机制

INP针对一次访问中交互延迟的代表值，包含input delay、processing duration与presentation delay；正式聚合须使用正确算法或web-vitals，不能用单个handler用时、longtask或TBT替代。EventTiming的processingStart/End帮助定位处理部分，duration量化并可能受隐私精度影响；没有超过上报阈值的条目不能记为INP=0。先提供即时状态，再减少阻塞/同步布局/过大更新；把请求等待或最终内容完成延迟和下一帧响应区分。

## 最小片段

```javascript
if (PerformanceObserver.supportedEntryTypes.includes('event')) {
  const observer = new PerformanceObserver(list => console.log(list.getEntries()));
  observer.observe({type:'event', buffered:true, durationThreshold:16});
  // 离开实验时observer.disconnect()，原始entry不等于完整INP。
}
```

片段上下文与完整可运行机制见操作卡，不把可选 API 当所有浏览器都支持。

## 实验与使用边界

lab真实click与event条目记录interactionId、processingStart/End和duration，阻塞/分片按钮的结果用于诊断，不称本地数据就是生产INP。完整web-vitals采集见9.1，soft-navigation等新指标按支持检测。

debounce可能减少次数却增加等待；选取搜索等语义允许的场景，不能吞掉支付/提交动作。

## 移动开发对照

移动端也关注UI线程、生命周期和列表窗口；浏览器的task/微任务/DOM/Worker/GC与框架原生线程不同，不能把移动API名字套为同一机制。
