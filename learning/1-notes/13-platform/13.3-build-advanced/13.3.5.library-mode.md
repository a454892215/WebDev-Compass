# 13.3.5 库模式双格式与声明：真实import、require和类型消费者

前置阶段3构建/类型、7部署、8模块边界、12包消费；本组先确认目标和工具角色，再实现插件/缓存/格式。目标是按真实产物与失败路径解释取舍，不以工具品牌推导能力。

## 机制与最小示例

库的格式、扩展名、package type、exports和types是一组消费契约。ESM/CJS不是简单把同一个.js文件换名字；条件导出需让Node与TypeScript分别选对入口。Vite library mode负责JS，tsc/vue-tsc或合适工具负责声明，产物必须由仓库外形态消费者验证。

build-lab/library用Vite实际输出index.mjs/index.cjs，tsc输出index.d.ts，再为当前无相对import的纯函数声明生成同内容index.d.cts。package.json将import/require各自映射default/types。临时node_modules包链接的ESM/CJS进程均通过公开入口得到5，.mts/.cts真实tsc正例与@ts-expect-error错误参数检查通过。

## 场景、边界与误区

临时消费者是本地包目录链接，不是registry安装或远程发布。复制.d.cts只对本例简单无模块图声明成立，复杂库需分别生成/验证。双包若各初始化全局状态可能产生双实例风险；本例纯函数无共享状态，不推导所有状态库都可安全双格式。主core若只发布ESM不应误称已有CJS。

## 移动开发对照

像AAR/平台产物加API声明，但JS加载器/扩展名与条件导出是Web/Node特有边界；.d.ts不能代替运行产物，也不能保证运行时校验。
