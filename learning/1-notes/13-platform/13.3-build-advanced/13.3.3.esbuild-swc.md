# 13.3.3 转换器、打包器与类型检查：Vite8/Rolldown/Oxc及esbuild/SWC

前置阶段3构建/类型、7部署、8模块边界、12包消费；本组先确认目标和工具角色，再实现插件/缓存/格式。目标是按真实产物与失败路径解释取舍，不以工具品牌推导能力。

## 机制与最小示例

转换把TS/JSX/新语法变成目标JS；打包还处理模块图、解析、chunk和副作用；类型检查验证静态类型，三者不能互推。Vite8官方默认统一到Rolldown bundler与Oxc编译工具链，不应继续写成所有Vite都默认esbuild开发+Rollup生产。旧配置兼容层和依赖树里的包名不证明某API本轮执行。

真实verify创建const total:number="not-a-number"的隔离TS。Vite library转换成功生成JS，单独tsc --noEmit产生TS2322。这说明转换成功不等于类型正确。项目正常构建也从app.ts擦除类型并在浏览器执行；本轮没有安装/调用esbuild或SWC API。

## 场景、边界与误区

esbuild有transform/build等不同API，SWC core transform有明确parser/target/module配置；选它们应先看框架/plugin已承担什么，不叠加两个编译器只求“更快”。target是语法输出范围，不自动补运行时Web API；declaration也不是Vite转换自动生成。源码映射、装饰器、宏及React/Vue编译要按具体工具核。

## 移动开发对照

原生编译通常让人习惯“编译成功即类型通过”，Web快速转换常故意不做完整类型检查；因此需要独立tsc/vue-tsc门禁，像多阶段构建分工而非重复浪费。
