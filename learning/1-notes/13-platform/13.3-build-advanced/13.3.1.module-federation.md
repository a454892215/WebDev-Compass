# 13.3.1 Module Federation故障定位：远程入口、共享版本与发布缓存

前置阶段3构建/类型、7部署、8模块边界、12包消费；本组先确认目标和工具角色，再实现插件/缓存/格式。目标是按真实产物与失败路径解释取舍，不以工具品牌推导能力。

## 机制与最小示例

Module Federation把远程模块加载、container初始化和共享依赖协商交给构建插件/runtime，不等于普通dynamic import，也不要求所有代码在同一仓库。代码在host执行上下文中运行，微前端名称不会自动建立安全沙箱、认证或数据隔离。先明确为什么需要独立部署，再决定是否值得承担运行期版本/网络复杂度。

本点是官方观察与配置审查，不运行MF SDK。阅读build-lab/federation-review.json：host要求catalog/Panel，而旧remote只暴露./Legacy，先比较请求alias、exposes与发布manifest，不凭404猜组件Bug。按官方runtime表区分入口获取、manifest形状、expose不存在、container init/shared不兼容；错误码是官方说明，不是本lab产生的日志。

## 场景、边界与误区

shared singleton/requiredVersion/shareScope只是协商规则，不能保证所有产物永远使用相同Vue实例；import:false还需真实provider。hash chunk应保留旧版本，manifest更新/缓存需协调；fallback必须是匹配模块契约的本地安全行为，不以关闭CSP/CORS或执行任意远程URL恢复服务。SSR渲染上下文与远程模块代码缓存分开，不把用户状态放进进程级runtime。

## 移动开发对照

可类比可更新模块，但浏览器远程代码有自己的加载/CORS/CSP、共享依赖与缓存机制；不是Android动态特性模块或Flutter package的直接替代。
