# 5.1.2 请求生命周期：取消、超时、迟到结果与状态恢复

## 前置与目标

阶段2异步/HTTP、阶段3TS/模块、阶段4Vue/Nuxt。能使旧请求失效、区分空与失败，并证明离开/清空后不会被迟到结果覆盖。

## 机制与场景

每次操作创建自己的AbortController，signal传到真实fetch及读取流程；已abort的signal不能复活再用。取消是客户端终止等待/消费的机制，不代表服务器事务回滚。AbortSignal.timeout可提供受支持环境的超时信号，目标浏览器不支持时用显式定时器并在finally清理。不要用Promise.race只让UI先退出却留下后台请求与副作用。

只靠abort不总够：库、缓存或自定义异步源可能不响应取消。保留请求代次或有效标志，在写状态前核对“还是最新且未离开”。清空输入也必须递增代次并清理旧请求，否则旧结果会把空页面重新填满。finally里也要判断归属，旧请求不能把新请求的loading关掉。

状态至少区分idle/loading、success、empty与error；取消原因可根据用户动作决定是否静默，但超时不应悄悄称成功。Vue同步setup创建的侦听可随卸载清理，Nuxt数据composable有自身key和刷新规则；不要再叠一套互相争用的watch自动请求。

## 最小例子

```javascript
const own = ++generation
controller?.abort()
controller = new AbortController()
const data = await loader(query, controller.signal)
if (own === generation) notify(data)
```

## 运行与观察

第二组用真实延迟HTTP验证AbortError和TimeoutError；第三组deferred故意忽略abort，快新结果先返回，慢旧结果后返回仍不覆盖；清空与dispose后的迟到结果也不回写。

## 移动经验对照与边界

可复用移动端的分层、状态所有者和失败恢复方法；浏览器凭据/CORS/对象URL及Nuxt服务端上下文必须按Web机制验证，不等同于移动网络库或安全存储。
