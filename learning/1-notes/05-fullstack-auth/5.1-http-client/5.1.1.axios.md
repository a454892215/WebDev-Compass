# 5.1.1 HTTP客户端选型：Fetch、Nuxt读取与统一错误边界

## 前置与目标

阶段2异步/HTTP、阶段3TS/模块、阶段4Vue/Nuxt。能区分传输、HTTP、解析和数据结构失败，再决定是否需要请求封装。

## 机制与场景

原生fetch在收到HTTP404/500时通常仍兑现Response；网络失败、取消、某些策略阻止才使Promise拒绝。先检查response.ok/status，再读body；json()只是解析JSON，不验证业务字段。204没有可解析JSON，不能机械对所有成功响应调用json()。响应体通常只能消费一次，需要多次读取时应在消费前clone，不能让日志拦截器先把body读空。

Nuxt读取优先考虑useFetch/useAsyncData的SSR payload生命周期；事件提交用$fetch并单独处理提交状态。$fetch对非成功状态的异常行为与原生fetch不同，不能把两个实现的错误对象直接当同一契约。封装应保留status、失败类别和取消语义，UI再转换为可理解反馈，不把每种异常都转成空数组。

Axios在已有项目、拦截器体系或特定适配器需求下可以选择；本章不强装第二套客户端。无论用何库，超时、运行期解码、凭据目标、重试与认证恢复仍是应用协议；不要在一个全局拦截器里无限重试、跳登录或打印敏感请求。

```javascript
const raw = await readJSON('/api/v1/items') // 完整函数见client.mjs
const page = decodePage(raw)              // JSON解析之后才校验字段
// readJSON将http/parse/content-type区分，decodePage报告schema。
```

片段用于说明机制，完整上下文与运行条件见操作卡；不要把注释中的占位URL/变量当可直接粘贴的完整工程。

## 运行与观察

运行pnpm check的第一组：正常页可解码，缺失路由为http404，坏JSON为parse，错误字段为schema，HTML冒充JSON为content-type，204返回null。

## 移动经验对照与边界

可复用移动端的分层、状态所有者和失败恢复方法；浏览器凭据/CORS/对象URL及Nuxt服务端上下文必须按Web机制验证，不等同于移动网络库或安全存储。
