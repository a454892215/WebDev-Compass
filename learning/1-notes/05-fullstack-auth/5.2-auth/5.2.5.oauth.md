# 5.2.5 OAuth 2.0与OIDC：授权码、PKCE与第三方登录

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

知道第三方授权、身份认证和本应用会话分别由谁完成，不在浏览器里放client secret或把access token当登录证明。

## 原理与选择

OAuth是授权框架，OIDC在其上定义身份层和ID Token等验证规则。第三方平台可能提供OAuth后再调用身份API，不能把所有“用某平台登录”都直接称OIDC。应优先成熟提供方SDK/服务器集成；浏览器是public client，无法保护静态嵌入的client secret。

当前安全基线采用Authorization Code并按客户端和发行者要求使用PKCE（S256）；授权事务绑定验证器/挑战，回调的redirect URI严格登记。不要把Implicit或Resource Owner Password当新应用默认。OAuth BCP允许在满足条件时由PKCE或OIDC nonce提供CSRF保护，但不能据此随便删掉库需要的state；必须核对提供方支持与事务/用户代理绑定。

回调先核验对应事务、允许redirect目标、发行者与错误，再按协议换码；OIDC还验证ID Token签名/iss/aud/time及适用nonce。state处理事务/CSRF，nonce关联ID Token、防重放，PKCE约束码兑换，三者用途不能混为一项万能参数。不要将任意returnTo当重定向目标；错误页不记录code/token/secret。

## 最小机制片段

```typescript
// 仅协议顺序，不是手写OAuth实现：
// 本应用创建一次性事务 -> 授权端点(code_challenge S256)
// -> 注册的回调(code/state或error) -> 校验事务与发行者
// -> 令牌端点(code_verifier) -> OIDC验证或提供方身份API
// -> 本应用自己的Session，第三方token不是直接暴露给任意前端的通行证。

```
