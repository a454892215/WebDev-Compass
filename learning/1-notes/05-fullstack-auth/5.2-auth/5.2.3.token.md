# 5.2.3 登录恢复、刷新协调、失效与退出

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

应用刷新、多个请求同时401、用户退出或切换身份时，避免旧状态复活和无限刷新循环。

## 原理与选择

Cookie/Session应用可查询会话恢复（本项目GET /api/session匿名或过期返回200与user:null，受保护API才对未登录返回401），不必额外把token写localStorage。页面有匿名/恢复中/成功/失效/失败状态，网络失败不能一概当密码错误，也不应把恢复期间的未定状态立刻解释为永久匿名。Nuxt首次SSR可携带当前请求Cookie获取同一用户，客户端接管复用结果，细节见5.2.9。

Bearer协议只有明确支持refresh时才刷新；同一客户端会话的并发401可共享一次refresh Promise，最多有限重试，刷新端点自己的401不能递归。非幂等写操作不能不加判断自动重放。刷新token轮换、复用检测是发行者服务器能力，本地single-flight不能替代它。

退出/身份切换应使本应用的旧请求代次失效、清理用户专属状态及请求缓存；迟到的/me或refresh不能重新写回旧身份。多标签页需要按实际Cookie/存储与消息约定协调，但跨标签通知不能替代服务器撤销。每应用/会话创建刷新协调器，SSR进程级单例会把不同用户的请求混在一起。

## 最小机制片段

```typescript
// 在jwt-lab目录的ES模块中运行；实例属于本客户端会话，不是进程单例。
import { createRefreshCoordinator } from './contracts.mjs'
const coordinator = createRefreshCoordinator()
let calls = 0
const loader = async () => { calls += 1; return 'public-fixture-result' }
await Promise.all([coordinator.refresh(loader), coordinator.refresh(loader)])
console.log(calls) // 1；退出后的迟到拒绝另见完整verify.mjs受控Promise测试。
```

片段按注释提供HTTP/页面或实验上下文；完整可运行文件与导入在[操作卡](../../../2-examples/05-fullstack-auth/5.2-auth/5.2.3.token-demo.md)，不能把协议示意当生产认证实现。

## 观察、场景与边界

jwt-lab真实验证3并发调用只执行1次loader、logout后迟到结果拒绝、两个实例不共享pending。Cookie登录恢复/过期/退出以综合项目HTTP/浏览器结果另验。

## 移动端对照

可迁移会话生命周期、权限最小化和失败恢复分析；浏览器的Cookie自动携带、脚本读取和SSR作用域须单独理解，不按Keychain/Keystore关键词类推。
