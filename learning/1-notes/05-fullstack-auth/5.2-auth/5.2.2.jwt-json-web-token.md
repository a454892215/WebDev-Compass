# 5.2.2 JWT：签名、claims与access/refresh职责

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

识别一个token是什么、谁签发、给谁使用、何时有效；避免把能解码的JSON当作可信授权。

## 原理与选择

JWT是一种claims表示格式，可以是签名/完整性保护或加密结构；本实验是签名JWS，payload可读，签名不提供内容保密。JWT不等于OAuth，也不保证一定是access token。API按已配置的发行者、用途、受众、算法和有效期验证，不能让未信任header任意决定验证策略。

access token用于资源访问，refresh token用于按发行者协议换新token，不能把refresh token当访问凭证发给每个业务API。短access有效期、refresh轮换/复用检测或发送方约束各需服务端支持；删除客户端token不自动撤销仍有效的已签发access token。选择opaque session也完全合理，不必为了“现代”改用JWT。

本实验固定RS256和at+jwt用途，用成熟jose验证签名、iss、aud、exp/nbf/iat和必要字段。RS256是实验取舍，不是所有系统唯一推荐算法。生产密钥轮换/JWKS信任与缓存另按发行者契约；不要从任意token里的URL下载信任密钥。客户端解码可用于非权威展示，角色与权限最终由服务器认定。

## 最小机制片段

```typescript
// jwt-lab/verify.mjs中的调用形态；token/publicKey在同一完整文件中生成。
const result = await jwtVerify(token, publicKey, {
  algorithms: ['RS256'], issuer, audience, typ: 'at+jwt',
  requiredClaims: ['exp', 'sub', 'iat'], currentDate,
})
// decodeJwt(token)只解码，不做上述验证。
```

片段按注释提供HTTP/页面或实验上下文；完整可运行文件与导入在[操作卡](../../../2-examples/05-fullstack-auth/5.2-auth/5.2.2.jwt-json-web-token-demo.md)，不能把协议示意当生产认证实现。

## 观察、场景与边界

运行jwt-lab：16组真实检查中覆盖签名成功、篡改role、错key、过期、未来nbf、错iss/aud、缺exp、错typ、禁止算法和maxTokenAge。密钥仅在进程中生成，不输出token或私钥。

## 移动端对照
