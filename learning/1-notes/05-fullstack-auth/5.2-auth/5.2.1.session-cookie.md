# 5.2.1 Session与Cookie：轮换、过期和CSRF边界

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

让浏览器带来的会话凭证与服务器认可的身份相对应，区分浏览器是否保存Cookie、是否发送Cookie，以及服务器是否接受这次会话。

## 原理与选择

Cookie是传输/存储机制，Session是服务器管理的会话。opaque session ID只作随机索引，身份与权限由服务器查到；不要把客户端给的userId/role当会话身份。成功登录或权限升级需要轮换会话ID并使旧ID失效，防会话固定。服务器还要有到期与撤销判断，浏览器Cookie尚存在不代表会话仍有效。

HttpOnly降低脚本直接读取Cookie的风险，不能阻止页面中的恶意脚本借用户身份发请求；Secure要求HTTPS传输，SameSite控制跨站携带边界，不等于同源策略或完整CSRF防护。生产可用符合条件的__Host-前缀限制Domain/Path；本地HTTP教学不能把不带Secure的Cookie宣称为生产配置。

对写操作核对可信目标Origin并验证与会话绑定的同步CSRF token；允许来源不是字符串后缀匹配。token不得放URL/日志。SameSite是纵深防御而非替代。GET不做状态修改；登录入口也有登录CSRF风险，不能只保护登录后的保存。退出应服务器撤销会话并按匹配路径/属性删除Cookie，按应用范围决定是否清理其他浏览器数据。

## 最小机制片段

```typescript
// HTTP配置示意，不是可复制的完整登录实现。
// HTTPS生产：Set-Cookie: __Host-session=<opaque>; Path=/; Secure; HttpOnly; SameSite=Lax
// 本地HTTP教学使用单独cookie名并明确Secure:false，不能当生产范例。
// 服务端：随机ID -> Session{ userId, csrf, expiresAt }；每次请求查验。
```

片段按注释提供HTTP/页面或实验上下文；完整可运行文件与导入在[操作卡](../../../2-examples/05-fullstack-auth/5.2-auth/5.2.1.session-cookie-demo.md)，不能把协议示意当生产认证实现。

## 观察、场景与边界

综合项目观察Set-Cookie、会话恢复、旧ID轮换/过期/撤销；直接HTTP写请求分别移除Origin或CSRF header，应被拒绝。只有浏览器实际断言通过才能称HttpOnly不可被document.cookie读取。

## 移动端对照

可迁移会话生命周期、权限最小化和失败恢复分析；浏览器的Cookie自动携带、脚本读取和SSR作用域须单独理解，不按Keychain/Keystore关键词类推。
