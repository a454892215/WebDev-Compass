# 5.2.4 Authorization Bearer：传输、解析与凭证边界

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

按服务端协议发送凭证，并区分缺凭证、无效凭证与已认证但不允许访问。

## 原理与选择

Bearer表示持有该凭证即可按协议使用，不要求token一定是JWT；应通过HTTPS Authorization header发送，避免放URL、Referer、日志或错误上报。不同协议可能使用opaque token或签名token，服务端解析后仍要查验。认证失败通常401并按协议给WWW-Authenticate，已认证但无权限通常403；具体隐藏资源存在性可选择404。

header格式与token验证是两步。不要把Basic或逗号拼接的多凭证当Bearer；HTTP scheme大小写不敏感。浏览器跨源Authorization通常触发CORS预检，允许发送header不等于凭证有效。跳转或转发到别的origin时不能无条件携带凭证。

CSRF依赖凭证发送方式与请求上下文分析，不是“用JWT就不会CSRF”。若token放HttpOnly Cookie由浏览器自动发送，仍检查Cookie写操作；若由脚本读出的Bearer header，XSS就可能盗用/调用。服务端到服务端的credential转发要明确目标allowlist和最小headers，不能把来访请求全部headers原样发给第三方。

## 最小机制片段

```typescript
// jwt-lab目录的ES模块；这里只证明解析，不声称认证成功。
import { bearerFromHeader } from './contracts.mjs'
const token = bearerFromHeader('Bearer opaque-teaching-value')
console.log(token === 'opaque-teaching-value') // true
// 真正验签见verify.mjs的verify(token)：服务器固定publicKey与validation policy。
```

片段按注释提供HTTP/页面或实验上下文；完整可运行文件与导入在[操作卡](../../../2-examples/05-fullstack-auth/5.2-auth/5.2.4.authorization-bearer-token-demo.md)，不能把协议示意当生产认证实现。

## 观察、场景与边界

运行jwt-lab的bearer-header组：合法方案大小写、opaque值可解析；缺失、多凭证、错误scheme和控制字符被拒绝。JWT验签另由真实jose实验执行，没有把解析当认证。

## 移动端对照

可迁移会话生命周期、权限最小化和失败恢复分析；浏览器的Cookie自动携带、脚本读取和SSR作用域须单独理解，不按Keychain/Keystore关键词类推。
