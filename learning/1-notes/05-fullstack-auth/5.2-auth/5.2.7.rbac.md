# 5.2.7 权限反馈、RBAC与对象所有权

前置：阶段0同源/HTTP、阶段2异步、阶段3TS与阶段4Nuxt。推荐先5.2.1/5.2.3再5.2.7/5.2.9；JWT/Bearer和OAuth/SSO按后台契约选读。

## 解决什么问题

让UI准确解释用户能做什么，同时保证直接调用API或修改资源ID不能绕过访问控制。

## 原理与选择

认证回答当前身份，授权判断能否对这个资源执行这个操作。RBAC把权限映射到角色，现实还常有对象所有者/租户/状态等条件；只检查reader角色不足以允许读取别人的私有文档。信任的身份来自服务器会话或已验证token，不来自body.userId、query.role或隐藏表单字段。

路由、菜单和按钮控制体验与反馈；服务器在每次受保护请求中执行策略。匿名通常401，已登录但不允许403；为避免暴露资源存在性可用一致的404，须在契约中写清。默认拒绝未知角色/操作；分页、导出、上传和实时通道也应按相同策略过滤。

权限改变或退出后前端缓存可能仍有旧数据，应明确清理/重新获取。UI不显示按钮不等于服务器安全，显示按钮也不能保证请求一定成功。角色策略测试至少包括匿名、owner、非owner同角色、admin和不存在资源，必要时检查写入后状态真的未变化。

## 最小机制片段

```typescript
// 与jwt-lab/contracts.mjs相同的纯策略；user必须先由服务器认证。
function mayReadDocument(user: { id: string; role: string }, document: { ownerId: string }) {
  return user.role === 'admin' ||
    (user.role === 'reader' && user.id === document.ownerId)
}
console.log(mayReadDocument({ id: 'bob', role: 'reader' }, { ownerId: 'alice' })) // false
// UI可以提示可用能力，API仍独立执行服务器检查。
```

片段按注释提供HTTP/页面或实验上下文；完整可运行文件与导入在[操作卡](../../../2-examples/05-fullstack-auth/5.2-auth/5.2.7.rbac-demo.md)，不能把协议示意当生产认证实现。

## 观察、场景与边界

jwt-lab验证owner reader允许、另一reader拒绝、admin允许。综合项目再用两份真实Cookie上下文直接访问资源、管理接口；纯策略函数不替代HTTP集成证据。

## 移动端对照

可迁移会话生命周期、权限最小化和失败恢复分析；浏览器的Cookie自动携带、脚本读取和SSR作用域须单独理解，不按Keychain/Keystore关键词类推。
