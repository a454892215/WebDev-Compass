# 5.4.4 HTTP状态、业务错误与响应契约

## 前置与目标

阶段2异步/HTTP、阶段3TS/模块、阶段4Vue/Nuxt。能按协议处理状态和业务错误，不强制所有API都返回code/data/message包壳。

## 机制与场景

HTTP状态表达传输层面的请求处理结果；200可承载业务结果，201表示创建、204无响应体、400输入无效、401缺少/无效认证、403权限拒绝、404资源不存在、409状态冲突、413/415上传问题、429限流、5xx服务端失败。具体协议可用404隐藏资源存在性，不能仅凭403/404推断业务身份。

{code,data,message}是可选约定，不是Web标准。选择裸数组、资源对象或问题详情等都可以，但成功与失败必须一致可解析；HTTP失败不应为了统一包壳一律改200。用户消息与诊断分开，不能把后端堆栈、数据库信息、Token或原始用户内容直接展示/上报。

客户端应先识别HTTP，再按Content-Type/空body处理，再按业务契约解码。重试、重新认证和输入纠正是不同恢复动作：400不应自动重试，401恢复有上限，403不应靠刷新Token绕过授权，429遵守等待预算。GraphQL还有data/errors局部结果，见选修点，不能机械套统一包壳。

## 最小例子

```javascript
if (response.status === 204) return null
if (!response.ok) throw new ApiError('http', `HTTP ${response.status}`, response.status)
// 后续JSON解析/DTO解码分别报告parse/schema，不把一切改成code:0。
```

片段用于说明机制，完整上下文与运行条件见操作卡；不要把注释中的占位URL/变量当可直接粘贴的完整工程。

## 运行与观察

实验实际看到404、400、403、409、413、415、429/503、201和204不同分支；相同幂等key不同body409不能当认证失败。

## 移动经验对照与边界

可复用移动端的分层、状态所有者和失败恢复方法；浏览器凭据/CORS/对象URL及Nuxt服务端上下文必须按Web机制验证，不等同于移动网络库或安全存储。
