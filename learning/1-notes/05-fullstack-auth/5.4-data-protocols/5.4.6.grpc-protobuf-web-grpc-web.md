# 5.4.6 gRPC-Web与Protobuf：生成代码、代理与RPC状态（选修）

## 前置与目标

阶段2异步/HTTP、阶段3TS/模块、阶段4Vue/Nuxt。能解释浏览器gRPC-Web链路与原生gRPC差异，不把.proto当可运行接口。

## 机制与场景

Protobuf用schema和稳定字段编号描述消息，工具生成客户端/服务端代码；.proto不实现业务。gRPC-Web为浏览器限制采用不同于原生gRPC的协议细节，通常经代理转换；浏览器能发fetch并不等于可直接调用所有原生HTTP/2 gRPC服务。

观察请求媒体类型、消息帧与尾部状态：HTTP200不自动等于RPC成功，还要看gRPC status及metadata；跨域响应头可读性和代理配置仍需核对。text编码与binary模式、unary/服务端流等支持依赖客户端/代理版本，不能把原生gRPC双向流能力全部照搬到Web。

字段编号是兼容性身份，不应删除后重用为新含义。生成代码和静态类型不替代目标服务验证、认证、deadline、取消与错误处理。本点提供.proto和官方链路观察清单，未安装protoc/Envoy/真实后端；迁移已有Android gRPC经验时尤其要核对Web支持差异。

## 最小例子

```protobuf
syntax = "proto3";
service ResourceService {
  rpc GetResource (GetResourceRequest) returns (ResourceReply);
}
message GetResourceRequest { string id = 1; }
message ResourceReply { string id = 1; string title = 2; }
```

片段用于说明机制，完整上下文与运行条件见操作卡；不要把注释中的占位URL/变量当可直接粘贴的完整工程。

## 运行与观察

按protocol-observations/README对照resources.proto，追踪生成客户端→浏览器→代理→后端，并辨认HTTP状态与RPC状态两层。没有伪造RPC成功日志。

## 移动经验对照与边界

可复用移动端的分层、状态所有者和失败恢复方法；浏览器凭据/CORS/对象URL及Nuxt服务端上下文必须按Web机制验证，不等同于移动网络库或安全存储。
