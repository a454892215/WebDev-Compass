# 5.3.2 CORS：简单请求、预检、凭据与精确Origin

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

跨源API要允许哪一个浏览器页面读取数据，应由服务器返回明确授权；不要靠前端加响应头或任意反射Origin。

## 机制与选择

满足CORS安全列出方法/头等条件的请求通常无需预检；带application/json、自定义头等请求可能先OPTIONS。预检通过才发送相应实际请求，但预检不是业务提交，也不是登录认证。不要因为OPTIONS没带会话Cookie就先强制401。

Access-Control-Allow-Origin应匹配允许的完整Origin；带凭据读取还需Access-Control-Allow-Credentials:true。credentials:include只是请求侧意图，不能绕过SameSite、第三方Cookie策略或服务端授权。凭据模式不能配通配*授权读取；允许特定Origin也不意味着该来源可信用户已登录。

动态按允许列表返回Origin时应有Vary:Origin以避免缓存混用；预检还需核对Allow-Methods、Allow-Headers。自定义响应头如ETag需Expose-Headers才能让跨源JS读取；不要盲目允许所有方法/头。

## 最小例子

```javascript
// server.mjs中只允许明确来源；Origin可被非浏览器伪造，不是身份。
if (request.headers.origin === 'http://127.0.0.1:4404') {
 response.setHeader('Access-Control-Allow-Origin', request.headers.origin)
 response.setHeader('Access-Control-Allow-Credentials', 'true')
 response.setHeader('Vary', 'Origin')
}
// 预检另外声明POST及Content-Type/X-Course，不执行业务写入。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

真实Chrome发送带X-Course与JSON的POST，options计数增加且成功；blocked-preflight实际POST计数始终0。seed设置本地HttpOnly Cookie后，精确Origin凭据读取成功；wildcard即使ACAC:true仍被浏览器拒绝读取。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
