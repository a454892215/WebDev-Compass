# 5.3.3 开发代理：浏览器同源，服务器再转发

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

开发服务器可把浏览器请求转发给另一个API，减少本地跨源配置摩擦；要知道代理改变的是哪一跳，而不是把CORS“破解”了。

## 机制与选择

浏览器请求同源的/proxy，Node/Vite开发服务器再请求API来源。服务器到服务器这一步不受浏览器CORS读取限制；因此浏览器看到的是同源响应。Vite server.proxy只影响开发服务器，不会自动进入生产静态JS，也不是托管后的反向代理配置。

rewrite必须对应后端路径，changeOrigin主要调整转发Host等行为，不能代替Cookie域/路径、CSRF Origin和真实身份设计。Cookie与Authorization不要不加判断地转发到任意用户指定URL，否则会把开发便利变成凭据泄露或SSRF。

Nuxt的server/api本地BFF与Vite开发代理有不同运行生命周期。生产是否需要BFF或反向代理取决于部署和接口契约，不能把开发通过当作部署已完成。

## 最小例子

```javascript
// Vite配置的独立对照片段；本lab实际使用Node固定目标代理。
export default {
 server: { proxy: { '/api': { target: 'http://127.0.0.1:4405', changeOrigin: true } } }
}
// 本lab GET4404/proxy只转发固定4405/plain，不接收任意target参数。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

直接跨源读4405/plain失败，读4404/proxy却得到同一公开JSON。真实转发由server.mjs执行，Vite片段仅对照配置，不冒称本lab启动了Vite。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
