# 5.3.4 JSONP：跨源脚本执行的历史方案

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

理解旧项目为什么能用script“跨域”，以及这种能力为什么不等同安全的JSON读取。现代API优先Fetch+CORS。

## 机制与选择

JSONP把数据包装成函数调用，通过script加载执行。script嵌入跨源资源与Fetch读取JSON适用不同规则；加载成功意味着远端代码获得页面脚本执行能力，不是只获得一块无害数据。

callback参数若未经约束也可能成为脚本注入入口。本地实验只允许固定courseReceiver名称、固定公开payload，不拼接不可信代码。它主要适用历史GET式读取，不能提供现代Fetch的错误/status/取消语义，也不能承担登录或敏感变更。

CSP的script-src、第三方脚本信任和供应链风险同样适用。不要让业务后端为了消除跨域报错新增JSONP，更不要把带Token的URL塞进script请求；URL可能进入历史/日志/Referer。

## 最小例子

```javascript
// 只在本地fixture中观察，callback固定且payload由服务器JSON序列化。
window.courseReceiver = value => console.log(value)
const script = document.createElement('script')
script.src = 'http://127.0.0.1:4405/jsonp?callback=courseReceiver'
document.head.append(script)
// 返回JavaScript courseReceiver({...})，不是application/json。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

真实Chrome在4404载入4405的本地脚本，得到courseReceiver回调。对照plain的Fetch仍失败，从而区别脚本执行与JSON暴露权限；没有加载任何外网脚本。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
