# 5.3.1 同源策略：限制读取，不等于阻止请求

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

浏览器页面要读取另一个来源的响应时，需要理解谁在执行限制。服务器已经收到请求、浏览器拿到响应、脚本可读取响应，是三个不同事实。

## 机制与选择

源由协议、主机、端口共同决定。http://127.0.0.1:4404与:4405不同源；“站点”用于SameSite等规则，不能用同源代替同站，两端口可以不同源但同站。DOM读取、Fetch响应暴露和脚本嵌入有不同约束，不应统称“所有跨域都禁止”。

同源策略限制不被授权的跨源读取。某些简单跨源请求可以先发送；服务端副作用已经发生，响应却不能被脚本读取。CORS不是CSRF防护，也不是服务器授权。原生客户端或服务器端程序不受浏览器CORS读取规则约束。

fetch的mode:no-cors不会解锁JSON：得到的opaque响应不能读取正常body/status。开发者工具显示网络记录不等于页面脚本可读；不要为消除红字关闭浏览器安全开关。

## 最小例子

```javascript
// 在4404页面执行；4405/plain故意不提供CORS授权。
try { await fetch('http://127.0.0.1:4405/plain') }
catch { console.log('浏览器未向脚本暴露响应') }
// 对/write发送text/plain POST后同样读失败，但服务端writes计数已增加。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

点击跨域实验：simple可读，plain读失败；writeBlocked为true，而stats.writes增加。只有这一组本地公开fixture，不涉及真实用户数据。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
