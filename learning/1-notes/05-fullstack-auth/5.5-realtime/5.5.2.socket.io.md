# 5.5.2 Socket.IO与原生WebSocket封装的选择

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

确认服务器协议后再选客户端。名字里有socket不代表可互换，封装也不会自动解决业务可靠性。

## 机制与选择

Socket.IO是包含Engine.IO/Socket.IO编码、事件与确认等机制的应用库，可使用WebSocket或长轮询传输；它不是原生WebSocket协议的同义词。原生WebSocket客户端不能直接当Socket.IO客户端，反过来也不行。

Socket.IO提供库级连接管理、心跳与重连选项；ack表示某个处理器回调，不自动证明事务持久化或恰好一次。默认投递保证、离线缓存、重连恢复和多节点适配需分别查目标版本。业务还需校验消息、认证、房间权限和背压。

浏览器WebSocket-only传输不能依赖自定义头方案；Socket.IO的auth载荷、Cookie、allowRequest、CORS和代理路径各有作用。长轮询与WebSocket跨源约束不完全一样，不能只配cors就忽略握手Origin/会话授权。

## 最小例子

```javascript
// 浏览器先加载本地Socket.IO客户端；不是new WebSocket(url)。
const socket = io('http://127.0.0.1:4405', {
 transports: ['websocket'], reconnectionAttempts: 1,
})
socket.on('connect', () => socket.emit('course-ping', 'ping', reply => console.log(reply)))
// 退出时socket.disconnect()；服务端对应socket.on('course-ping', (..., ack)=>...)。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

实际Socket.IO4.8.4客户端/服务端完成course-ping→received:ping确认；原生WS实验走独立/ws路径。没有将两套协议混用，也未验证跨进程恢复或持久化投递。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
