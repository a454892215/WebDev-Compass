# 5.5.3 SSE：事件流、Last-Event-ID与停止重连

前置：阶段2浏览器/HTTP、阶段3模块与测试；认证边界参见5.2。先理解协议，再运行本地实验，不需要生产凭据。

## 解决什么问题

服务端只需持续推送文本更新时，SSE可复用HTTP与EventSource，但重连、历史和认证仍有边界。

## 机制与选择

响应Content-Type为text/event-stream，事件由空行分隔，data可多行，id影响后续自动重连的Last-Event-ID；retry是重连延时提示，注释可作保活。服务器/代理缓存、缓冲和超时可能让事件迟到，需要按部署检查。

EventSource是服务端到客户端单向事件通道，客户端提交仍走Fetch等HTTP请求。构造器有withCredentials等选项，不能任意设置Authorization请求头；跨源Cookie仍服从CORS/SameSite策略，Bearer需求可考虑受控fetch流等方案，不把长期Token塞URL。

浏览器自动重连不代表自动补齐历史。服务端必须理解cursor、重放窗口和缺口恢复；事件可能重复，客户端需按业务id去重，不能只依赖TCP顺序宣称恰好一次。close()才停止本EventSource；不应再并排维护另一套无界重试定时器。

## 最小例子

```javascript
// 在本lab4404页面：服务端首条id1后断流，重连时观察Last-Event-ID。
const source = new EventSource('http://127.0.0.1:4405/sse', { withCredentials: true })
source.onmessage = event => {
 console.log(event.lastEventId, JSON.parse(event.data))
 if (event.lastEventId === '2') source.close()
}
// 服务端使用id/data字段与空行分隔；本地重放fixture不代表持久事件日志。
```

这是有明确上下文的机制片段，完整导入/服务器/页面代码见操作卡，不作为孤立可运行文件。

## 实际观察与边界

真实EventSource收到服务端重复发送的id1但只应用一次，服务端关闭后自动重新请求并携带Last-Event-ID:1，收到id2后显式close，活动连接归零。openFeed用seen集合去重并限制错误预算；本例固定两条fixture不是通用持久重放系统。

## 移动端对照

与移动网络层一样要分析超时、身份和失败恢复；浏览器额外受源/站点、CORS及受限请求API影响，不把Cookie或页面连接当系统安全存储/推送。
