# 8.3.5 同构代码：请求作用域、序列化与公开payload

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

可在server/browser导入不等于代码在两个环境有相同能力。DOM、Node文件系统、数据库连接、进程环境和请求凭据有各自位置；动态import也可能在错误环境初始化。服务端每请求身份/可变状态不能放进进程级单例，公开不可变常量则可安全共享。

useState/useAsyncData数据会进入客户端payload，应只保存所需可序列化公开DTO，不保存数据库客户端、函数、真实凭据或所有原始上游字段。key要描述数据身份和查询维度，但key不能代替服务端授权。退出/切身份需清理可见数据与对应缓存，代理/CDN/Nitro缓存也必须检查。

## 最小机制片段

```typescript
// Nuxt setup中调用，而非模块顶层创建ref
const useSelection = () => useState<string[]>("selected-course-ids", () => []);
// state会序列化；禁止放token、函数或连接。
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

读取主项目请求内workspace聚合、shared契约、服务端adapter与按scope区分的data key；并发检查Alice/Bob合成fixture和降级结果。scope是公开教学选择，不是认证；主项目未使用真实Cookie身份，不虚构凭据测试。

故障：SSR handler把全量上游对象返回且缓存key固定workspace。先查HTML/payload和最终响应，再裁剪DTO、区分key和服务端缓存策略；单改前端类型不足以修复。

## 移动开发对照

原生App进程单例通常服务单个安装用户；Node SSR一个进程可同时服务很多请求，作用域不能照搬。
