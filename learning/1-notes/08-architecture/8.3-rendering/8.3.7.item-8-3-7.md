# 8.3.7 渲染决策树：从身份、时效和托管约束给出可推翻决定

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

决策树是讨论约束的工具，不是自动证明架构正确。先问内容是否公开且可在构建时获取、最大可接受陈旧时间、是否需每请求身份/数据，再问路由能否枚举、托管运行时与预算；最后比较交互量、无JS/搜索要求和维护成本。

公共文档可SSG，个性化请求可SSR或静态壳+受保护API，封闭交互工具可CSR；混合模式需逐路由记录缓存、身份与更新机制。为候选写被否决原因、未知项、最小验证和重新评估触发，避免只给一个永远不变的框架答案。

## 最小机制片段

```typescript
const decision = { chosen:"Node SSR", alternative:"SSG + API", revisitWhen:"工作台不再需要请求时聚合" };
console.log(decision.alternative);
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

把主工作台的公开合成scope/请求聚合/可选降级与部署限制作为输入写ADR；对照阶段7三profile历史实践。主项目展示Node SSR，不称已经验证每个分支或生产性能。

故障：决定书以“SSR更先进”作为唯一理由。用内容时效/身份/部署能力重写，并注明未测预算；不编造性能数字填表。

## 移动开发对照

架构决策类似移动端模块/状态取舍；Web必须额外区分HTML生成时点和托管能力。
