# 8.3.4 Hydration不匹配：先保证首次数据与DOM一致

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

服务器HTML和客户端首次渲染需采用同一输入与有效DOM结构。时间、随机数、隐式时区、setup中读window/localStorage、浏览器修正非法嵌套、第三方提前改DOM都可能造成不匹配。没有报warning不证明所有输入正确，不能把生产压掉日志当修复。

Nuxt用useAsyncData/useFetch把服务端结果放payload供初始接管，useState按应用提供可序列化初始状态；不能用Node模块级可变对象掩盖问题。浏览器专属功能在mounted初始化、清理时注销；稳定占位在两端首次一致，必要时采用ClientOnly并给合理fallback。

## 最小机制片段

```typescript
// Nuxt setup上下文；同一SSR payload保存初值
const stamp = useState("render-stamp", () => "lesson-v1");
console.log(stamp.value);
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

先看主工作台原始HTML、payload和实际browser console，再比较首次API请求。主项目不默认显示浏览器宽度；故障练习必须先在副本新增该功能，再造错。不声称未运行的所有故障注入已通过。

故障：server占位但客户端setup立即按innerWidth切另一DOM。定位首次render输入差异，恢复mounted更新或CSS；不用全局suppress警告代替一致性。

## 移动开发对照

类似移动端状态恢复需一致，但Web还要接管服务器已生成的DOM，而非只创建一棵Widget/View树。
