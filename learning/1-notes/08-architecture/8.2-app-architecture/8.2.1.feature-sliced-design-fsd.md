# 8.2.1 Feature-Sliced Design：协调业务模块与Nuxt目录

前置：阶段3模块/测试、阶段4 Vue/Nuxt、阶段5–7身份/缓存/部署。先判断真实约束，再理解机制、做实验与变体；微前端按需，不是普通页面的门槛。

## 解决什么问题与原理

FSD是一套带层/切片/片段语义与导入约束的组织方法，不等同所有按功能划分的目录。官方层含app/pages/widgets/features/entities/shared，processes已废弃；无需全建。不同业务slice通常不横向深导入，公开API控制协作边界。Nuxt的app/pages是路由约定，server是执行边界，不能为了复制FSD树把服务端代码挪进浏览器。中小项目可采用较少的feature+shared，明确叫项目适配而非完整FSD认证。

## 最小机制片段

```javascript
// 项目适配示意，不是要求新增全部FSD层。
const feature = { publicApi: ['listCourses'], internal: ['mapRawCourse'] };
console.log(feature.publicApi);
```

片段的上下文由注释说明；标为契约草案的内容不是工具完整配置。完整可执行机制见操作卡，不能把示意代码当联邦/插件平台实装。

## 观察、使用场景与边界

阅读主Nuxt的app/features/catalog与shared契约；对照FSD layers/import规则，列出哪些采用、哪些不采用。独立lab是机制实验，不称严格FSD实现。

先分清功能与实体，再按项目规模决定层；不把所有业务挪shared，也不为了层数套空壳。

## 移动开发对照

Android/Flutter的业务边界、接口与生命周期经验有助于判断职责；Web还涉及document、origin、URL、异步产物加载和每请求SSR。模块目录不是进程/权限沙箱，不能把移动端运行模型直接等同浏览器。
