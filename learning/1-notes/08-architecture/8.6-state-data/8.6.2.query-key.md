# 8.6.2 查询Key、缓存层级与作用域失效

前置：阶段2异步/存储、阶段4 Vue/Nuxt状态与数据、阶段5身份边界、阶段6缓存。先学8.6.1/2归属与key，再并发/过期/离线，最后按需选择协作模型。

## 解决的问题与机制

查询key描述“这份结果由哪些输入决定”：资源/版本、筛选、页码、语言、必要的用户或租户维度。key不是凭据，不放Token。不同用户需要同形查询不等于可共享结果；同key调用还必须保持数据处理选项一致。

浏览器/ServiceWorker、Nuxt客户端payload/应用缓存、Nitro、反向代理/CDN和后端缓存是不同层。客户端clearNuxtData不能清掉CDN；no-store也不代替Nitro cache:false或认证。退出/换租户时先撤销可见私有数据、取消/隔离旧请求，再按业务清理相关key/持久化；只在名字里加userId还不足以阻止迟到响应回写。

## 最小片段与上下文

```javascript
// state-lab/logic.mjs的可执行函数：
export function scopedKey(scope, query = '') {
  if (!['alice','bob'].includes(scope)) throw new TypeError('Unknown scope')
  return JSON.stringify(['workspace-v1', scope, query])
}
```

## 观察、场景与误区

pnpm test验证不同scope或query生成不同key，旧epoch响应被拒；主Nuxt查询scope实际由URL传入，公开fixture不是登录，不能把scope参数当访问控制。

缓存key维度要与真实数据依赖对应，不能无脑加入随机时间破坏复用；身份授权始终由服务端真实协议完成。

## 移动开发对照

本地草稿、版本和生命周期的目标可类比移动端；Nuxt还有服务器进程与每请求应用、HTML/payload、浏览器存储和多层HTTP缓存，不能把Flutter进程单例或原生安全存储直接照搬。scope是公开fixture不是认证，生产权限和同步协议须独立设计。
