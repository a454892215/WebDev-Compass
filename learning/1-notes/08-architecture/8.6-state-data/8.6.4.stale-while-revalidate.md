# 8.6.4 SWR体验：旧数据、后台刷新与失败可见性

前置：阶段2异步/存储、阶段4 Vue/Nuxt状态与数据、阶段5身份边界、阶段6缓存。先学8.6.1/2归属与key，再并发/过期/离线，最后按需选择协作模型。

## 解决的问题与机制

SWR在允许短暂过期的场景先用已有数据再刷新；收益是连续性，代价是用户可能看到旧值。需要定义新鲜期、可接受过期时长、错误展示、刷新时机与失效。余额/权限等敏感决策不应仅凭过期视图执行写操作。

HTTP Cache-Control的stale-while-revalidate、ServiceWorker策略、Nuxt数据刷新与应用自己保留旧结果不是同一实现。本lab staleResult是纯应用模型：成功替换数据并清错误，失败保留原数据且显示可能过期；不把catch返回空数组当成功，也不宣称配置了生产HTTP SWR。缺首次数据的错误要显示无数据，不能虚构旧结果。

## 最小片段与上下文

```javascript
import { staleResult } from './logic.mjs' // state-lab上下文
// 输入来自受控刷新结果，非真实HTTP缓存：
const previous = { data: '已缓存课程：Vue 3' }
const view = staleResult(previous, { ok: false })
// view仍有原数据，stale=true，并有明确错误。
```

## 观察、场景与误区

运行页面点击“模拟刷新失败/成功”，核对旧文字保留、错误出现、成功替换；Node与浏览器均验证。按钮使用可控结果，不把它声称真实外网刷新或生产缓存命中。

陈旧可用和成功空结果不同；新鲜度承诺应由业务与数据协议决定，不靠库默认选项自动推导。

## 移动开发对照

本地草稿、版本和生命周期的目标可类比移动端；Nuxt还有服务器进程与每请求应用、HTML/payload、浏览器存储和多层HTTP缓存，不能把Flutter进程单例或原生安全存储直接照搬。scope是公开fixture不是认证，生产权限和同步协议须独立设计。
