# 8.6.3 乐观更新：版本冲突、确认值与安全回滚

前置：阶段2异步/存储、阶段4 Vue/Nuxt状态与数据、阶段5身份边界、阶段6缓存。先学8.6.1/2归属与key，再并发/过期/离线，最后按需选择协作模型。

## 解决的问题与机制

乐观更新先展示预期结果，服务端确认后成为事实；失败必须区分网络未知、明确拒绝与版本冲突。多次操作/迟到响应使“保存旧快照，失败整页回滚”危险：旧失败可能覆盖新成功。给操作稳定标识、scope/epoch和服务端revision，确认值与临时显示值分开。

本lab仅演示一个数值的latest-intent模型：旧失败不能回滚最新成功，当前失败回到最新确认值；换scope后旧响应无效。真实HTTP /api/value按expectedRevision比较，过期409并返回当前公开fixture值，客户端需重读/提示冲突再决定重试。集合、库存、支付、多实体事务需要更具体协议，不能照搬此简单模型。

## 最小片段与上下文

```javascript
import { OptimisticValue } from './logic.mjs' // state-lab上下文
const state = new OptimisticValue('alice', 0)
const older = state.begin(1), newer = state.begin(2)
state.accept(newer, { value: 2, revision: 2 })
state.reject(older, 'late failure') // false，仍是2
```

## 观察、场景与误区

pnpm test运行旧失败/新成功、当前失败、跨scope与低revision反例。pnpm verify另真实POST /api/value：第一次expectedRevision1成功，第二次同版本409且服务端当前值不变；不是仅打印预编日志。

顺序冲突不靠多sleep或全局串行掩盖；乐观不是忽略权限/服务端验证，出错也不能把用户最新输入无声丢掉。

## 移动开发对照

本地草稿、版本和生命周期的目标可类比移动端；Nuxt还有服务器进程与每请求应用、HTML/payload、浏览器存储和多层HTTP缓存，不能把Flutter进程单例或原生安全存储直接照搬。scope是公开fixture不是认证，生产权限和同步协议须独立设计。
