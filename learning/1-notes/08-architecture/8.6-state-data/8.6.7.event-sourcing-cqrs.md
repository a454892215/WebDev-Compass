# 8.6.7 CQRS与事件溯源：读写分离、投影与运维代价

前置：阶段2异步/存储、阶段4 Vue/Nuxt状态与数据、阶段5身份边界、阶段6缓存。先学8.6.1/2归属与key，再并发/过期/离线，最后按需选择协作模型。

## 解决的问题与机制

CQRS将命令处理和查询模型分开，可共用一个数据存储，不强制消息队列或微服务。Event Sourcing以追加事件作为事实来源，通过重放建立状态或读投影；二者能组合也能分别采用，前端action日志/Redux devtools不是自动成为事件溯源。

需要同时设计事件版本、乐观并发、幂等消费、顺序、投影延迟、重建/快照与补偿。事件不可变不等于写入天然无冲突，两个命令读同版本仍须revision检查。隐私删除/审计保留也可能冲突，不能永远保存PII来换重放能力。普通课程CRUD多半不值得承担全部代价。

## 最小片段与上下文

```javascript
import { project } from './logic.mjs' // state-lab上下文
// state-lab纯投影，不是持久事件库：
const events = [{ type:'added', amount:2 }, { type:'added', amount:3 }]
const count = project(events) // 5，未知事件显式拒绝
// 没有消息代理、snapshot、可靠发布或生产event store。
```

## 观察、场景与误区

pnpm test验证有限事件数组投影与未知事件拒绝。再按Microsoft CQRS/Event Sourcing官方正文列命令/查询/事件/投影的职责；这是小模型与文档观察，不是持久事件系统或分布式一致性演练。

按实际业务风险选模型；写入ack与读模型可见可能不同，回滚代码不会撤销历史事件。

## 移动开发对照

本地草稿、版本和生命周期的目标可类比移动端；Nuxt还有服务器进程与每请求应用、HTML/payload、浏览器存储和多层HTTP缓存，不能把Flutter进程单例或原生安全存储直接照搬。scope是公开fixture不是认证，生产权限和同步协议须独立设计。
