# 8.1.1 RFC与ADR：记录可检验的取舍和决策后果

前置：阶段3类型/检查与阶段4–7 Vue/Nuxt、API、质量和部署。先明确约束，再读机制、观察和变体。

## 解决什么问题与机制

RFC用于提议、讨论和备选；ADR记录一次重要决定的背景、选择、理由与后果。两者不是所有团队必须同一格式，也不等于互联网RFC标准。本例有单体模块化、微前端和前后端分离三种候选，但只有当前约束驱动的一个选择；已经接受的ADR后续可被新记录取代，不能抹掉历史假装从未改变。

## 最小项目观察

读综合docs/RFC.md与ADR-001.md，逐项对照server/api组装、端口接口、app/features公共入口和真实测试。选择Nuxt单体不是因为其永远最好，而是本教学场景只有一个交付单元，没有团队自治或多运行时约束。

相关代码和完整运行条件见示例；这里的路径以综合项目根为基准。

## 使用场景、误区与移动端对照

ADR聚焦一个重要决定；后续改变写supersedes而非改旧决定，不把大量模板当设计质量。

移动经验可用于边界/契约与测试；Web仍需单独核对浏览器、SSR每请求与产物生命周期，不按目录或API相似推断能力。
