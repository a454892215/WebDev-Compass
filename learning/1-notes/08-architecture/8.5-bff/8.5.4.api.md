# 8.5.4 API版本与废弃：并行兼容、Deprecation与Sunset

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

兼容取决于消费者实际契约，不只看URL是否/v2。删除字段、变类型、改变null/排序/权限/错误语义通常破坏消费者；加字段也可能破坏严格解码器。先确认客户端版本、契约测试和迁移窗口，再决定URL/header/媒体类型版本策略；不为每个内部重构新建版本。

Deprecation按RFC9745使用Structured Field Date，如@unix-seconds，说明被弃用/生效日期；不是布尔true或HTTP-date。Sunset按其规范用HTTP-date说明预计停止服务日期，二者不自动执行下线，也不代替迁移说明。并行服务旧版直到约定窗口，记录兼容和回滚；不能让旧hash页面突然调用已删API。

## 最小机制片段

```typescript
const deprecatedAt = `@${Date.parse("2026-11-25T00:00:00Z")/1000}`;
console.log(deprecatedAt); // Deprecation语法；不是Sunset格式
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

真实lab /api/v1/workspace保留原DTO并返回Deprecation、Sunset、successor-version链接；/api/v2/workspace保留旧字段并增加meta.schemaVersion。检查旧调用仍工作，不把教学日期当真实服务停用计划。

故障：返回Deprecation:true并次日直接删除v1。依据RFC修正格式，补真实消费者迁移/观察窗口；不能只改header掩盖破坏性下线。

## 移动开发对照

类似旧App版本长期调用旧接口；Web旧标签页/缓存脚本也可能跨越发布窗口，并非每次刷新都已换新。
