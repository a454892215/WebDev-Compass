# 8.5.6 BFF与移动Gateway/API Adapter：职责相似但信任位置不同

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

移动端API Adapter与Web客户端composable可统一请求/模型，运行在用户设备，不能保密服务端凭据。Gateway常管入口路由、TLS、认证/配额等公共能力；BFF面向特定UI组织聚合与展示契约，三者职责可以协作但不是同义词。

PC/H5 UI独立不必自动产生两个BFF；同一业务服务可共享授权/领域规则，不同终端聚合需求若真实分化再拆。BFF无法消除上游权限、网络失败和版本成本，拆分要有所有者、契约、监测及恢复边界。教学scope只能选公开fixture，不代表已建立生产租户隔离或身份认证。

## 最小机制片段

```typescript
const responsibilities = { device:"view + request adaptation", gateway:"entry policy", bff:"UI-oriented aggregation", service:"business authorization" };
console.log(responsibilities.service);
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

把主Nuxt的页面/composable、server workspace、进程内adapter标在调用图；把lab的真实HTTP上游另画，不把两张图混为主项目已联网。说明真实用户进入系统时授权应在哪里，以及本轮未实现部分。

故障：把Android拦截器中的服务secret搬入Nuxt public配置，认为BFF相同架构。追踪浏览器payload，改在server持有受限凭据并最小化返回，真实泄露需轮换。

## 移动开发对照

可参考职责划分与工程约束，不能把Flutter/Android进程单例、存储和网络安全模型直接搬到多请求SSR。
