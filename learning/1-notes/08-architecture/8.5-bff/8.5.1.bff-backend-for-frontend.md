# 8.5.1 BFF聚合与裁剪：服务端职责和失败预算

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

BFF面向特定用户界面聚合、适配后端数据，减少客户端瀑布/契约泄露；它不是通用反向代理，也不是把全部业务逻辑复制一遍。身份入口可在BFF统一处理，但后端仍需在其信任边界检查调用者和资源权限。聚合必须区分必要依赖与可选依赖，给总deadline、取消、并发上限和降级语义。

若必要课程失败，应明确失败而非空列表成功；可选进度失败可返回degraded和null/警示，不能假装进度0。保留可观察错误类别，日志不带凭据与隐私查询。重试只对幂等/安全边界下可重试故障做预算，写请求还需幂等与冲突处理。

## 最小机制片段

```typescript
const policy = { required:["catalog"], optional:["progress"], deadlineMs:80 };
console.log(policy.optional); // 完整真实HTTP逻辑见bff-lab
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

真实bff-lab固定loopback上游：正常200、可选超时200 degraded+progress:null、必要超时504、坏必要DTO502；deadline会取消待完成fetch。主Nuxt聚合进程内fixture adapter，不虚称跨服务HTTP；两者分别阅读。

故障：Promise.all令一个可选失败清空全页。按依赖重要性改变聚合策略，仍对必要输入失败快速退出；不能无条件allSettled后吞掉全部错误。

## 移动开发对照

类似移动网关/API Adapter，但BFF在服务端可有上游身份和资源访问权限；客户端adapter不能保密凭据或代替服务端授权。
