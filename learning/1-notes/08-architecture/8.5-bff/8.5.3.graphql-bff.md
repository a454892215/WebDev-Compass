# 8.5.3 GraphQL与REST BFF：契约、成本与权限不是二选一魔法

前置：阶段3类型/构建、阶段4 Nuxt、阶段5API与阶段6–7质量/部署。先读机制，再运行/观察，独立变体后进入架构决策。

## 解决什么问题与原理

REST用资源与HTTP方法表达接口，GraphQL用schema与查询描述所需字段；GraphQL减少过取并不保证减少总计算或自动消除N+1。GraphQL可返回data加errors，HTTP200不等于完整业务成功；REST聚合也能明确部分失败。选择应考虑团队工具、缓存、查询复杂度和后端形态。

两种都需输入校验、身份/逐资源字段权限、成本/深度/并发限制、超时与可观察性。GraphQL DataLoader/客户端缓存不得跨用户无限共享；GraphQL endpoint不因只有一个URL就免CSRF。选择REST不等于已经解决DTO和版本兼容。

## 最小机制片段

```typescript
const partial = { data:{course:{title:"Vue"},progress:null}, errors:[{message:"progress unavailable"}] };
console.log(partial.data.progress); // 合成GraphQL响应，未运行GraphQL服务
```

片段的Nuxt/校验上下文按注释使用；设计对象/伪码不冒充已运行框架工程。

## 观察、场景与误区

类型：GraphQL官方观察+REST lab对照。读GraphQL response data/errors与授权指南，把lab的degraded/null语义写成GraphQL样例，说明HTTP/字段错误/认证分别怎么处理。本轮未装Apollo/urql或GraphQL server。

故障：客户端只检查response.ok就把data.progress:null当0。检查data/errors与业务字段语义，展示部分失败并保留课程；不要把所有errors一律全屏崩溃。

## 移动开发对照

移动端网络库可复用错误模型思路；GraphQL字段级部分结果仍需要业务级UI设计。
