# 2.2.7 资源提示：preload、prefetch与preconnect的边界

[本章目录](./README.md) · [阶段地图](../../../../knowledge-map/01-foundation-stages-0-2.md#22-浏览器原理)

## 解决什么问题

浏览器发现关键资源太晚时，可以提前提示；提示太多或参数不匹配也会浪费带宽与连接。

## 原理与关键规则

preload面向当前导航将要使用的资源，需正确as及匹配URL/请求模式；它请求资源但不会自动执行脚本或应用样式。

prefetch面向可能的后续导航，浏览器可按网络、数据节省和策略忽略；不能把声明存在等同于已下载。preconnect尝试提前准备跨源连接，不能让跨源请求绕过CORS。

字体等跨源模式要匹配crossorigin，否则可能重复请求。preload错资源、错as或根本不使用，可能抢占真正关键请求；先用Network和Resource Timing确认发现顺序与重用。

本地同源preconnect没有展示公网握手收益；Resource Timing的duration也不证明给用户带来多少提升。最终仍需实际加载指标。

## 最小例子

以下JavaScript在配套浏览器页面的模块环境或Console中观察，元素由该页面提供；HTML片段中的资源名是说明用占位，完整实验使用本地真实文件，不要求在空白Node文件直接运行。

```html
<link rel="preload" href="./cover.svg" as="image" />
<!-- 后面确实使用同一资源 -->
<img src="./cover.svg" width="640" height="360" alt="阅读主题示意" />
```

片段用于解释本节关键机制；完整运行环境和真实资源见[本节实验](../../../2-examples/02-javascript-browser/2.2-browser-internals/2.2.7.link-rel-preload-demo.html)，不把占位资源名视为仓库已有文件。

## 移动端对照与边界

类似预取资源的思路，但浏览器资源提示受导航、连接、缓存和用户策略控制，不等于App能随意提前下载全部内容。

## 常见误区

preload不会自动应用CSS；preconnect不是CORS授权；prefetch可能被忽略，不能把全部资源都提升为高优先级。

## 实验与独立实践

1. 页面真正preload并使用本地SVG，读取其Resource Timing与完成状态。
2. 核对prefetch声明与实际条目，缺条目时记录策略差异而非伪造成功。
3. 在DevTools看优先级和重复请求；不要从同源本地样本声称降低了TLS耗时。
