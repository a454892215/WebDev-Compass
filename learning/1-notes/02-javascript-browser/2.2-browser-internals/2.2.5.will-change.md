# 2.2.5 合成与will-change：提示不是GPU加速开关

[本章目录](./README.md) · [阶段地图](../../../../knowledge-map/01-foundation-stages-0-2.md#22-浏览器原理)

## 解决什么问题

transform/opacity有时能减少每帧布局或绘制，但给所有元素加will-change可能增加资源成本。需要理解提示、层与实际测量的区别。

## 原理与关键规则

合成将适当的图层组织成屏幕图像；层是否产生、如何栅格化和放到GPU由浏览器决定。DOM元素与合成层不是固定一对一。

will-change向浏览器提示预期变化，可能提前准备资源，也可能增加内存和建立层叠上下文。它不改变CSS属性语义，不保证提层或更快。

只在已知热点和有限元素上提前设置，交互结束后移除，给浏览器释放资源的机会。用transform表达位移时仍需考虑焦点、命中区域、溢出与减少动效偏好。

实际GPU、图层数和速度需要Layers/Performance等工具确认；getComputedStyle只能证明声明生效。不能把translateZ(0)当所有性能问题的修复。

## 最小例子

以下JavaScript在配套浏览器页面的模块环境或Console中观察，元素由该页面提供；HTML片段中的资源名是说明用占位，完整实验使用本地真实文件，不要求在空白Node文件直接运行。

```javascript
const card = document.querySelector('#card');
card.style.willChange = 'transform';
// 先给浏览器准备机会；实际交互结束或取消时：
card.style.willChange = 'auto';
```

片段用于解释本节关键机制；完整运行环境和真实资源见[本节实验](../../../2-examples/02-javascript-browser/2.2-browser-internals/2.2.5.will-change-demo.html)，不把占位资源名视为仓库已有文件。

## 移动端对照与边界

和移动端合成/纹理资源成本有共通点，但Web应用不能仅凭CSS声明保证某个GPU路径，浏览器实现与设备能力仍需测量。

## 常见误区

“will-change:all越多越快”“有transform就是独立GPU层”不成立。不要用合成优化掩盖过量脚本或错误布局。

## 实验与独立实践

1. 准备提示后移动方块，观察实际transform和will-change读数。
2. 清除提示，确认几何目标仍然相同；在reduce偏好下不依赖动画才能完成状态更新。
3. 若需证明图层变化，另用Layers/Performance记录；页面输出不报告虚构GPU状态。
