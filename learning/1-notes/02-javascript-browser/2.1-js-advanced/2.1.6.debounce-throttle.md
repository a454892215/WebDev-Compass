# 2.1.6 防抖与节流：频繁事件的调度与取消

[返回章节](./README.md) · [知识地图](../../../../knowledge-map/01-foundation-stages-0-2.md#21-javascript-进阶)

## 解决什么问题与前置

搜索框每个字符都请求，滚动事件每次都计算，怎样分别控制触发频率？

前置：阶段1闭包、this/参数、定时器；2.1.2与2.1.4。

## 工作机制

1. 防抖把一串密集调用归为一次，常见trailing策略在最后一次之后等待窗口结束；持续输入可能持续延后，是否需要leading或maxWait由产品任务决定。

2. 节流限制窗口内执行频次，但leading、trailing和窗口起点是实现策略，不能只背“每N毫秒一次”而忽略最后一个值。

3. 包装函数需保留需要的this和参数，取消接口应清除定时器与保留引用。组件销毁时清理，重复创建包装器会破坏同一窗口的合并。

4. 防抖不解决已发请求竞争；仍需AbortController或版本号防迟到结果。定时器不是精确时钟；视觉更新可考虑RAF但不能把它等同网络请求节流。

## 最小示例

```javascript
function debounce(fn, wait) {
  let timer;
  function wrapped(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  }
  wrapped.cancel = () => clearTimeout(timer);
  return wrapped;
}
const search = debounce(value => console.log(value), 150);
search("v"); search("vu"); search("vue"); // 最终只输出vue
// 离开当前功能时：search.cancel();
```

## 场景、边界与误区

debounce(fn,150)每次input重新创建无法合并；只cancel定时器不代表取消之前已发HTTP请求。取消调用后也不要假定业务操作已回滚。

## 移动端经验对照

可类比移动端debounce/throttle操作符的目标，但库的leading/trailing、取消和生命周期语义各不相同，必须核对实际实现。
