# 2.1.4 事件循环：任务、微任务与渲染机会

## 解决什么问题与前置

为什么Promise回调通常先于零延迟timer执行，而长同步代码仍会阻塞点击？

前置：先完成2.1.3及阶段1Promise、定时器、DOM事件。

## 工作机制

1. 浏览器主线程上的JavaScript执行具有run-to-completion特征；当前调用栈没有清空时，另一个普通任务不会抢占它。Web API可在宿主其他机制中工作，但回调仍需排队。

2. 通常称“宏任务”的内容在HTML规范中是task。定时器、事件等有不同任务来源，不是一条全局FIFO队列；微任务检查点会把已排入的Promise反应、queueMicrotask等继续处理。

3. 同一个检查点中新加入的微任务会继续处理，直到队列空；递归制造微任务会饿死后续任务与渲染，不是免费后台计算。

4. 浏览器在合适机会更新渲染，并非每个任务后必画一帧。requestAnimationFrame、timer、网络之间不能推导所有环境的绝对顺序。长工作应分片或交给Worker；scheduler.yield需能力检测和适当回退。

## 最小示例

```javascript
const order = [];
order.push("sync:start");
setTimeout(() => { order.push("timer"); console.log(order); }, 0);
Promise.resolve().then(() => {
  order.push("promise");
  Promise.resolve().then(() => order.push("nested"));
});
queueMicrotask(() => order.push("microtask"));
order.push("sync:end");
// 本例：sync:start, sync:end, promise, microtask, nested, timer
```

## 场景、边界与误区

setTimeout(fn,0)表示不早于条件满足后排队，不保证精确0ms；await Promise.resolve()只让出到微任务，不保证浏览器能先处理输入或绘制。
