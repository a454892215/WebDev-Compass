# 6.2.5 依赖安全：审计快照、锁文件与升级判断

前置：阶段3工程工具、阶段4Vue/Nuxt和阶段5请求/会话边界。先机制、再本地实验、最后副本变体，不把这些基础质量要求延后到上线。

## 机制与使用场景

audit把解析依赖与已知漏洞数据库比较，不证明未知漏洞不存在，也不证明应用的可达路径一定受影响。区分生产依赖、开发/构建链、可选平台包与实际部署环境，记录日期、命令、退出码和范围。服务不可达时应写无法获取，不能说0漏洞。

读取公告的受影响范围、修复版本、攻击前提与传递路径，结合可达性和升级回归决定处理；不要为了清数字盲目audit fix force、删锁或大版本乱升。无公告的包也需评估维护、来源、发布和权限；完整性哈希锁住内容，不等于内容安全。

pnpm11的发布年龄/依赖脚本策略在YAML，具体例外应审阅，不抄全局放行模板。最小固定依赖、锁文件复核和有针对性的构建/行为回归共同提供证据，本节不要求每次运行都重复外网审计。

## 最小例子

```bash
pnpm audit --prod --json
pnpm install --frozen-lockfile
# 根据确切公告与变更范围升级后，运行相关测试；不自动--force。
```

片段按注释提供上下文；完整导入与运行入口见操作卡，不是独立工程。

## 运行与边界

本lab在2026-11-25实际pnpm audit --prod返回0项已知公告，metadata生产依赖总量31；这不含开发依赖，不代表全知识库或所有平台安全。保留该有日期的快照和固定锁。

## 移动开发经验对照

迁移的是信任边界、状态所有权与失败恢复方法；浏览器脚本/Cookie/DOM/SSR和原生宿主机制不同。国际化同样需区分语言、时间与排版，不能照搬字符串替换或平台存储假设。
