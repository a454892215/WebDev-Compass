# 6.2.2 CSRF：凭据自动携带、Origin与会话绑定Token

前置：阶段3工程工具、阶段4Vue/Nuxt和阶段5请求/会话边界。先机制、再本地实验、最后副本变体，不把这些基础质量要求延后到上线。

## 机制与使用场景

浏览器可能自动携带Cookie，攻击站点即使读不到响应，也可能发出简单表单写请求；CORS主要控制脚本读取，不能当作CSRF防线。SameSite围绕站点而非端口源，两个localhost端口可不同源但同站；HttpOnly也不会阻止请求携带Cookie。

对需要Cookie身份的变更接口使用服务端可核对的Origin与会话绑定同步token，防止错误信任子域/任意反射来源。Token不放URL或日志，认证/资源授权仍独立检查。普通读取不应造成业务变更，登录与退出本身也要分析CSRF。非浏览器客户端、webhook、OAuth回调等应按各自协议设计，不能盲目要求所有端点完全相同。

本独立lab只有匿名演示nonce Cookie与变更计数，非真实登录；阶段5已建立实际本地会话绑定CSRF。主阶段6公开课程没有登录写接口，不虚构新的CSRF认证实现。

## 最小例子

```javascript
// server.mjs处理器上下文：req/res、sessions、sid、origin和json均由完整文件提供。
const sessionToken = sessions.get(sid)
if (req.headers.origin !== origin || !sessionToken || req.headers['x-csrf-token'] !== sessionToken) {
  return json(res, 403, { changed: false })
}
// 之后仍需身份/对象授权和输入校验；不能只在按钮上检查。
```

片段按注释提供上下文；完整导入与运行入口见操作卡，不是独立工程。

## 运行与边界

同源带正确token的POST计数加一；缺token403；4504发来的跨源简单POST不能使计数增加。另有CORS错误反射可读合成私有值，证明读/写策略不是一回事。

## 移动开发经验对照

迁移的是信任边界、状态所有权与失败恢复方法；浏览器脚本/Cookie/DOM/SSR和原生宿主机制不同。国际化同样需区分语言、时间与排版，不能照搬字符串替换或平台存储假设。
