# 6.2.1 XSS：按输出上下文防护，而非依赖HttpOnly

前置：阶段3工程工具、阶段4Vue/Nuxt和阶段5请求/会话边界。先机制、再本地实验、最后副本变体，不把这些基础质量要求延后到上线。

## 机制与使用场景

XSS按数据到可执行上下文的路径分析：反射型由请求进入响应，存储型先保存再展示，DOM型由客户端代码把不可信值送入危险sink；分类可能交叠，不能只靠URL里有没有script判定。默认把文本作为文本输出，Vue插值和textContent适合文本；HTML属性、URL、CSS和JavaScript上下文有各自规则，不能用一份通用转义包治全部。

确需富文本时使用适配当前环境、持续维护的净化器并最小化允许标签/属性。本例DOMPurify只允许b/em且不允许属性，净化后不再拼接未信任HTML。不要用正则删script当净化，不把所有v-html都称安全；原生Sanitizer/Trusted Types还需目标浏览器支持和明确策略。

CSP是纵深防护，不替代安全输出与净化；HttpOnly限制读取会话Cookie，不阻止脚本执行或借当前用户发请求。代码执行、数据读取和请求权限是不同风险。

## 最小例子

```javascript
// security-entry.js：完整浏览器上下文在lab内。
const input = '<img src=x onerror="window.xssMarker=true"><b>Allowed bold</b>'
document.querySelector('#text').textContent = input
const clean = DOMPurify.sanitize(input, { ALLOWED_TAGS: ['b', 'em'], ALLOWED_ATTR: [] })
document.querySelector('#rich').innerHTML = clean // 仅这份净化后的HTML进入sink
```

片段按注释提供上下文；完整导入与运行入口见操作卡，不是独立工程。

## 运行与边界

真实Chrome中text区域没有img节点，净化区保留b但没有img/script/a，xssMarker未出现；同页未经许可内联脚本被CSP阻止。没有向真实用户注入脚本。

## 移动开发经验对照

迁移的是信任边界、状态所有权与失败恢复方法；浏览器脚本/Cookie/DOM/SSR和原生宿主机制不同。国际化同样需区分语言、时间与排版，不能照搬字符串替换或平台存储假设。
