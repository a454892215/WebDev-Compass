# 6.4.2 Vue-i18n与Nuxt：应用实例、URL语言和SSR一致

前置：阶段3工程工具、阶段4Vue/Nuxt和阶段5请求/会话边界。先机制、再本地实验、最后副本变体，不把这些基础质量要求延后到上线。

## 机制与使用场景

Vue-i18n的global scope是一个Vue应用内的作用域，不等于Node进程全局。Nuxt SSR要按请求/应用创建实例，不能把可变locale保存在模块顶层单例；否则并发用户可能串语言。

当前样例从已验证的URL locale决定语言，在页面渲染前设置对应实例，服务端/客户端用同一规则。不要服务端默认英文、浏览器初始化又按navigator/localStorage改中文导致接管不一致。若采用Nuxt i18n模块，其路由/懒加载/SEO能力与配置要按版本核对，本lab不冒称安装该模块。

组件组合式useI18n要在正确setup上下文调用，区分局部/全局消息与返回ref；i18next作为React分支对照，不要求两套库都装进Vue项目。

## 最小例子

```javascript
// Nuxt插件机制；每次应用创建时执行，而非文件顶层共享实例。
export default defineNuxtPlugin(nuxtApp => {
  const instance = createI18n({ legacy: false, locale: trustedRouteLocale, fallbackLocale: 'en', messages })
  nuxtApp.vueApp.use(instance)
})
// trustedRouteLocale须由允许列表解析；完整代码见主工程。
```

片段按注释提供上下文；完整导入与运行入口见操作卡，不是独立工程。

## 运行与边界

独立lab创建两份Vue-i18n，改变A语言不改变B；浏览器en→ar→en真实更新。Nuxt SSR并发与导航由主工程另验，不把纯实例测试当真实SSR证明。

## 移动开发经验对照

迁移的是信任边界、状态所有权与失败恢复方法；浏览器脚本/Cookie/DOM/SSR和原生宿主机制不同。国际化同样需区分语言、时间与排版，不能照搬字符串替换或平台存储假设。
