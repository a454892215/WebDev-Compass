# 6.4.3 Intl：显式locale、时区、日历与货币

前置：阶段3工程工具、阶段4Vue/Nuxt和阶段5请求/会话边界。先机制、再本地实验、最后副本变体，不把这些基础质量要求延后到上线。

## 机制与使用场景

Intl格式化表示，不做汇率换算或业务时区决策。locale决定语言/地区格式，timeZone决定一个时间瞬间显示在哪个地区，calendar与numberingSystem也可能影响输出。货币代码需要业务明确，不因语言猜用户的钱种。

ISO带Z/offset的时间点与纯日期是不同数据；不要随意把生日/账期当UTC时间点再转换。SSR与浏览器至少应共享明确locale/timeZone和同一数据语义，避免午夜跨日或接管差异。ICU/运行时版本仍可能影响空格和样式，应按目标环境核对或用formatToParts验证语义，不把所有输出写成手工模板。

本lab固定2026-11-25T23:30:00Z与UTC，展示en/zh-CN/ar数字/货币；主Nuxt显式gregory/UTC。它证明参数与当前运行结果，不表示所有时区/历法均认证。

## 最小例子

```javascript
const date = new Date('2026-11-25T23:30:00Z')
new Intl.DateTimeFormat('en', { year:'numeric', month:'2-digit', day:'2-digit', timeZone:'UTC' }).format(date)
new Intl.NumberFormat('en', { style:'currency', currency:'USD' }).format(1234.5)
// $1,234.50是表示结果，不表示把其他币种换成美元。
```

片段按注释提供上下文；完整导入与运行入口见操作卡，不是独立工程。

## 运行与边界

Node真实UTC日为25、英文11/25/2026和货币1,234.50检查通过；浏览器切语种后日期/货币随实例locale变化。

## 移动开发经验对照

迁移的是信任边界、状态所有权与失败恢复方法；浏览器脚本/Cookie/DOM/SSR和原生宿主机制不同。国际化同样需区分语言、时间与排版，不能照搬字符串替换或平台存储假设。
