# 6.1.3.2 Service Worker：公开白名单、离线与更新

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

控制离线公开资源的回退和版本，不把所有请求缓存成可能泄露的副本。

## 原理与选择

Cache First适合版本化公开资产，Network First优先新响应并在网络失败回退缓存。策略还需说明状态检查、超时、缓存上限/版本和离线无命中情况，不能只给策略名字。

SW scope是URL控制范围，不是权限沙箱。应只拦截明确GET白名单和同源目标，不缓存登录/API/私有响应；Cache API可保存某些HTTP不打算缓存的响应，应用必须自行保护。

lab注册仅/sw-lab/，缓存名前缀专有；activate只删自己的旧版本，保留其他cache。更新skipWaiting/claim用于本地演示，生产需评估新worker与旧页面版本一致，不自动照搬强切换。

## 最小机制片段

```javascript
// 放在sw.js的fetch事件handler内；request来自event.request。
// 此片段在同源公开GET白名单判断之后执行。
const request = event.request
const cache=await caches.open('compass-stage6-performance-v1')
try { const response=await fetch(request); if(response.ok)await cache.put(request,response.clone()); return response }
catch { return (await cache.match(request)) || new Response('offline missing',{status:503}) }
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

Chrome真注册/控制，cache-first预缓存、network-first在线版本变化/离线回退、离线导航页均验证；旧专有v0删除、foreign前缀保留，最终注销自己scope并删自己缓存。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
