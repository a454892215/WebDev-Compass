# 6.1.2.1 布局读写：定位强制布局与批处理

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

减少反复使布局失效又立刻同步读取的工作，先找真实强制布局。

## 原理与选择

DOM/style写入可能使布局变脏，随后读取offsetWidth/getBoundingClientRect等几何值可能迫使浏览器同步计算。每个读取都昂贵并非绝对，关键是时序与影响范围。

把必要读取集中，再批量写入通常可减少交错失效；CSScontain/content-visibility可限制范围但有布局与访问边界，不能盲目全局will-change。

比较必须保持相同元素、操作和结果，测量可能受机器/热身/浏览器影响。一个duration更小不构成稳健收益，不能用控制台数字替代trace定位。

## 最小机制片段

```javascript
// 放在含#layout-box及其子元素的lab页面模块中。
const box = document.querySelector('#layout-box')
if (!box) throw new Error('缺少layout-box')
const rows = [...box.children]
const width = box.offsetWidth // 先收集需要的布局值
for (const row of rows) row.style.width = `${width - 8}px`
// 反例是在每次样式写入后再读取布局；完整lab给同条件按钮与measure。
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

点击交错/批处理按钮，实际measure记录各耗时并检查相同输出宽度；不硬断言单次batch一定更快，trace可继续手工定位。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
