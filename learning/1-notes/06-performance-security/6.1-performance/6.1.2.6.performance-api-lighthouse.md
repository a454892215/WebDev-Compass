# 6.1.2.6 Performance API与Lighthouse：可复核测量

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

建立“操作→证据→解释→限制”的闭环，避免用分数或计时器装饰优化。

## 原理与选择

performance.mark/measure可定位应用区间；PerformanceObserver按支持类型订阅条目，buffered能获取部分历史条目。observer与资源都要清理，不能在不支持时直接调用。

Lighthouse是特定配置/设备模拟的lab审计，受环境、节流、负载和缓存影响。性能分数采用指标权重/分布，不是业务SLA；TBT有诊断价值但不等于真实用户INP。

本实验只运行一次本地audit并保存配置/指标，交互变体另用原生条目记录。对照保持内容/视口/缓存/CPU策略一致，多次和分布评估属于后续阶段9。

## 最小机制片段

```javascript
// 放在lab模块中，work是待观察的实际函数，不使用未声明变量。
const work = () => document.querySelectorAll('#rows li').length
performance.mark('work:start')
await work()
performance.mark('work:end')
performance.measure('work','work:start','work:end')
// 完整上下文在lab；不要把await区间总时长当CPU执行时间。
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

pnpm verify产生artifacts/runtime.json与Lighthouse原始JSON；记录blocking/chunked/thrash/batch的真实duration，单次结果不硬断言更快。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
