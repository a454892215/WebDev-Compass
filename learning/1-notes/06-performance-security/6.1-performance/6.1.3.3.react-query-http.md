# 6.1.3.3 Nuxt数据缓存与HTTP响应缓存的失效

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

数据不一致时区分应用内key、SSR payload和HTTP缓存，而非全局刷新碰运气。

## 原理与选择

Nuxt useFetch/useAsyncData的key对应应用数据身份与共享状态，payload可避免接管时重复读取；这不是默认跨用户全局HTTP缓存。相同key的关键选项应一致，变换数据身份要换key/响应式URL或明确刷新。

HTTP缓存头控制响应层；应用内缓存清理不自动清CDN/SW/HTTP，反之亦然。写入后应按契约失效相关查询，身份变化要取消/清理私有结果并隔离新请求。

本组HTTP cache和Vuecomputed是真实实验；Nuxt运行复用阶段6主工程的既有数据key/统计按需路径，不声称本lab运行React Query或Nuxt服务端私有缓存。

## 最小机制片段

```javascript
// Nuxt setup中的机制示意，完整调用上下文以主工程为准。
const {data,refresh,clear}=await useFetch('/api/catalog',{key:'public-catalog'})
// 写入成功后按相关key刷新；退出清理私有key，不盲清所有用户/所有项目。
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

观察lab HTTP重验证与private no-store，再核对主工程Nuxt key/SSR读取。React Query只随React分支选学，本组不额外引依赖。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
