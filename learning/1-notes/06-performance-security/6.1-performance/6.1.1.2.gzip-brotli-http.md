# 6.1.1.2 网络：压缩、请求成本与HTTP/2

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

降低实际传输成本，而不是不看缓存和协议就追求最少请求数。

## 原理与选择

Gzip/Brotli对文本资源编码；Content-Encoding说明编码，Content-Type仍描述原始媒体。协商通常基于Accept-Encoding并正确设置Vary；已压缩图片或很小资源不一定值得再压缩。

HTTP/2在连接上多路复用多个流，改善HTTP/1.1某些连接限制，不意味着没有优先级、拥塞或TCP层队头阻塞。不能用本地HTTP/1.1压缩实验冒称HTTP/2部署已验收。

请求合并、分包、缓存命中和关键资源优先级要一起权衡。更多小chunk可能增加开销，单一大包又可能延迟首屏；应看实际瀑布和内容复用。

## 最小机制片段

```javascript
// Node实验用gzipSync/brotliCompressSync编码同一固定文本。
// 响应同时返回Content-Encoding与Vary。
const response = await fetch('/api/compressed?encoding=gzip')
const text = await response.text() // Fetch通常已解码，text.length不是线上的压缩字节数。
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

pnpm check通过Node http读取原始字节并解码核对，报告固定125000字节文本的编码大小；极重复fixture不代表业务压缩比。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
