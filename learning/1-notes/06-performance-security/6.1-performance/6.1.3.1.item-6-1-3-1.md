# 6.1.3.1 缓存层：HTTP、内存、bfcache与Cache API

前置：阶段2浏览器/模块、阶段3工程工具与阶段4Vue/Nuxt；先明确测量目标，再读机制和实验。

## 解决什么问题

判断命中的是哪一层，才能解释为什么没有网络或为什么仍看到旧内容。

## 原理与选择

HTTP缓存按Cache-Control/ETag等规则管理响应，内存/磁盘是实现位置；no-cache允许存储但要求重验证，no-store要求不存HTTP缓存。304复用原有响应体，浏览器Fetch最终可能呈现200，这是合并后的结果。

bfcache保存页面执行/DOM快照，和HTTP响应缓存不同。Chrome2025起在安全条件下允许部分no-store页进入bfcache，因此不能教成no-store在所有浏览器永远阻止后退快照。敏感数据仍需no-store及会话/恢复策略。

Cache API由应用/SW明确管理，不是自动HTTP缓存；应用内Nuxt key/payload又是另一层。删除某一层不代表其他层都失效，身份变化必须考虑用户数据边界。

## 最小机制片段

```javascript
const response = await fetch('/api/cache')
// 首次200 + ETag:v1，之后浏览器可条件重验证。
// 直接HTTP条件请求的304没有新响应体；浏览器消费会合并缓存。
```

片段按注释说明DOM/模块/框架上下文，完整导入与运行工程在操作卡；不把独立片段冒充完整可执行项目。

## 实际观察与边界

Node测试真实200/If-None-Match304，Chrome重复读取后server stats有revalidation；mockPrivate两次都到服务器。bfcache提供pageshow/DevTools观察，不冒称本轮有普遍命中保证。

## 移动开发对照

共同目标是减少等待、主线程工作和资源成本；浏览器渲染、HTTP/页面生命周期、DOM与缓存层不同于移动框架，不能按API名字套底层方案。测试只覆盖本次Web环境。
