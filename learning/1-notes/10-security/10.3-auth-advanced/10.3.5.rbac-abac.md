# 10.3.5 RBAC、ABAC与对象授权：服务端每请求默认拒绝

前置：阶段0同源/HTTP、3类型与测试、5会话/授权、6安全基础、8请求/状态边界；先解释机制，再进入实验与独立变体。

## 解决什么问题与原理

前端权限数据用于可用交互和解释，不构成访问控制。RBAC以角色组织能力，ABAC/关系条件可把主体、资源、tenant、owner与情景一起判断；角色足够宽时仍可能越权访问他人对象。策略应默认拒绝，服务端每次读取/写入均验证当前可信身份与资源关系，不能从请求body接收owner/role并直接信任。

本例read需要reader且owner一致、tenant一致；delete还需admin且owner/tenant一致。业务可能有合法跨租户管理员，但必须显式设计，不以“admin就全部放行”为默认。403/404如何减少对象枚举取决于契约，本lab返回403但数据全是公开合成fixture。

## 最小上下文片段

```javascript
const allowed = authorize(
 {id:'alice', tenant:'t1', roles:['reader']},
 {owner:'bob', tenant:'t1'}, 'read'
);
console.log(allowed); // false，角色存在也不能读另一个owner
```

片段中的helper来自[auth-lab完整源码](../../../2-examples/10-security/10.3-auth-advanced/auth-lab/README.md)，不是任意项目可直接粘贴的全套认证。

## 场景、观察与边界

第四组Node验证owner、tenant、role、未知action与坏roles类型拒绝。真实HTTP再验证同一会话own note200、note-b他人owner403、note-c其他tenant403、reader DELETE403；不是只隐藏按钮。会话由任何访问者可创建公开Alice fixture，不是真实身份认证。

可信认证上下文和资源授权分层；每次服务端决策都从当前会话/已验证claims取得主体，不用浏览器缓存角色当永久事实。

## 移动开发对照

Web页面、SSR、Cookie请求与原生存储的生命周期不同；只借鉴规范/契约，不能将移动API或进程单例直接视为Web安全方案。
