# 10.3.6 JWT验证：签名、算法、声明、用途和撤销上下文

前置：阶段0同源/HTTP、3类型与测试、5会话/授权、6安全基础、8请求/状态边界；先解释机制，再进入实验与独立变体。

## 解决什么问题与原理

JWT decode只是解析不可信payload，不证明签名或声明。使用维护中的jose等库，固定允许算法与可信key来源，校验iss/aud/exp/nbf等适用声明、subject/用途和所需claim类型。ID Token与access token需按不同上下文验证，typ只是补充上下文；kid/jku不能变成任意网络URL或文件读取。签名不提供内容保密，浏览器收到payload就应视为可见。

短期JWT不会自动立即撤销；服务端可用会话/版本/denylist等在线条件，明确保存期限和传播策略。令牌轮换、用户退出与角色更改分别考虑；不要自己拼base64或手写加密算法作为生产实现。

## 最小上下文片段

```javascript
// 上下文：core.mjs createJwtFixture内，publicKey由generateKeyPair得到，token为verify参数。
const result = await jwtVerify(token, publicKey, {
 algorithms:['ES256'], issuer:'https://issuer.example', audience:'stage10-lab',
 requiredClaims:['exp','iat','sub','jti'], typ:'at+jwt', maxTokenAge:'2m'
});
// 然后验证业务claim类型/固定kid与应用撤销状态，仍须对象授权。
```

片段中的helper来自[auth-lab完整源码](../../../2-examples/10-security/10.3-auth-advanced/auth-lab/README.md)，不是任意项目可直接粘贴的全套认证。

## 场景、观察与边界

jose6.2.18由本轮官方registry固定。第三组Node真实生成临时ES256 keypair并签验，拒绝错误算法HS256、其他签名key/被改签名、issuer/audience、过期、错误typ/kid、坏roles；撤销jti后拒绝。私钥只在进程内，未导出真实密钥，未建立远程JWKS轮换或生产KMS。

本lab模拟撤销Set不是持久分布式撤销服务；maxTokenAge是一项本例政策，不是所有JWT固定2分钟。

## 移动开发对照

Web页面、SSR、Cookie请求与原生存储的生命周期不同；只借鉴规范/契约，不能将移动API或进程单例直接视为Web安全方案。
