# 10.3.1 OAuth/OIDC授权码与PKCE：分清授权、身份和客户端边界

前置：阶段0同源/HTTP、3类型与测试、5会话/授权、6安全基础、8请求/状态边界；先解释机制，再进入实验与独立变体。

## 解决什么问题与原理

OAuth让客户端在授权范围内访问资源，不独自定义用户登录身份；OIDC在其上增加ID Token和身份语义，JWT只是可能采用的令牌格式。授权码+PKCE流程先生成高熵verifier和S256 challenge，发起请求时绑定注册redirect_uri和客户端事务，再由回调核对state/事务，兑换时验证code、redirect与verifier；本例同时检查state和PKCE，不把二者作用简单等同。

真实OIDC还要按提供商元数据验证ID Token的签名、issuer、audience、时间、nonce等适用要求，不把ID Token当API access token。浏览器公共客户端不能保守client_secret；BFF可在服务端保存令牌但仍须认证、CSRF与授权。避免隐式流/资源所有者密码授权作为新项目默认，不把URL日志里的code/token当普通诊断数据。

## 最小上下文片段

```javascript
const flow = mockAuthorizationFlow();
const result = flow.complete({
  callbackState: flow.state, authorizationCode: flow.code,
  codeVerifier: flow.verifier, redirectUri: 'http://127.0.0.1:4523/callback'
});
console.log(result.subject); // alice，公开合成身份，非真实IdP
```

片段中的helper来自[auth-lab完整源码](../../../2-examples/10-security/10.3-auth-advanced/auth-lab/README.md)，不是任意项目可直接粘贴的全套认证。

## 场景、观察与边界

运行auth-lab的第一组Node测试，检查错误state、错误S256 verifier、错误redirect_uri及已消费code被拒绝，正确组合只通过一次。这是受控内存协议模型，未建立真实授权服务器、用户认证、OIDC签名ID Token或外部provider联调；SHA256仅实现标准PKCE计算，不手写JWT签验。

先保证代码/回调/事务绑定；PKCE不替代后端资源授权，nonce也不等于任意CSRF token。生产集成使用维护中的OIDC库，处理错误回调、重放、时钟与注销约定。

## 移动开发对照

Web页面、SSR、Cookie请求与原生存储的生命周期不同；只借鉴规范/契约，不能将移动API或进程单例直接视为Web安全方案。
