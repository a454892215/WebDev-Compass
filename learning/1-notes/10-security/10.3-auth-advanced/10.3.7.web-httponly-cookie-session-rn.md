# 10.3.7 Web Cookie与原生安全存储：迁移威胁模型，不照搬API

前置：阶段0同源/HTTP、3类型与测试、5会话/授权、6安全基础、8请求/状态边界；先解释机制，再进入实验与独立变体。

## 解决什么问题与原理

原生Keychain/Keystore可降低静态密钥/凭据的特定存储风险，浏览器HttpOnly Cookie解决的是脚本读取边界，两者不等价。Web还受同源脚本、Cookie自动请求、CSRF、页面/文档生命周期与浏览器扩展影响；原生应用也有设备、进程、桥接与服务端授权风险。不能用“放安全存储”概括整个认证系统。

SSR进一步区分客户端可见payload与服务端上下文；全局currentUser/缓存可能跨请求混用。复用移动端架构规范与接口契约，Web技术方案仍采用Web适配的会话、CSP、CSRF和request-scoped状态，真实后台每请求授权。

## 场景、观察与边界

对照本lab HttpOnly不可读但fetch成功、logout后旧Cookie401，与主Nuxt将来的每会话owner-only notes源码核对。此处只执行Web本地fixture，不安装Android/Flutter/RN、不测试Keychain/Keystore，也不把原生安全存储称能抵御所有XSS或服务端越权。

不要硬抄Flutter第三方库或底层框架；用平台适配生命周期与威胁边界，保留高层规范、契约和最小充分验证。

## 移动开发对照

Web页面、SSR、Cookie请求与原生存储的生命周期不同；只借鉴规范/契约，不能将移动API或进程单例直接视为Web安全方案。
