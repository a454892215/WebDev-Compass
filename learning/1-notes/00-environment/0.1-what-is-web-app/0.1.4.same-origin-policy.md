# 0.1.4 同源策略与跨域问题的来源

> [← 返回 0.1 目录](./README.md) · [知识库地图](../../../../knowledge-map/01-foundation-stages-0-2.md#01-web-应用是什么)

## 一句话理解

**同源策略**是浏览器的安全机制：限制脚本跨源读取响应和访问其他文档；跨源嵌入、导航与部分写入可以发生。当前端请求的 API 协议/域名/端口与页面不一致时，就会遇到**跨域（Cross-Origin）**问题。

---

## 什么是「源」（Origin）

一个源由 **协议 + 域名 + 端口** 三部分组成：

```
https://www.example.com:443/api/users
└─┬──┘ └──────┬──────┘└┬┘
 协议        域名      端口（HTTPS 默认 443，通常省略）
```

### 同源判定

| URL A | URL B | 是否同源 | 原因 |
|-------|-------|----------|------|
| `https://example.com/a` | `https://example.com/b` | ✅ 同源 | 协议、域名、端口相同 |
| `https://example.com` | `http://example.com` | ❌ 跨域 | 协议不同（https vs http） |
| `https://example.com` | `https://api.example.com` | ❌ 跨域 | 域名不同 |
| `https://example.com` | `https://example.com:8080` | ❌ 跨域 | 端口不同 |
| `https://example.com` | `https://example.com:443` | ✅ 同源 | 443 是 HTTPS 默认端口 |

> 注意：**子域名不同即跨域**。`www.example.com` 和 `api.example.com` 是不同源。

---

## 同源策略限制了什么

浏览器默认禁止以下跨源行为：

| 限制 | 说明 |
|------|------|
| **DOM 访问** | A 页面的 JS 不能读写 B 页面的 DOM（如 iframe 跨域） |
| **Ajax / Fetch** | JS 发起的 HTTP 请求不能读取跨源响应 |
| **Cookie / Storage** | Storage 依 origin 隔离；Cookie 有 Domain/Path 等独立作用域，并不按端口隔离 |
| **部分 Web API** | 如 Canvas 导出跨域图片等 |

### 不受同源策略限制的

- 图片、经典 script、样式表等常可跨源嵌入，但仍受 CSP、CORS 等具体规则约束；模块 script 与字体等通常要求 CORS。绘制跨源图片还可能污染 Canvas
- `<form action>` 提交到跨域地址（但无法读取响应）
- 页面**导航**到跨域 URL（变成那个源下的页面）

---

## 为什么会有跨域问题

### 场景

你的前端页面部署在 `https://app.example.com`，API 在 `https://api.example.com`：

```javascript
// 在 app.example.com 的页面中执行
const res = await fetch('https://api.example.com/users');
const data = await res.json(); // ❌ 浏览器拦截响应
```

无预检的请求可能已发出，但 JS 无法读取响应体；需预检的请求若 OPTIONS 失败，实际请求不会发送，Console 报错：

```
Access to fetch at 'https://api.example.com/users' from origin
'https://app.example.com' has been blocked by CORS policy
```

### 为什么浏览器要这样做

假设没有同源策略：

1. 你登录了 `bank.com`，浏览器存有 Session Cookie
2. 你访问了恶意网站 `evil.com`
3. `evil.com` 的 JS 偷偷向 `bank.com` 发请求转走你的钱
4. 若 Cookie 发送策略与服务端权限设计允许，操作可能成功，即使攻击脚本读不到响应

**这段转账攻击属于 CSRF**：同源策略主要限制跨源读取，不能保证阻止跨站表单或简单请求改变状态。服务端还需验证权限、CSRF Token/Origin，并按场景配置 SameSite；CORS 不是身份认证或完整的 CSRF 防护。

---

## CORS：官方的跨域解决方案

**CORS（Cross-Origin Resource Sharing）** 不是绕过安全，而是让**服务器明确声明**「我允许哪些源访问我」。

### 简单请求

服务器在响应头中添加：

```http
Access-Control-Allow-Origin: https://app.example.com
```

对公开、无凭据且确实允许任何网站读取的资源，可使用通配符；涉及用户数据必须收紧来源：

```http
Access-Control-Allow-Origin: *
```

### 预检请求（Preflight）

对 `POST` + `Content-Type: application/json` 等非简单请求，浏览器会**先发 OPTIONS**：

```
OPTIONS /users HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization
```

服务器返回匹配的许可后，浏览器才发真正的 POST；预检缓存有效时可复用许可（受浏览器上限和缓存键限制）：

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

### 带 Cookie 的跨域

还需要：

```http
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://app.example.com  （不能是 *）
```

客户端：

```javascript
fetch('https://api.example.com/users', {
  credentials: 'include'  // 携带 Cookie
});
```

---

`credentials: include` 不绕过 SameSite、第三方 Cookie 限制或服务端授权。Cookie 的同站判定与同源不同，详见 [0.3.4 Cookie 与存储](../0.3-network-basics/0.3.4.cookie-session-localstorage-sessionstorage.md)。

## 开发中常见的跨域解决方式

| 方式 | 适用场景 | 说明 |
|------|----------|------|
| **服务端配置 CORS** | 生产环境标准方案 | 后端加响应头，推荐 |
| **开发代理（Proxy）** | 本地开发 | Vite/Webpack dev server 代理 API |
| **Nginx 反向代理** | 部署时同源 | 前后端通过同一域名访问 |
| **JSONP** | 老旧方案 | 仅 GET，已过时，了解即可 |

### Vite 开发代理示例

```javascript
// vite.config.js
export default {
  server: {
    proxy: {
      '/api': {
        target: 'https://api.example.com',
        changeOrigin: true,
      }
    }
  }
}
```

前端请求 `/api/users` → Vite 转发到 `https://api.example.com/users`，浏览器认为是同源。

## 跨域 vs 移动端

### 为什么移动端没有 CORS

| | Web 浏览器 | Android / iOS App |
|--|-----------|-------------------|
| 运行环境 | 浏览器（有同源策略） | 原生 App（无此限制） |
| 请求方式 | `fetch` / `axios` 受 CORS 约束 | OkHttp / Dio 直接请求任何 URL |
| 安全模型 | 浏览器强制 | 由 App 权限和网络配置决定 |

📱 **这是 Web 开发独有的问题**。你在 Android 用 Retrofit 调任何 API 都不会遇到 CORS，但 Web 前端必须处理。

### WebView 中的跨域

Android/iOS WebView 加载的 H5 页面**同样受同源策略约束**。H5 中的 fetch 受浏览器规则约束；JS 调原生桥不是 HTTP CORS，应由宿主校验页面来源、桥接权限与参数，不能拿代理代替桥接安全。

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| 「跨域 = 请求发不出去」 | 简单请求可能已发送，预检失败则实际请求不发；网络故障需另判 |
| 「CORS 是前端配置」 | CORS 主要靠**后端**设置响应头；前端只能配置 `credentials` 等 |
| 「开发时关掉浏览器安全就行」 | 本课程不关闭安全策略；用本地双源实验或正确代理配置 |
| 「用 * 允许所有源最安全」 | 通配符仅适合有意公开的无凭据资源，用户数据按明确来源授权 |
