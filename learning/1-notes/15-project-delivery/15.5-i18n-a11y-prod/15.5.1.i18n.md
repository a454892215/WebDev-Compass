# 15.5.1 按模块加载消息、ICU复数与select

前置：阶段6国际化/无障碍、阶段12测试与组件契约；先15.5.1→15.5.2→15.5.3，再15.5.4确定交付范围，15.5.5/6落实导航和复杂交互。目标是解释机制、运行对应路径、定位变体故障并限定交付声明。

## 原理、场景与边界

先把“翻译内容”和“格式化数据”分开。消息key按业务namespace组织，如catalog.count，而不是把中文整句当永久ID；语言、namespace和版本共同决定加载目标。页面进入时加载所需消息，缺key/加载失败有可观察回退；不要把用户传入的locale直接拼成服务器文件路径。SSR需在当前请求确定语言并把一致的公开消息结果交给hydration，避免服务器英文/客户端阿拉伯语产生首屏不一致。全局只读字典可复用，当前用户语言/私有数据不能跨请求共享。

ICU MessageFormat不是简单字符串替换。plural按目标语言复数类别选择分支，=0是精确匹配，#在plural中代表格式化数值；one不等于所有语言的“数字1”。select按受控枚举选句式，other作为兜底。性别等信息仅在产品确需且用户明确提供时使用，不能从姓名推断，未知值用中性表达。整句由翻译者调整，不能把半句话拼接强迫所有语言遵守中文词序。

本lab真实运行intl-messageformat10.7.18；messages-en/ar是catalog语义的一组消息按语言动态import，尚未实现完整多namespace业务工程。createMessages各自保存加载Promise，失败后删除该Promise便于重试；字典是公开内容，不放秘密。这个库的ICU语法不能直接当成Vue I18n所有版本默认支持的语法，接Nuxt时先核对所选消息引擎、编译与加载策略。

## 最小上下文

代码依赖同点示例的i18n-lab上下文；格式化函数从messages.mjs导入，DOM变量对应index.html/ui.mjs，不是任意浏览器可直接粘贴的独立程序。

~~~js
const format = createMessages()
console.log(await format('en', 'count', { count: 3 })) // 3 files
console.log(await format('ar', 'count', { count: 2 })) // ملفان
~~~

## 移动端对照

Flutter ARB/Intl经验能帮助理解消息ID，但Web还需考虑按路由分包、网络失败和SSR/hydration一致；库语法不能跨引擎直接搬。
