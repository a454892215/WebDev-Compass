# 1.1.1.4 列表：ul、ol、li、dl、dt、dd

> [← 返回 HTML 目录](./README.md) · [知识地图](../../../../knowledge-map/01-foundation-stages-0-2.md)

## 一句话理解

列表用结构表达“集合”“顺序”“术语及其说明”，不只是给每行前面添加一个符号。

## 核心机制与选择

| 关系             | 元素               | 典型场景           |
| ---------------- | ------------------ | ------------------ |
| 顺序不影响意义   | `ul` + `li`        | 功能集合、材料清单 |
| 顺序影响意义     | `ol` + `li`        | 操作步骤、排名     |
| 名称与描述的分组 | `dl` + `dt` / `dd` | 术语解释、产品参数 |

嵌套列表应放进所属 li 内，而不是当作外层 ul 的另一个直接内容项。dl 的一组可以有多个名称或多个说明；不要把它当作只有两列的视觉表格。

## 最小示例

```html
<h2>发布步骤</h2>
<ol>
  <li>检查代码</li>
  <li>
    运行验证
    <ul>
      <li>类型检查</li>
      <li>专项测试</li>
    </ul>
  </li>
  <li>构建发布</li>
</ol>
<dl>
  <dt>DOM</dt>
  <dd>浏览器中的文档对象树。</dd>
  <dt>URL</dt>
  <dd>资源地址。</dd>
</dl>
```

## 实际使用与边界

`ol` 的 start 与 li 的 value 可以表达实际序号，但不要只为视觉效果使用。列表标记和缩进由 CSS 控制，去掉标记不会让数据失去列表关系。

若数据需要按多个字段横纵比较，选择 table；若只是导航集合，可用 nav 包裹 ul。不要依靠手写“1. ”文本维护可自动计算的编号。

## 📱 移动端对照

ListView/LazyColumn/RecyclerView 决定如何渲染大量项目；ul/ol 决定内容的列表语义，两者不在同一个抽象层。大量数据是否虚拟化，是后续性能与交互决策。

## 常见误区

- 多个 p 不一定能代替有关系的列表。
- 不能把 li 当成脱离 ul/ol 的通用卡片标签。
- 顺序列表不是 CSS 自动编号的唯一用途，但步骤关系应优先写成 ol。
