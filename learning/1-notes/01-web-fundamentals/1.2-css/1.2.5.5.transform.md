# 1.2.5.5 动画性能：测量布局、绘制与合成

[返回 CSS 目录](./README.md) · [知识地图](../../../../knowledge-map/01-foundation-stages-0-2.md)

## 学习目标与前置

前置：HTML 元素、属性与基本页面结构；含切换按钮的脚本仅用于观察，不要求此时掌握完整 JavaScript。

学完应能解释此规则、在 DevTools 中找到获胜声明或计算值，并对照内容变化判断是否适用。工程化选修项需区分源码与浏览器产物。

## 一句话理解

选择transform/opacity常能避免布局变化，但是否更快、是否合成，需要真实测量。

## 工作机制与使用规则

1. 改变left/width等可能触发布局，颜色/阴影等通常涉及绘制；transform/opacity更有机会在合成阶段处理。
2. “有机会”不等于保证，图层大小、滤镜、内存和浏览器策略都会影响成本。
3. will-change是提前告知，不是永久加速开关；只在需要的元素和生命周期内使用，避免过多图层。
4. 用Performance录制比较前后，关注长任务和帧稳定性，不拿一次视觉流畅感觉当性能证据。

## 最小代码与阅读顺序

```css
.moving {
  transform: translateX(var(--offset));
}
/* 先测量；确认需要才短期使用 will-change:transform */
```

先读匹配目标与参照条件，再读计算结果。不要把一份截图当作所有内容、浏览器和字号均正确的证据。

## 移动开发经验对照

与减少rebuild/repaint的目标相通，但Web还有布局、paint、composite和资源加载阶段，不能只套移动端帧数经验。

## 常见误区与修正

- transform永远零成本，或所有动画都会自动GPU加速。
- 全站will-change:transform导致内存和合成负担。
