# 1.4.3 从设计稿到可用页面：层级、内容与交互状态

> [返回质量目录](./README.md) · [知识地图](../../../../knowledge-map/01-foundation-stages-0-2.md)

## 学什么，先会什么

已了解 HTML 结构、CSS 字号/间距与简单事件即可。目标是把单张静态设计稿转成有状态、有边界的功能说明；不要求先成为视觉设计师，也不要求手机与桌面采用同一个 UI。

## 一句话理解

设计交付应描述内容优先级和状态变化，开发实现需要保证真实文本、输入和失败条件下仍能完成任务。

## 拆解一张设计稿

先明确用户当前要完成的任务，再识别主要动作、必要信息和次要信息。字号、间距、对齐、颜色和分组服务信息层级，不能把“像素相近”当作唯一验收。

| 需要确认的内容 | 可以问设计/产品的问题                            |
| -------------- | ------------------------------------------------ |
| 文本与数据     | 标题最长多少、能否换行、数字/语言变化怎样展示    |
| 布局           | 哪些内容必须同屏，何时换行或折叠，窄窗口如何操作 |
| 控件           | 这是导航还是动作，键盘顺序与焦点态如何表达       |
| 组件状态       | 初始、加载、成功、空、错误、禁用是否有完整说明   |
| 端侧差异       | 手机软键盘、安全区、触控与桌面键盘/鼠标如何处理  |
| 反馈与恢复     | 错误告诉用户什么，能否重试，是否保留已有输入     |

间距、颜色、字体等重复决策可提取为 CSS 变量或设计 token。先确定语义和布局约束，再统一数值；不要因为图中宽度固定，就把整个页面等比缩小。触控命中区域、焦点可见性与对比度从当前组件开始考虑。

## 状态应覆盖什么

```text
初始 → 加载 → 成功 / 空 / 错误
                  错误 → 重试 → 加载
```

加载状态要阻止不合理重复操作，但不能让用户永远无法取消或退出。成功和空状态分别表达“有结果”和“查询完成但无结果”。错误应提供适合用户理解的说明及可恢复操作，不把完整堆栈、凭据或敏感请求参数直接展示出去。

```html
<section aria-labelledby="results-title" aria-busy="false">
  <h2 id="results-title">学习项目</h2>
  <p role="status">尚未查询。</p>
  <button type="button">加载演示项目</button>
</section>
```

aria-busy 表达区域正在更新，但并不自动添加禁用行为或加载动画。内容更新后复位；焦点通常留在用户正在操作的控件，不因普通状态变化强制跳转。

## 配套实验与验收

[打开设计状态示例](../../../2-examples/01-web-fundamentals/1.4-quality-basics/1.4.3.design-interaction-states-demo.html)。

1. 下拉选择加载/成功/空/错误，逐一观察说明、结果、按钮和 aria-busy 是否匹配。
2. 切到错误，点击“重试示例”，应进入成功状态；这是人工状态演示，不是真实 API 验证。
3. 切换长内容，缩到手机宽度，确认主要操作、标题与说明仍可读。
4. 给一个自己的列表画出状态表，说明每种状态能做什么、焦点在哪里、哪些信息应保留。

## 📱 移动开发对照

已有 Android/Flutter/RN 的 loading/error/empty 状态模型可以复用，但 Web 需要额外考虑文档语义、链接行为、可访问名称、浏览器缩放和可变窗口。桌面和手机可以采用独立 UI，公共数据与状态契约仍可共享。

## 常见误区

- 设计稿只给成功页，异常状态以后再说：实现前至少明确核心状态。
- skeleton 替代全部错误信息：等待与失败应有不同表达。
- 只检查短中文占位：真实长标题、多语言和空值更容易暴露布局缺陷。
- 为了复用强制两端同布局：复用业务/状态并不要求所有交互相同。
