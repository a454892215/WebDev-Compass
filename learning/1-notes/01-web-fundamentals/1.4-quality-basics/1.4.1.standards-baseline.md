# 1.4.1 Web 标准、Baseline 与渐进增强

> [返回质量目录](./README.md) · [知识地图](../../../../knowledge-map/01-foundation-stages-0-2.md)

## 学什么，先会什么

前置是 HTML 文档与基础 CSS。目标是给一个页面写出“支持谁、依赖什么、缺失时怎么办”的说明，而不是背诵所有浏览器版本。完成这项后再使用容器查询、dialog 等能力；阶段 6 的兼容与阶段 12 的自动化测试再深化目标环境验证。

## 一句话理解

标准描述预期行为，浏览器实现和用户环境决定实际行为；先给出可用基础，再用能力检测增强体验。

## 标准、实现和项目目标

| 层面                  | 回答的问题                                     | 不能推出什么                                 |
| --------------------- | ---------------------------------------------- | -------------------------------------------- |
| WHATWG/W3C 规范       | 这个能力应当如何工作                           | 规范存在不等于所有浏览器已实现               |
| MDN 兼容表与 Baseline | 哪些主流浏览器支持、何时互通                   | 不保证所有旧 WebView、嵌入式浏览器或缺陷场景 |
| 项目支持矩阵          | 本产品承诺哪些浏览器、最低版本、设备与辅助技术 | 不能只写“现代浏览器”就假定全部用户都能用     |
| 实际验证              | 在目标环境里关键任务是否可完成                 | 单个 Chrome 通过不代表跨浏览器通过           |

Baseline 的核心浏览器集包括桌面与移动主流浏览器。它区分 Limited、Newly available、Widely available；Widely available 通常表示达到跨核心浏览器互通后经过 30 个月。它是选型线索，不覆盖一切设备、旧系统、WebView、辅助技术或供应商实现缺陷。

业务应先明确最低环境、访问场景与可接受降级。对新能力，检查它是否影响核心任务：布局升级可以退回单列，关键登录能力不支持时则需要可理解的替代流程，不能只隐藏按钮。

## 能力检测怎样用

```css
.cards {
  display: block;
} /* 基础内容一直可读 */
@supports (display: grid) {
  .cards {
    display: grid;
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}
```

```javascript
const canUseGrid =
  typeof CSS !== "undefined" && CSS.supports("display", "grid");
if (canUseGrid) {
  // 可按需要增强；基础 HTML 仍应有内容。
}
```

CSS.supports 和 @supports 主要判断语法/声明是否被支持；返回 true 不证明某个复杂组合没有布局缺陷、性能问题或辅助技术问题。JavaScript API 应检测具体方法，例如 `typeof dialog.showModal === 'function'`，之后仍测试行为。避免仅以 User-Agent 字符串猜测能力。

Polyfill 也不是万能补齐：浏览器渲染、权限、辅助技术或安全机制未必能由脚本等价模拟。需要付出包体与维护成本时，先评估简单回退是否已满足业务。

## 📱 移动开发对照

类似 Android 的能力/系统版本检查，但 Web 用户的浏览器内核、系统版本和嵌入容器可能分离升级。判断 Android 版本不能直接代替检查 WebView 能力，Flutter/RN 的平台适配经验也不能证明浏览器 API 支持。

## 常见误区与验收

- “Baseline 可用就支持全部用户”：仍需项目矩阵，尤其检查旧 WebView。
- “@supports 为真就不用测试”：它不执行完整用户旅程。
- “回退必须视觉完全相同”：核心内容和任务保持可用更重要。
- 验收：写下最少两个目标环境、一个不支持能力、一个基础回退及相应验证方法；能在示例中说明检测结果与行为证据的区别。
