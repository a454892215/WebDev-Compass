# 3.1.5 pnpm workspace：两个包的明确依赖

[章节目录](./README.md) · [知识地图](../../../../knowledge-map/02-engineering-stages-3-5.md)

## 解决什么问题与前置

在同一仓库管理两个相关包，并保持依赖方向可见。

前置：3.1.1、模块导入与包命名。选读，不要求把每个小项目改多包。

## 原理与规则

1. workspace由根pnpm-workspace.yaml声明包范围，子包仍有独立manifest。workspace:*明确要求本地workspace包，避免误从注册表匹配同名外部版本。

2. Monorepo只是代码组织策略，不能自动保证模块边界、版本发布、权限或可复现。pnpm的链接/存储布局也不是安全沙箱。

3. Lerna、Turborepo等可处理发布/任务图与缓存，但本小实验两包不需要这些额外工具。是否采用由实际协作和构建需求决定。

## 最小例子

```javascript
# pnpm-workspace.yaml
packages:
  - packages/*
# app/package.json 的 dependencies: {"@compass/math":"workspace:*"}
```

以上片段用于解释规则；运行上下文与源文件见[本点实验](../../../2-examples/03-engineering/3.1-package-management/3.1.5.monorepo-demo.md)，不要把配置片段粘贴进错误工具或空白Node文件。

## 移动端经验对照

类似多个移动模块显式依赖，但仓库数量、包数量、部署单元不是同一维度。

## 场景与误区

不要因两个项目共用代码就默认必须合仓；也不要依靠未声明的根依赖“碰巧可用”。

## 综合实践关联

评估阅读任务板当前是否需要workspace；如新增共享纯模型包，在副本显式声明依赖方向。

已有能力与副本扩展分开，按阶段综合项目的实际代码判断，不为覆盖知识点强加工具。
