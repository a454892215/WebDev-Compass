# 3.1.4 锁文件：解析图与冻结安装

[章节目录](./README.md) · [知识地图](../../../../knowledge-map/02-engineering-stages-3-5.md)

## 解决什么问题与前置

让同一manifest在团队与CI中安装可审查的依赖图。

前置：3.1.1与3.1.3。

## 原理与规则

1. package-lock.json、yarn.lock、pnpm-lock.yaml分别由对应工具维护，记录解析版本、完整性及依赖关系等。格式与语义不应手工互相改名转换。

2. 冻结安装要求manifest和锁文件一致：pnpm --frozen-lockfile不会悄悄更新锁；不一致应失败，而不是自动重新解析后假称可复现。

3. 锁文件不是离线包仓库，也不保证跨平台完全相同产物；Node、工具版本、可选平台包、脚本和环境仍影响结果。应用通常提交本工具锁文件。

## 最小例子

```bash
pnpm install --frozen-lockfile
# 在临时副本改变依赖声明、不更新锁，再执行同一命令：应失败。
```

以上片段用于解释规则；运行上下文与源文件见[本点实验](../../../2-examples/03-engineering/3.1-package-management/3.1.4.package-lock.json-demo.md)，不要把配置片段粘贴进错误工具或空白Node文件。

## 移动端经验对照

可对照pubspec.lock或依赖锁定，但需要按当前工具和项目类别判断提交策略，不能只复制扩展名。

## 场景与误区

不要为消除冲突直接删锁重装而不检查依赖图变化；也不把有锁等于网络和安装来源安全。

## 实验与独立练习

先冻结安装现有package-lab，再在独立临时副本改变semver版本验证冻结拒绝；复跑脚本不会破坏本仓库锁。

## 综合实践关联

在任务板保持manifest与pnpm锁一致，升级时同时审查锁变化并运行检查。

已有能力与副本扩展分开，按阶段综合项目的实际代码判断，不为覆盖知识点强加工具。
