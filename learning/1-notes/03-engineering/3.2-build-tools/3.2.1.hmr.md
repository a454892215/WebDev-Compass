# 3.2.1 构建工具：转换、模块图与检查边界

[章节目录](./README.md) · [知识地图](../../../../knowledge-map/02-engineering-stages-3-5.md)

## 解决什么问题与前置

浏览器原生ESM之外，为什么还需要开发与生产工具链？

前置：阶段2模块、HTTP资源与JS执行。

## 原理与规则

1. 开发工具解析包导入、转换TypeScript/CSS等资源并维护模块图；生产构建生成适合部署的资源，可能进行代码分割、去除不可达代码和压缩。

2. 转换类型语法与静态类型检查不是同一件事。Vite能处理.ts，但不会替你做完整tsc检查；lint、格式与测试也分别负责不同问题。

3. Vite8实际使用的转换/打包实现以当前版本官方说明为准，不把旧版esbuild/Rollup描述当跨版本永恒原理。Web标准模块与工具内部实现要分开。

## 最小例子

```bash
pnpm typecheck
pnpm bundle-only
pnpm build
# bundle-only只打包；build显式先typecheck再打包。
```

以上片段用于解释规则；运行上下文与源文件见[本点实验](../../../2-examples/03-engineering/3.2-build-tools/3.2.1.hmr-demo.md)，不要把配置片段粘贴进错误工具或空白Node文件。

## 移动端经验对照

可对照移动编译/资源处理，但Web构建还需处理浏览器URL、静态资源和模块加载，不能仅当生成可执行安装包。

## 场景与误区

“页面能跑”或“vite build成功”不能证明类型、逻辑和业务正确。

## 实验与独立练习

在临时副本增加const count: number = "wrong"，对比Vite bundle-only与tsc；错误只在类型检查时被拒绝，副本随后清理。

## 综合实践关联

审查任务板的typecheck/build/lint/test命令各自职责，并在副本注入类型错误验证门禁。

已有能力与副本扩展分开，按阶段综合项目的实际代码判断，不为覆盖知识点强加工具。

## 官方依据

核对日期：2026-11-24。先读[Modern Web Guidance Performance](https://developer.chrome.com/docs/modern-web-guidance/guides/performance/performance)，采用显式模块边界、按需加载与可验证资源；包管理/构建器细节没有覆盖全部的MWG专门条目，继续核对[对应官方正文](https://vite.dev/guide/features#typescript)。Vite8/Node26等实际版本以实验manifest与运行报告为准，不把最新页面示例无条件套到旧版本。
