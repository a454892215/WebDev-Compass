# 3.4.5 Conventional Commits：写清变更类型、范围与破坏性变化

前置：阶段2 JavaScript 与阶段3.1–3.3 包管理、脚本、TypeScript。目标：能解释本节机制、运行真实检查并定位一种失败。组件最小概念在3.5.3解释，完整 Vue 3 留到阶段4。

## 解决的问题与机制

约定以 type(scope可选)!可选: 描述 开头；正文补充原因，footer 可声明 BREAKING CHANGE。fix、feat 常用于版本工具语义，其余类型按团队约定。! 或 BREAKING CHANGE 表示破坏性契约变化，不能只依赖标题猜。

## 最小例子

以下片段对应完整共享实验工程；依赖、import 和脚本以其源文件为准，不作为脱离上下文的完整工程。

```text
fix(parser): 拒绝空任务标题

避免导入后出现不可辨认的任务。

Refs: #42
```

## 运行与观察

verify:tools 检查两个合法教学标题和一个无结构标题；使用的是项目标题子集正则，并非完整规范解析器。真实规范包括正文/footer，多行内容不能靠这一个正则完全验证。

## 使用场景与误区

适合变更日志和回溯。标题格式不会保证业务质量、测试充分或自动发布安全；语义版本和发布仍需团队规则、兼容分析与授权。本仓库默认中文描述，保留英文 type/scope。

## 移动端经验对照

与 Android/Flutter 项目使用相同 Git 提交约定；没有平台专属技术依赖。
