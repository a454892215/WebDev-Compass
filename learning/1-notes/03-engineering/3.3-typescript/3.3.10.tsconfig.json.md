# 3.3.10 strict、target、module与paths

[章节目录](./README.md) · [知识地图](../../../../knowledge-map/02-engineering-stages-3-5.md)

## 前置与目标

模块与编译/运行区别；先完成3.3.9。

## 原理与选择

strict启用一组严格检查，但并非所有安全选项；noUncheckedIndexedAccess、exactOptionalPropertyTypes等按需求显式选择。本例数组索引显式处理undefined。

target决定输出语法级别；lib声明可用API的类型，不会安装polyfill。module/moduleResolution要匹配Node或打包器宿主，不能把NodeNext配置无脑复制给Vite。

paths帮助类型检查器查找导入，不自动重写输出import。Vite alias或其他运行时解析要同步配置；本例真实验证tsc成功但Node无法找到@lab/lib。

## 最小例子

```typescript
// tsconfig.json局部：普通Vite工程应按对应宿主另选moduleResolution
// {"compilerOptions":{"strict":true,"noUncheckedIndexedAccess":true,"target":"ES2022"}}
const values: string[] = [];
const first: string | undefined = values[0];
console.log(first ?? "空列表");
```

此处是本节机制片段；完整可编译源和反例见[运行实验](../../../2-examples/03-engineering/3.3-typescript/3.3.10.tsconfig.json-demo.md)。类型检查与运行输出分别观察，不能把注释当编译器证据。

## 场景、边界与误区

修改配置后要运行tsc与真实构建/运行。单独传文件可能不按预期读取项目tsconfig；使用tsc -p。版本升级的废弃选项需查对应版本文档。

## 移动开发对照

类似Gradle/编译器参数分工，但TS目标语法与浏览器API可用性必须分开；不能把target视为Android minSdk。
