# 11.3.5 回滚：不可变产物、旧资源保留与数据库兼容

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

回滚是恢复可用服务，不一定是Git revert重新构建。应保留可识别的已验证产物/配置和切换方式；事故中重建旧源码可能拉到新依赖或花费不可控时间。前端HTML、hash资源、SSR程序、运行配置、API/数据库是不同层，需要分别考虑兼容和恢复证据。

hash资源应与内容绑定并可长期缓存；HTML/manifest选择当前版本。切回旧HTML时对应旧hash必须仍存在，已打开的新页面可能继续请求新hash，因此不能回退时立刻删除新资源。CDN purge、服务工作线程缓存和页面会话会形成多个版本并存，不能把单个文件rename说成全网瞬间原子切换。

SSR要切完整输出和对应配置/依赖运行环境，健康检查、代表性业务检查、流量切换与连接排空配合；不是只拷贝.output/server某个JS。lab创建两套真实hash脚本和manifest，在同一临时目录rename current.next→current.json，切candidate后恢复stable，验证两个资源保留和旧脚本可读取。该实验是本机文件指针模型，未启动两套SSR进程、CDN或真实数据库。

数据库不可机械反向迁移。先新增兼容字段/双读写或适配，部署新旧都能工作的程序，待旧版本不再访问再收缩；删除列、重写数据后应用回退可能不再安全。事件和后台任务已产生的副作用也需补偿/修复方案。回退之前确认数据契约、配置开关、队列、密钥版本与回滚目标，不把“页面恢复200”当所有业务已恢复。

```js
import { rollbackDrill } from "./rollback.mjs";
console.log(await rollbackDrill());
// initial stable → candidate → restored stable
// oldAssetRetained/newAssetRetained/restoredAssetReadable 均为true
// finally删除整个系统临时目录
```

## 场景、误区与移动端对照

删除新hash造成仍开着页面404；回滚源码而没有保留旧产物；数据库down迁移当万能恢复；健康200却业务失败。

移动端多版本长期共存使后端兼容成为常识；Web虽然可快切HTML，旧标签/缓存/Worker同样制造多版本并存，仍需保留兼容窗口和资源。

## 实践与边界

运行pnpm rollback或第四组pnpm test；查看initial/candidate/restored和两hash保留/readable。临时目录finally清理。未进行CDN purge、真实SSR服务切换、数据库迁移或灾备恢复。
