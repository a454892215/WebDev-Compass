# 11.3.4 PR预览环境：环境隔离、秘密边界与销毁

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

Preview为某个提交或PR生成独立可访问版本，让评审看到具体变更。它与生产灰度不同：预览通常给评审/测试，不应接生产用户数据或复用高权限生产凭据。先确定命名/URL/认证/索引策略、数据来源、生命周期和配额，再选Vercel/Netlify/自建容器等宿主。平台能力、套餐和审批规则随时间变化，按官方文档与实际仓库核实。

每个预览必须能追溯commit/release，明确构建产物、运行模式（静态还是SSR）和配置。Nuxt Node服务器使用完整.output，不是把服务器目录当静态文件上传。公开的NUXT_PUBLIC_*等配置不能保密；预览用隔离的合成数据库/受限账号或mock。noindex不是访问控制，私有预览需要真实鉴权，URL难猜不是保护。

GitHub环境可以关联deployment URL、环境secret和审批/分支规则，但“YAML写environment名字”不代表所有保护已配置。PR来自不可信代码，不能用pull_request_target加高权限秘密去checkout并执行外来提交；生产令牌不得交给可改构建脚本的未审核PR。审查后部署也要最小权限，prefer短期身份而非随意长期令牌。

保留按PR/提交独立的环境，避免后一次部署覆盖正在评审的地址；关闭PR时销毁服务/临时数据并保留必要审计。并发取消旧构建、失败状态和过期URL要清楚。本节为官方文档/契约观察，未创建远程环境、发布网站、配置GitHub审批或使用任何secret。

```yaml
# 结构示意，需在目标仓库接入平台后才可用；本轮未执行
jobs:
  deploy_reviewed_preview:
    environment:
      name: reviewed-preview
      url: https://preview.example.invalid/pr-123
    permissions:
      contents: read
    # 省略runner、构建和平台部署步骤，不能直接当完整workflow。
```

## 场景、误区与移动端对照

预览连生产库；将noindex当认证；硬编码示例URL却称已部署；假设PR自动有secret；关闭PR不清理成本。

类似移动端分支测试包，但Web链接可能被搜索/分享且SSR在远端持续运行；仍需访问控制、后端数据隔离和销毁策略，不能只管理一个安装包。

## 实践与边界

类型：官方部署契约观察。打开上述GitHub环境与Nuxt部署说明，在纸面填写PR123/commit/release/产物模式/环境URL/鉴权/合成数据/关闭清理/负责人；本lab不发远程请求，不声称生成了可访问预览。
