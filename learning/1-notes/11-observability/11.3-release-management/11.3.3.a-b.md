# 11.3.3 A/B实验：分配、可见曝光、转化与污染控制

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

A/B以预先定义的假设、分配单位、主要指标和分析方法比较体验；Canary主要控制发布风险。稳定分组是二者的共用能力，但把50%功能开关打开并不自动构成可信实验。先写清实验版本、单位是用户/会话还是设备、主指标与保护指标、观察期和停止策略；反复偷看直到显著、同时改多变量、跨实验干扰都会损害结论。

分配不等于曝光：服务端求得A/B值时用户可能没看到卡片。SDK的impression事件有时表示一次isEnabled/getVariant评估，也未必是人眼看到。要根据实验定义选择“已渲染/进入视口/点击后”等可实现标准并如实命名。lab点击显示后，以IntersectionObserver的50%交叉记录近似可见；未验证遮挡、后台注意力，也不保证人确实阅读。

归因需要把experiment+version+variant与定义好的单位关联，转化应能追溯到该单位合法曝光。lab只允许三个公开合成主体，服务端重新计算分配，错误variant拒绝；先曝光后转化，Set按单位/版本/变体去重。重复刷新或重试不会重复unique计数，但整个内存进程重启清空，无跨实例事务。事件可伪造，因此真实订单应以业务后端事件归因，不能靠浏览器按钮证明成交。

稳定ID也有隐私成本：最小化、目的限定、保留期限与适用的用户选择仍需评估；“哈希后就匿名”不成立。不采集邮箱/完整URL/令牌作分组或指标标签。匿名到登录的单位合并、跨设备和迟到转化要有规则，不能偷偷换组再把数据混合。

```js
import { assign, createLedger } from "./core.mjs";
const subject = "fixture-001",
  variant = assign(subject),
  ledger = createLedger();
console.log(ledger.event(subject, variant, "conversion")); // false：未曝光
ledger.event(subject, variant, "exposure");
ledger.event(subject, variant, "exposure");
console.log(ledger.snapshot().exposed); // 1：重复请求去重
```

## 场景、误区与移动端对照

渲染前就当曝光；同一人每次换组；把分母用PV、分子用unique用户；没有归因窗口/实验版本；把两三个fixture推断成显著提升。

移动分析SDK常有屏幕曝光回调，Web路由、DOM渲染与视口可见是不同事件；Nuxt SSR完成也不代表用户看到。两端都应明确单位/版本/归因，不把生命周期回调当真实注意力。

## 实践与边界

运行node server.mjs，读分配后查看exposed仍0；显示卡片进入视口后为1，重复显示仍1，转化为1。pnpm verify自动用390/1440视口复验，并用HTTP验证无曝光转化409/额外字段400。
