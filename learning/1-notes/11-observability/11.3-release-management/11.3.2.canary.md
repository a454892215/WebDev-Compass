# 11.3.2 Canary灰度：稳定群组、分版本指标与停止条件

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

灰度是把变更先交给部分合格流量并在限定观察窗口内评估，再决定扩量、暂停或回退。Feature Flag可以在同一部署中灰度某条路径；按实例/地域路由不同产物则是部署灰度，两者可组合但不是同一层。总错误率可能稀释小群组的新缺陷，至少按release/变体比较同口径分母、错误率和延迟，同时看业务与资源保护指标。

稳定分桶由“稳定主体+分组/版本”决定。在lab使用SHA-256后取0–9999，百分比p对应bucket < p*100，0%必关闭、100%全开。固定group和subject时扩量保留已进入群组，回退相同比例返回同一集合。Unleash官方使用MurmurHash/其规范化规则，本算法只说明机制，不兼容其平台分桶。不能每渲染Math.random；否则同一用户跨刷新、SSR与客户端会抖动。缺稳定主体时应选择明确默认或建立合适匿名会话，不偷偷做指纹。

白名单与区域在评估前需界定可信来源。lab的CN/DE是固定合成上下文，不采集位置，也不把URL自报国家用于真实资格判断；地域规则不一定产生代表性样本。region不合格时即使allow也拒绝；这是本例优先级，应写清而不是当作所有平台的唯一语义。

先规定最小样本/观察时长、控制组、停止和回退负责人，再放量。零样本和一个成功请求不能证明安全；短窗口新旧群组流量结构不同也会误导。开关关闭不回滚已写数据，后端契约和数据库兼容仍需单独设计。

import { baseline, evaluate } from "./core.mjs";
const context = { subject: "fixture-002", region: "CN" };

  console.log(percent, evaluate({ ...baseline, percent }, context).enabled);

## 场景、误区与移动端对照

只看全站平均；把2个请求的0错误叫验证通过；同时改salt又扩量却声称旧群组稳定；把匿名Cookie当真实权限。

移动端商店分批安装通常不能立即召回二进制，Web可切路由/HTML但缓存资源和已打开页面仍在；两者都需要后端兼容与停止条件，Web回退也不是瞬间清除所有旧会话。

## 实践与边界

运行pnpm test第一组，逐个fixture扫0–100百分比，确认false只会变true、不逆转；0/100、区域、白名单、kill分别测试。三个fixture仅验证算法性质，不证明真实人口恰有25%或流量代表性。
