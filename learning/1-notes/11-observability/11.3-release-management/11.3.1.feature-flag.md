# 11.3.1 Feature Flag与Kill Switch：配置开关、失效默认值与服务端边界

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

发布代码和开放功能是两个决定。Feature Flag让同一已部署版本按配置选择行为；Kill Switch是在故障时优先关闭高风险路径的控制，不负责恢复被破坏的数据，也不等于应用授权。LaunchDarkly、Unleash等提供配置、SDK缓存和审计，自研只适合边界清楚的小需求；本例是独立教学评估器，不冒充任一平台SDK。

先定义名称/所有者/用途/过期清理时间/默认值，再定义配置来源和不可用策略。对可选新功能通常保守回旧路径；对支付等关键控制要由业务决定安全失败方式，不能一概认为“关闭”总安全。远程配置应有版本、刷新、最大陈旧时间和审计，客户端初始化前也必须有稳定默认。本lab没有远程连接或TTL，null/无效配置只返回关闭；不能据此宣称已验证配置断网缓存。

服务端拥有配置。evaluate依次检查kill/总开关、配置合法性、主体与区域资格、白名单、百分比，kill高于白名单。开关分流不是访问控制：即使UI隐藏，API仍需验证真实身份和资源权限。浏览器SDK可用的client key/已计算结果不等于可公开服务端密钥、完整用户规则或管理员权限。开关移除要包含旧代码清理与监控，否则组合数量和技术债随开关增加。

最小可运行上下文：在release-lab内运行下面模块，或查看tests/core.test.mjs同一实现。

```js
import { baseline, evaluate } from "./core.mjs";
const context = { subject: "fixture-001", region: "CN" };
console.log(
  evaluate(
    { ...baseline, percent: 100, kill: true, allow: ["fixture-001"] },
    context,
  ),
);
// { enabled: false, reason: 'off' }
```

## 场景、误区与移动端对照

把enabled=true等同有权限；kill之后只隐藏按钮却仍调用危险API；平台不可用时每个组件用不同默认；忘记删除临时开关。

类似移动端远程配置，但Web SSR先在服务器求值、浏览器再接管；不能让两边各随机决定，更不能在SSR模块里保存全局currentUser。客户端结果可被改，安全边界仍在服务端。

## 实践与边界

运行pnpm test第一、二组；读core.mjs evaluate的优先级。把percent设100、allow加入fixture-001，再kill=true，结果仍关闭；传null、percent=101或缺上下文也关闭。没有连接远程平台。
