# 11.3.6 事件响应：先恢复、再定位，形成可执行Runbook与复盘

前置：阶段5请求/身份边界、阶段7部署回滚、阶段8SSR状态；本组先11.3.1→11.3.2→11.3.3，预览/回滚/响应再形成交付闭环。

## 问题与原理

告警是线索，不等于已定位根因。响应先确认用户影响、范围、开始时间和当前变更，建立事件记录与负责人；优先选择低风险止损（关闭新功能、暂停扩量、切回已验证产物），同时保留诊断信息。不能看到一个异常就无差别重启或让多人同时改配置。

小团队也应明确指挥/操作/沟通角色，可由少数人兼任，但每次操作要有owner和时间线。Runbook给触发条件、所需权限、检查命令、判据、止损/回退、升级条件和恢复验证，不只是“查看日志”。记录使用脱敏traceId/release/指标窗口，避免复制Cookie、token、完整用户文本。跨团队状态更新按真实影响/已知/未知/下次更新时间表达，不编造恢复ETA。

本组提供可重复的桌面推演：candidate推荐模块故障→停止扩量→kill优先关闭→本地manifest恢复stable→检查业务与资源→关闭事件。脚本只实测开关和文件回退机制；“谁值班/谁对外沟通/5分钟收到告警”是练习角色和虚构时间线，不是真实生产事故或真实通知发送。

Postmortem应无责地解释触发、促成条件、发现与缓解过程、用户影响、哪些措施有效/无效，以及可跟踪改进。不是把“工程师粗心”当根因，也不是把无证据猜测写成事实。行动项要owner、期限、验收证据和优先级；并非所有事件都需要巨型报告。复盘后更新监测、测试或流程，再演练验证，才形成闭环。

```bash
# 在release-lab目录执行，均为本地机制
pnpm test
pnpm rollback
# 桌面推演角色/时间线见incident-drill.md；未发送任何告警/消息。
```

## 场景、误区与移动端对照

多人无记录同时改；先证明根因才止损；恢复后不核对业务；复盘只责备人；虚构“告警已通知值班人”。

类似移动崩溃事故，但Web可立即切开关/SSR产物；服务端和浏览器版本可能并存，恢复验证要包含旧会话/资源，不只看新安装或新页面。

## 实践与边界

先读incident-drill.md，分别扮演指挥/操作/沟通，按检查点运行pnpm test和pnpm rollback，填自己实际开始/结束和输出。模板时间是相对推演节点，禁止填成真实事故已发生。
