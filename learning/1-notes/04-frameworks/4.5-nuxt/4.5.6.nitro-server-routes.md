# 4.5.6 Nitro最小API：输入校验与业务后端边界

## 前置与目标

先完成阶段3工程与TypeScript；4.4需CSS布局/层叠基础，4.5需Vue组件、组合式API与路由。能解释本点机制、运行对应实验并定位一种失败。4.4可按需要选读，完整SEO与生产部署分别留阶段6、7。

## 解决什么问题

在Nuxt中提供少量请求适配或聚合能力，理解服务端运行位置与真正的信任边界。

## 原理与选择

server/api文件按路由和方法约定注册，处理器用defineEventHandler，读取路径/查询/请求体后按业务契约校验。TypeScript不会在运行时自动检查用户JSON。响应数据应只包含允许公开字段；输入错误返回合适4xx，未找到与服务故障分开。BFF可聚合已有服务，但不因叫BFF就能省去授权、超时、审计和下游边界。

## 最小机制片段

```typescript
// 独立机制示例：server/api/check.post.ts
export default defineEventHandler(async (event) => {
  const body: unknown = await readBody(event)
  if (typeof body !== "object" || body === null ||
      !("title" in body) || typeof body.title !== "string" ||
      !body.title.trim()) {
    throw createError({ statusCode: 400, statusMessage: "Invalid title" })
  }
  return { accepted: true }
})
```

片段只解释当前机制；不是可直接替代完整工程的文件。变量、依赖与运行上下文见[代码操作卡](../../../2-examples/04-frameworks/4.5-nuxt/4.5.6.nitro-server-routes-demo.md)及其源码链接。

## 场景、边界与常见误区

示例仅校验不持久化；没有账号和受保护资源，不能称生产授权已完成。如果真实端点涉及用户数据，必须在服务端根据已验证身份检查资源权限；客户端路由守卫不能替代。server/代码不应导入Vue app-only composable，公共纯类型/校验可放shared。

## 移动端经验对照

复用移动端的分层、状态所有者和失败恢复经验；Nuxt还要分别考虑服务端请求、浏览器应用与hydration，不能按移动进程生命周期直接等同。
