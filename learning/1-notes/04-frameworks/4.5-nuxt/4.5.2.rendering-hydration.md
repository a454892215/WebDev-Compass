# 4.5.2 CSR、SSR、SSG与hydration：同一组件的不同运行时机

## 前置与目标

先完成阶段3工程与TypeScript；4.4需CSS布局/层叠基础，4.5需Vue组件、组合式API与路由。能解释本点机制、运行对应实验并定位一种失败。4.4可按需要选读，完整SEO与生产部署分别留阶段6、7。

## 解决什么问题

解释首屏内容从哪里来、为什么Vue代码可能运行两遍，以及哪些代码不能直接访问浏览器。

## 原理与选择

SSR在请求时生成HTML，浏览器收到后hydration接管事件；后续站内导航通常在客户端进行。CSR的初始HTML通常是壳，内容依赖客户端JS。SSG在构建/预渲染时生成静态内容，之后是否更新取决于重新生成等策略。主工程默认build保留动态SSR；独立generate在静态输出里保留明确路径，只作只读对照，查询条件和POST不会自动获得服务端执行能力。它们不是三种不同语法，Nuxt可以按routeRules混合。确定性初始值与payload可使服务端/客户端输出一致。

## 最小机制片段

```typescript
// nuxt.config.ts中的局部策略示意
export default defineNuxtConfig({
  routeRules: {
    "/client-demo": { ssr: false },
    // 预渲染由独立generate脚本启用，不改默认SSR验证。
  },
})
// 完整配置与COMPASS_PRERENDER条件见综合工程；浏览器专属代码放正确环境。
```

片段只解释当前机制；不是可直接替代完整工程的文件。变量、依赖与运行上下文见[代码操作卡](../../../2-examples/04-frameworks/4.5-nuxt/4.5.2.rendering-hydration-demo.md)及其源码链接。

## 场景、边界与常见误区

onMounted不在SSR运行；ClientOnly只适用于确实客户端专属内容，不是掩盖所有hydration问题的通用补丁。服务端和客户端的随机数、当前时间、无效HTML和浏览器存储都可能造成初始差异。不要在不同HTML字符串中搜索单词就断言hydration正确，还需实际浏览器检查。

## 移动端经验对照

复用移动端的分层、状态所有者和失败恢复经验；Nuxt还要分别考虑服务端请求、浏览器应用与hydration，不能按移动进程生命周期直接等同。
