# 4.5.4 Nuxt状态：组件、本应用与SSR请求隔离

## 前置与目标

先完成阶段3工程与TypeScript；4.4需CSS布局/层叠基础，4.5需Vue组件、组合式API与路由。能解释本点机制、运行对应实验并定位一种失败。4.4可按需要选读，完整SEO与生产部署分别留阶段6、7。

## 解决什么问题

分清状态应该共享给谁，避免把浏览器单个应用实例的直觉误套到服务端进程。

## 原理与选择

组件内部ref适合局部交互；useState用key在当前Nuxt应用上下文共享，并通过payload衔接SSR与客户端。服务端同一进程可能处理多个请求，所以模块顶层可变ref/数组/对象可能被不同请求共用。每请求状态放setup/composable的正确上下文初始化；useState的值应适合序列化，不能把函数、连接或类实例当业务payload。Pinia需要SSR集成，不能直接复用一个进程级store实例。

## 最小机制片段

```typescript
// app/composables/useReadingList.ts中的机制示意
export const useReadingList = () => {
  const ids = useState<string[]>("reading-list", () => [])
  return { ids }
}
// 反例：模块顶层 export const ids = ref<string[]>([])
// 在SSR进程中可能跨请求共享，不能作为用户级状态。
```

片段只解释当前机制；不是可直接替代完整工程的文件。变量、依赖与运行上下文见[代码操作卡](../../../2-examples/04-frameworks/4.5-nuxt/4.5.4.state-request-boundaries-demo.md)及其源码链接。

## 场景、边界与常见误区

useState不是数据库，不提供跨设备持久化；浏览器刷新后的结果取决于初始化或另设存储。请求隔离也不自动解决CDN缓存、后端授权或server全局缓存泄漏。示例isolation的query seed只证明公开输入的请求隔离，不是认证身份。

## 移动端经验对照

复用移动端的分层、状态所有者和失败恢复经验；Nuxt还要分别考虑服务端请求、浏览器应用与hydration，不能按移动进程生命周期直接等同。
