# 4.5.5 runtimeConfig：公开配置、服务端秘密与运行时覆盖

## 前置与目标

先完成阶段3工程与TypeScript；4.4需CSS布局/层叠基础，4.5需Vue组件、组合式API与路由。能解释本点机制、运行对应实验并定位一种失败。4.4可按需要选读，完整SEO与生产部署分别留阶段6、7。

## 解决什么问题

让同一构建按部署环境取配置，同时避免把私有值送进浏览器。

## 原理与选择

在nuxt.config声明runtimeConfig结构，public下字段进入客户端可见范围，其他自定义字段仅服务端读取。匹配的NUXT_环境变量可在运行时覆盖结构对应键。开发/build/generate会读取.env，但运行构建后的Node服务不会自动读取项目.env；托管环境应实际注入变量。静态站点没有同样的每请求Node运行配置通道，需要重新生成或设计公开配置加载机制。

## 最小机制片段

```typescript
// 结构示例，综合工程字段名请查nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    privateDemoLabel: "server-only-demo", // 公开的教学占位，不是真实秘密
    public: { courseLabel: "Vue 3 与 Nuxt 学习站" },
  },
})
// server handler内: const config = useRuntimeConfig(event)
// 浏览器只消费config.public；不返回privateDemoLabel。
```

片段只解释当前机制；不是可直接替代完整工程的文件。变量、依赖与运行上下文见[代码操作卡](../../../2-examples/04-frameworks/4.5-nuxt/4.5.5.runtime-config-demo.md)及其源码链接。

## 场景、边界与常见误区

public不是加密、客户端构建配置不是秘密存储。把process.env.OTHER_NAME读成默认值可能只在构建时生效；优先用对应NUXT_变量。私有字段也可被错误的API返回或日志泄漏，字段位置不是完整安全证明。只用虚构演示值检验输出，不需要真实凭据。工程的server-only-demo是可公开的教学占位；真实秘密应保留空默认值并在部署环境注入，而不写入源码。

## 移动端经验对照

复用移动端的分层、状态所有者和失败恢复经验；Nuxt还要分别考虑服务端请求、浏览器应用与hydration，不能按移动进程生命周期直接等同。
