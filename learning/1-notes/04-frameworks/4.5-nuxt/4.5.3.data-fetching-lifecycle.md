# 4.5.3 useFetch/useAsyncData：payload、状态、key与取消

## 前置与目标

先完成阶段3工程与TypeScript；4.4需CSS布局/层叠基础，4.5需Vue组件、组合式API与路由。能解释本点机制、运行对应实验并定位一种失败。4.4可按需要选读，完整SEO与生产部署分别留阶段6、7。

## 解决什么问题

让SSR首屏和客户端导航共享正确的数据结果，同时区分读取、刷新、取消与用户提交。

## 原理与选择

useFetch封装常见HTTP读取，useAsyncData承接一般异步handler；它们把服务端结果送入payload供hydration复用。单独在setup调用$fetch通常没有这层复用，可能两端重复请求。data/status/error是ref；status区分idle/pending/success/error。handler应返回可复用的确定结果，不能返回undefined/null造成预期外重新获取。相同key共享状态，handler、deep、transform、pick、getCachedData和default等选项需按官方要求一致。

## 最小机制片段

```typescript
// Nuxt上下文中的独立机制片段，API协议以综合项目为准
const route = useRoute()
const key = computed(() => `resource:${String(route.params.id)}`)
const { data, status, error, refresh } = await useAsyncData(
  key,
  (_app, { signal }) => $fetch(`/api/resources/${encodeURIComponent(String(route.params.id))}`, { signal }),
)
// 用户提交时在事件里await $fetch(..., { method: "POST", body })，另行处理提交失败。
```

片段只解释当前机制；不是可直接替代完整工程的文件。变量、依赖与运行上下文见[代码操作卡](../../../2-examples/04-frameworks/4.5-nuxt/4.5.3.data-fetching-lifecycle-demo.md)及其源码链接。

## 场景、边界与常见误区

相同key并不等同跨用户全局缓存；响应式URL/查询可触发重取，数据身份必须正确。当前Nuxt4.7的handler提供signal，应传给真正支持取消的下层；dedupe:cancel不代表远端业务一定没执行。POST取消后结果可能不确定，幂等与授权另由后端契约解决。错误、空列表与加载不能混为一谈。

## 移动端经验对照

复用移动端的分层、状态所有者和失败恢复经验；Nuxt还要分别考虑服务端请求、浏览器应用与hydration，不能按移动进程生命周期直接等同。
