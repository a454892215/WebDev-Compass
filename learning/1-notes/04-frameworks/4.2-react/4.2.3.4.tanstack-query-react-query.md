# 4.2.3.4 TanStack Query：服务端缓存、失效与乐观更新

**React选修**。前置为阶段1 JavaScript/DOM与阶段3 TypeScript/模块/测试；不阻塞Vue 3 + Nuxt主线。目标：能解释本节机制，完成一个变体并定位指定故障。

## 解决什么问题与原理

Query用queryKey标识缓存内容，queryFn返回Promise。key应包含影响结果的输入，例如用户范围和筛选；不同查询共用同一key会污染结果。

staleTime描述新鲜度，gcTime描述无观察者缓存保留，二者不同。invalidateQueries标记匹配缓存失效，活跃查询可按选项触发重新获取；重试需要结合幂等和错误类型。

乐观更新通常先取消冲突查询、保存旧值、临时更新、失败回滚、完成后失效；本例直接操作QueryClient证明缓存与回滚机制，不冒充完整mutation并发协调。

## 最小例子

```tsx
const old=client.getQueryData(["tasks",userId])
client.setQueryData(["tasks",userId],optimistic)
// 出错时恢复old；最终invalidateQueries明确失效
```

## 操作、场景与边界

真实QueryClient测试相同key新鲜缓存只调用queryFn一次，保存/恢复旧值后显式失效，再取发生第二次调用。无真实网络/乐观mutation UI。

远程缓存和纯UI状态职责不同。

新增受控失败实验：optimisticAppend先取消冲突查询、保存旧值并写临时数据，save Promise失败时恢复快照，最后失效；另用retry:1/retryDelay:0验证一次重试后恢复。仍未实现React useMutation并发UI或真实服务端。
