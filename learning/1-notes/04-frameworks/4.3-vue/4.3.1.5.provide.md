# 4.3.1.5 Vue依赖注入：provide/inject的作用域与类型

## 前置与目标

props/事件、ref与TS Symbol/接口。

目标：能解释本节机制，运行对应实验，独立定位下述故障并说明边界。

## 解决什么问题与原理

provide在祖先setup或app层提供依赖，inject沿组件祖先链选择最近匹配提供者，解决深层逐级透传。它依赖组件树作用域，不是按文件目录搜索，也不是进程级Service Locator。

字符串键可能冲突，TypeScript可用InjectionKey<T>与Symbol共享契约。键必须是同一个Symbol实例；各文件各造一个同名Symbol不会相等。inject可能没有提供者，要给合理默认或明确失败。

直接提供普通值只是该值；提供ref保留响应连接，提供readonly(ref)+动作可让修改集中在提供者。readonly是约束数据流而非防攻击措施。SSR应用实例/请求边界需由框架创建，不能把用户状态放模块全局再provide。

## 最小例子

```typescript
// context.ts
import type { InjectionKey, Ref } from 'vue'
export const key: InjectionKey<Readonly<Ref<string>>> = Symbol('theme')
// 父setup：provide(key, readonly(themeRef))
// 子setup：const theme = inject(key); if (!theme) throw new Error('缺少提供者')
```

片段用于解释本节规则；标注为setup或模板的代码需放进对应SFC。完整导入、类型与运行入口见[示例操作卡](../../../2-examples/04-frameworks/4.3-vue/4.3.1.5.provide-demo.md)。

## 运行与观察

App提供readonly主题ref和toggle动作，ThemeBadge注入并切换；VTU提供同一Symbol，点击后文字由light变dark，未引入全局单例。

## 场景、边界与移动开发对照

可类比树作用域依赖传递，但不能把移动进程级容器原样放到SSR；真正共享范围由应用/请求决定。

实验只验证Vue组件树注入，不证明服务端请求隔离；该项在Nuxt综合工程另验。
