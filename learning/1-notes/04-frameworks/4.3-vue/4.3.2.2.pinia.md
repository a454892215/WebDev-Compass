# 4.3.2.2 Pinia：state、getters、actions与实例边界

## 前置与目标

响应式与组件契约，先判断局部状态能否满足需求。

目标：能解释本节机制，运行对应实验，独立定位下述故障并说明边界。

## 解决什么问题与原理

Pinia为跨组件的业务状态提供store。defineStore声明如何取得store，真正状态属于某个Pinia实例；Option Store中的state用工厂返回对象，getters是派生状态，actions组织同步/异步修改。不同组件在同一Pinia读同名store会共享，不同Pinia实例应隔离。

直接解构store上的响应属性会丢失与原属性的连接，storeToRefs保留state/getter的ref；action可直接解构或调用，保持各自实际契约。Setup Store要返回需要的状态，不能故意藏状态再期待SSR/devtools正常序列化。

全局状态不等于永久存储，更不等于服务端数据缓存和认证权威。不要把每个input草稿都塞进store；区分组件状态、URL、服务端获取结果和跨页面业务状态。SSR按应用/请求创建Pinia并使用框架适配，不能在模块顶层握住一个用户store跨请求复用。

## 最小例子

```typescript
import { defineStore } from 'pinia'
export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: { double: state => state.count * 2 },
  actions: { increment() { this.count++ } }
})
```

## 场景、边界与移动开发对照

与共享业务状态容器目标类似，但SSR隔离和序列化属于Web运行边界；Pinia不是移动进程单例的原样替代。

lab使用Pinia4.1.0，只有内存状态；无持久化插件、真实会话或并发HTTP请求隔离结论。
