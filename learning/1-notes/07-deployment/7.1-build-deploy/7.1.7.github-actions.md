# 7.1.7 GitHub Actions：验证门禁、产物和受控发布

前置：阶段3构建/类型/测试、阶段4 Nuxt与阶段6缓存/安全；本点聚焦首次生产交付。先说明产物/请求如何流转，再操作，不能把开发服务器当生产部署。

## 解决什么问题与原理

CI在隔离runner重建并验证，CD将已验证产物推广到目标。先按锁文件安装、类型/规范/测试/构建，失败不发布。缓存依赖提升速度但不是可发布构建，不能用缓存命中替代校验。一次验证后的产物应有提交/摘要/profile，避免部署时悄悄重建不同内容。

## 选择、边界与误区

工作流遵循最小权限、受保护环境和可信分支；不要给不可信PR代码生产凭据，尤其不把pull_request_target当普通PR构建。第三方Action固定完整审核SHA，定期升级；SHA固定降低漂移但不替代审阅。发布并发控制防止旧流水线覆盖新版本，失败有明确回滚入口。

## 最小观察

查看templates/quality.yml.example：固定官方Action SHA、contents:read、pnpm11.4锁文件、主工程门禁和三profile构建；模板不在.github/workflows，未推送/运行真实GitHub任务，也没有自动发布凭据。

完整代码与命令见[发布lab](../../../2-examples/07-deployment/7.1-build-deploy/release-lab/README.md)。平台、Docker、远端CI明确为观察/模板；真正本地运行记录不替代它们。

## 移动开发对照

类似移动端构建包与发布渠道需要版本/恢复证据，但Web资源可能在页面生命周期中分批加载，HTML、JS、服务端和CDN可各自变更；回滚服务器不等于撤回已经执行的客户端或业务写入。不能直接套APK安装的原子包假设。
