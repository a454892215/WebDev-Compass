# 7.4.6 交付文档：README、CHANGELOG与API契约

前置：阶段3代码检查/测试、阶段4–6 Nuxt与质量。先明确可交付行为，再组织方案、审阅与交接。

## 解决什么问题与原理

README帮助别人从干净环境复现；CHANGELOG解释对使用者可见的变化与兼容性；API文档明确方法、状态、类型、身份、缓存与限制。三个文档有不同职责，不机械复制。注明命令工作目录/环境/产物与恢复流程，未测部署不写已上线。

## 最小操作与使用场景

按主README依次安装、三个profile构建、HTTP与浏览器验证；再核对docs/CHANGELOG.md和API_CONTRACT.md。产物不提交，命令应从项目根执行；静态public不能用Nitro server入口运行，但可用Node静态文件服务器托管；SSR不能只上传public。

该操作在本地教学项目进行；规范阅读、人工审阅与真实部署是不同证据。不要把文档模板存在当成行为已经验证。

## 边界与移动开发对照

文档针对最终版本重写，不保留弃用方案冒充现行步骤；日期/版本与真实验证分开。

移动端也有评审、环境与版本管理；Web还需明确HTML/JS资源与服务端的独立生命周期。商店安装包回退经验不能直接证明线上旧页面、hash资源、API和数据库同时兼容。

核对日期2026-11-25。先读[MWG安全](https://developer.chrome.com/docs/modern-web-guidance/guides/security/security)中的现状发现、分步发布和报告隐私，再核对[官方/原始依据](https://keepachangelog.com/en/1.1.0/)。具体项目取舍不是标准要求。
