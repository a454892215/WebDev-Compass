# 7.2.1 CSR、SSR、SSG与增量再生成：先选产物，再选托管

前置：阶段3构建与测试、阶段4 Nuxt数据/状态、阶段5身份边界及阶段6质量检查。先读本章机制，再运行操作卡；7.2.2为选修观察，不阻塞Nuxt交付。

## 解决什么问题

同样能打开页面，不代表可以把同一份构建交给任意托管。先确认HTML何时生成、数据何时更新、谁执行服务端职责，才能比较延迟、成本和恢复路径。

## 原理与选择

CSR主要在浏览器执行页面渲染，静态站点可交付HTML壳、JS与CSS；首次显示依赖脚本，公开内容需要另评估搜索与无JS体验。SSR在请求时产生HTML，仍会发送客户端脚本完成hydration；有缓存时也可能返回先前生成的HTML，不能把“SSR”简单等于每次重新计算全部内容。SSG在构建时生成每条已知路由的HTML/payload，内容更新需再次构建部署，或明确设计客户端独立API；静态文件托管不会因此获得Nuxt server/能力。

增量生成/再验证是在请求、时间或显式失效后更新预生成内容，成功语义取决于框架、缓存层及托管适配。Nuxt routeRules中的swr在Node可缓存响应并后台再验证；isr另依平台CDN支持。不能把swr、CDN ISR、浏览器Cache-Control和useFetch数据key当同一层缓存。带身份页面通常不适合共享整页缓存。

选择从业务输入出发：公开、少更新、路由可枚举的文档先考虑SSG；需要请求身份/时效聚合的页面考虑SSR或独立API；封闭交互工具可CSR。也可逐路由混合，但每新增profile都要增加相应部署验收。不存在所有指标同时最优的通用模式。

## 最小机制片段

```typescript
// 配置片段：仅展示路由策略，不是主项目完整配置。
export default defineNuxtConfig({
  routeRules: {
    '/docs/**': { prerender: true },
    '/account': { prerender: false, cache: false },
    '/tool/**': { ssr: false },
  },
})
```

## 观察与适用边界

在综合项目对同一公开详情比较SSR原始HTML、SSG磁盘文件和CSR原始壳，再用浏览器确认三者交互。保存profile、命令、产物、HTTP状态及内容时效来源，不能只看最终截图。

## 常见误区

SSG页仍可交互；CSR也可能由Node托管；是否有Node服务器与是否SSR不是同一维度。反向代理fallback若对所有缺失文件返回200 HTML，会把坏JS伪装成页面；错误状态需按托管模型验证。

## 移动开发对照

可借用移动端“编译产物与服务端依赖分开”的经验，但Web还存在构建时HTML、请求时HTML和浏览器接管，不能把SSR类比成简单的远程Widget树。
