# 7.2.4 Hydration生产排查：原始HTML、payload与重复请求

前置：阶段3构建与测试、阶段4 Nuxt数据/状态、阶段5身份边界及阶段6质量检查。先读本章机制，再运行操作卡；7.2.2为选修观察，不阻塞Nuxt交付。

## 解决什么问题

页面看起来能点，不代表初始HTML、客户端状态与数据生命周期一致。生产压缩可能减少警告输出，应同时检查行为、请求与数据，而不是只搜索console。

## 原理与选择

Hydration是Vue接管服务端已生成DOM，并建立事件和响应式关系。初始数据与结构需要一致；Math.random、当前时间/时区、浏览器窗口、localStorage、无效HTML被浏览器修正等都可能导致差异。CSS能解决的响应式布局优先用CSS，而不是在setup中用window决定SSR结构。

useFetch/useAsyncData把初始SSR结果放入payload，客户端在相同key和适用配置下复用，可避免setup里裸$fetch导致的重复读取。不是所有二次请求都错误：URL/参数变化、显式refresh、缓存失效和用户动作可能合理；应按请求原因和时间线判断。仅仅“请求数量少”也不能证明没有错误缓存或旧身份数据。

浏览器专属依赖需放client插件、onMounted或合适的ClientOnly边界；仅if(import.meta.client)改变首屏可见结构仍可能不一致。更稳妥是SSR稳定占位，再在mounted更新，或用可序列化useState在请求内初始化并传给浏览器。ClientOnly不是把全部应用包住的默认修复，必要内容和样式、加载失败与SEO还要保留。

## 最小机制片段

```vue
<!-- 自足Vue/Nuxt页面片段；挂载后才读浏览器API。 -->
<script setup lang="ts">
const width = ref<number | null>(null)
onMounted(() => { width.value = window.innerWidth })
</script>
<template><p>视口：{{ width === null ? '挂载后读取' : width }}</p></template>
```

## 观察与适用边界

在综合项目公开详情保存原始HTML，监听页面error/console和API请求，再执行一次计数交互、链接导航与刷新。SSR内容被接管且事件有效；初始取数没有无原因重复。对同一输入比较初始数据与payload，不用最终DOM截图代替原始响应。

## 常见误区

不要在模块顶层使用window；不要以typeof window避免崩溃后就认为结构一致；不要把SSR useState当Node进程全局状态；生产无警告不等于绝无mismatch，需检查实际内容和交互。

## 移动开发对照

页面接管不同于Flutter首次build或RN挂载：DOM已在浏览器解析，HTML纠错也可能改变结构。可以复用状态一致性意识，但排查应沿响应→解析DOM→payload→接管顺序。
