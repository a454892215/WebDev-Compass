# 14.3.4 SSR Cookie/Header：入站身份与上游转发白名单：代码与观察

## 类型与运行条件

代码入口为相邻runtime-lab，Node>=22，无额外依赖。Node请求作用域/调度模型与真实HTTP传输实验分开，不冒充Nuxt框架执行。主Nuxt验证见综合项目。

## 操作与真实预期

runtime-lab 的 upstreamHeaders 丢弃入站 cookie、authorization 和 x-forwarded-for，只接受有长度/字符边界的 accept-language，并使用函数参数中的服务端 fixture token。测试输入包含伪造授权和 CRLF；结果不得包含这些入站值。fixture token 是公开测试字符串，不是生产密钥。

~~~ts
// Nuxt app setup 中，只请求固定相对路径的本地 API。
const requestFetch = useRequestFetch()
const { data } = await useAsyncData('account-summary', () => requestFetch('/api/summary'))
~~~

这个片段说明官方上下文传播用法，不承诺主项目必定用相同路由名。切换登录用户时，应按主项目的明确动作清理/刷新旧状态；仅改 key 不能替代 Session 校验。

从本目录进入runtime-lab执行：

~~~sh
node --test test.mjs
~~~

本轮六项测试通过：交错请求局部状态、上游白名单、独立任务同时启动、真实首块/终结块、提交头前后错误、断开取消清理。测试临时监听127.0.0.1随机端口并自动关闭。受限执行器需要允许loopback；不能把EPERM当代码逻辑成功。Next的观察结论不在六项运行覆盖中。

## 变体与排错

故障：把 upstreamHeaders 改成 {...requestHeaders, authorization: serviceToken}，用户 Cookie/代理声明也被带走。断言真实输出头发现额外字段，修复为逐字段允许；不要只把日志中 Cookie 隐去而保留实际转发。

## 对照主 Nuxt 实际代码

实际页面 app/app.vue 使用相对路径 /api/dashboard，避免把SSR请求盲目发到外部地址。server/utils/aggregate.ts 只允许固定127.0.0.1:4567与profile/items路径，对上游重新构造合成fixture授权，不转发入站Cookie或Authorization；demo_session只在本地BFF校验。server/api/session.post.ts 设置HttpOnly、SameSite=Lax、Path=/，本地HTTP时Secure=false，这只是loopback教学例外；生产HTTPS应使用Secure并按部署选择__Host-前缀。页面选择公开Alice/Bob不能作为生产身份认证。

## 范围

移动 HTTP client常由 App 显式注入 token；浏览器 Cookie有自动发送和同站策略，SSR服务又是一跳独立客户端。复用移动端HTTP拦截器设计时，要明确每跳目标和身份来源，不能把一个“全局带所有头”的拦截器搬到服务器。
