# 14.3.2 Nuxt Nitro：请求生命周期、配置和用户隔离：代码与观察

## 类型与运行条件

代码入口为相邻runtime-lab，Node>=22，无额外依赖。Node请求作用域/调度模型与真实HTTP传输实验分开，不冒充Nuxt框架执行。主Nuxt验证见综合项目。

## 操作与真实预期

本节 runtime-lab 的 requestView 使用函数调用内 context，并用人为闸门使 A/B 交错：A 暂停、B 完成、A 恢复。断言两次输出各自身份，展示请求局部数据原则；它是 Node 模型，不是 Nitro 实际路由验证。主 Nuxt 综合项目另做真实双会话 HTTP/SSR 验证。

在 Nuxt server API 中，可采用以下最小模式；authenticate 是上下文依赖，示意不等于本仓库已存在的函数：

~~~ts
export default defineEventHandler(async (event) => {
  const principal = await authenticate(event) // 必须先实现 Session/权限校验
  event.context.principal = principal
  return { displayName: principal.displayName } // 最小可见 DTO
})
~~~

完整运行入口以阶段14综合实践 README 为准；不要把上面未定义的 authenticate 原样粘入并声称可运行。

从本目录进入runtime-lab执行：

~~~sh
node --test test.mjs
~~~

本轮六项测试通过：交错请求局部状态、上游白名单、独立任务同时启动、真实首块/终结块、提交头前后错误、断开取消清理。测试临时监听127.0.0.1随机端口并自动关闭。受限执行器需要允许loopback；不能把EPERM当代码逻辑成功。Next的观察结论不在六项运行覆盖中。

## 变体与排错

故障：模块顶层 let currentUser，在 await 前赋值、await 后返回。使用可控 Promise 闸门稳定复现，不靠随机并发碰运气。定位共享变量作用域，修复为 event.context 或调用参数；模块级连接池不必一并删除。

## 对照主 Nuxt 实际代码

主项目的 server/middleware/context.ts 每请求创建 traceId；server/api/dashboard.get.ts 验证 demo_session 后把 fixtureUser 写入当前 event.context。server/utils/state.ts 共享的是有上限、有过期的合成 Session存储和限流桶，不是全局 currentUser。nuxt.config.ts 明确 node-server preset、私有 runtimeConfig 和禁用响应缓存。这里只列实际实现，部署后的多实例共享存储属于新增任务；内存Map不会跨进程同步。

## 范围

移动 App 的进程通常属于当前安装/用户会话；服务端进程同时服务多个人。可借鉴移动端分层和依赖注入，但服务端请求作用域需独立建立；不因为不能全局保存 currentUser 就禁止连接池。浏览器里的状态也要在退出/切账号时清理，SSR隔离不会代替客户端状态管理。
