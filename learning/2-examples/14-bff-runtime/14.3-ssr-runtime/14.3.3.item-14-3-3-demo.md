# 14.3.3 SSR 数据获取：识别 waterfall 与安全并行：代码与观察

## 类型与运行条件

代码入口为相邻runtime-lab，Node>=22，无额外依赖。Node请求作用域/调度模型与真实HTTP传输实验分开，不冒充Nuxt框架执行。主Nuxt验证见综合项目。

## 操作与真实预期

runtime-lab 的 aggregate 测试让两个 loader 都在同一个 gate 等待，并在放行前断言两者已经启动。该方法验证调度关系，不靠“总耗时恰好小于100ms”等易抖阈值。实验只演示调度，不声称模拟真实服务器吞吐。

~~~js
const profilePromise = loadProfile()
const catalogPromise = loadCatalog()
const [profile, catalog] = await Promise.all([profilePromise, catalogPromise])
~~~

Nuxt 页面应在 setup 中结合 useAsyncData 包装真实 BFF 入口；不要把需保密的上游 token 放在 handler 返回值。真实故障/预算由主 BFF 的接口测试验证。

从本目录进入runtime-lab执行：

~~~sh
node --test test.mjs
~~~

本轮六项测试通过：交错请求局部状态、上游白名单、独立任务同时启动、真实首块/终结块、提交头前后错误、断开取消清理。测试临时监听127.0.0.1随机端口并自动关闭。受限执行器需要允许loopback；不能把EPERM当代码逻辑成功。Next的观察结论不在六项运行覆盖中。

## 变体与排错

故障：loader 内先 await loadProfile 再调用 loadCatalog，导致 catalog 在 profile gate 放行前没有开始。看 started 事件而非只看网络截图；恢复先发起再汇合。另解释 Promise.all 失败时其他请求为何可能仍在运行。

## 对照主 Nuxt 实际代码

app/app.vue 通过 useAsyncData 和 useRequestFetch 访问 /api/dashboard；server/api/dashboard.get.ts 在鉴权后用 Promise.allSettled 同时发起 profile/items，profile必需，items失败返回空列表和warnings。server/utils/aggregate.ts 在250ms预算内连同body消费一起取消，redirect:error拒绝重定向；浏览器断开通过当前response的close传入AbortSignal。局部实验的gate验证调度原理，主接口测试另验证真实超时和partial响应。

## 范围

Flutter 的 Future.wait 可类比独立异步任务汇合，但 Nuxt 还要考虑 SSR payload/hydration、共享请求上下文和响应缓存。CPU 密集工作不是简单加 Promise.all 就能利用多核，需参考14.1 Worker 与隔离边界。
