# 阶段编写与验收总则

规则版本：1。适用于全部阶段、章节和知识点的编写、修改和复核。目标是**准确、完整、层层递进、实践对应**。复用现有四部分目录与检查脚本，不额外建立复杂教学流程。

## 1. 先明确读者、目标和顺序

读者已有 Android / Flutter / React Native 开发经验，但未必熟悉浏览器。利用已有编程能力，重点解释 Web 特有机制及差异，不能照搬移动框架概念。

主线：HTML/CSS/JavaScript → TypeScript → Vue 3 → Nuxt；React/Next 选修。开始时读取 AGENTS.md、知识地图、学习路径和本阶段已有记录，列全本次编号与待办。

- 阶段入口写清前置、目标和产出；目标用“能解释、实现、比较、排错”等可观察行为，避免只写“了解”。
- 从基础概念到简单例子，再到独立练习和综合应用。先解释再使用，复杂代码分步展开；历史编号不改动，必要时在章节索引说明推荐顺序。
- 示例支架不等于必须先会的知识。HTML中需DOM、类或异步的实现，明确在JavaScript对应章节后回读，避免循环先修。
- 正文围绕“解决什么问题 → 原理 → 最小例子 → 使用场景 → 边界与误区”展开，标题可以因主题调整。
- 理论、示例、练习考查同一核心能力；独立练习需改变输入、情景或故障，综合任务结合具体项目，不只复制例子或重复标题。

这些安排参考[CMU目标对齐、Google读者分析、Diátaxis教程方法等一手资料](./TEACHING_EVIDENCE.md)，属于本项目适配，不保证固定学习时长或学习效果。不要求学习者每点填写额外教学设计表。

## 2. 每个知识点交付四部分

目录及契约遵守[学习资料结构规范](./LEARNING_STRUCTURE.md)。每个已编写点都必须有四部分，多个点允许共享项目。

| 部分 | 最低质量要求 |
| --- | --- |
| 理论笔记 | 机制、场景、最小例/观察、误区、移动端对照及边界、可核对来源 |
| 代码示例 | 运行条件、操作与真实预期结果；代码确实展示目标机制，资源路径有效 |
| 独立练习 | 动手任务、至少两项具体验收、可复现排错、参考要点；能独立尝试后对照 |
| 综合实践 | 项目目标与运行入口，每点对应具体实现/分析任务及至少两项标准；区分现有功能和新增扩展 |

最小片段的变量、元素、资源和模块应自足，或明确给出上下文。不能用未声明变量、尚未讲解的语法或不存在的项目功能制造隐含前提。DNS/TLS等可用可操作观察清单，标明类型与未验证范围；不为凑数量造空文件或重复工程。

## 3. 技术与来源必须核实

先用简短英文动作短语检索 Modern Web Guidance 并读匹配正文，再核对MDN、WHATWG或框架/工具官方资料。无匹配或无法访问如实记录，继续用可核实来源；不能只看摘要或编造出处。

- 核对日期、版本、兼容性和安全边界。区分技术事实、项目取舍、推断和未验证事项。
- 移动端类比须说明差异，严格区分同源/同站、SOP/CSRF、SPA/SSR、DOM/Widget、绑定/对象等不同维度。
- 本地fixture、模拟日志、静态编译结果、实际构建、真实接口分别说明；理论上应该发生不等于本轮已经实测。
- 示例优先本地资源与原生能力；无真实凭据和无关上报，教学服务仅loopback。按主题核对标签、键盘、缩放、溢出、失败与回退；不机械给所有主题套全套UI测试。

## 4. 阶段验收标准

必须逐点阅读四部分，并交叉核对章节衔接；不能只看标题或文件数量。下列9条全部满足才称阶段资料质量达标。

| 规则 | 检查内容 |
| --- | --- |
| R01 范围完整 | 全阶段编号无遗漏，四部分映射齐全，不重复充数 |
| R02 层层递进 | 前置、目标、推荐顺序清楚，术语先解释，代码上下文明确，无阻断学习的循环依赖 |
| R03 内容准确 | 机制、场景、来源、版本及移动端类比正确，没有已知的明显错误 |
| R04 示例有效 | 按说明可运行/观察，操作确实展示目标机制；预期、模拟与实测一致 |
| R05 练习具体 | 能独立操作和解释；排错有具体故障/输入、定位线索及修复判据，参考能帮助纠错 |
| R06 综合对应 | 每点任务和项目有关，现有实现与要求新增的功能分清，成功标准可核验 |
| R07 前后一致 | 标题、理论、代码、练习、术语和项目事实不矛盾；兼容、可访问性及安全检查适用于主题 |
| R08 问题关闭 | 必要验证通过，发现的必达缺陷已修复复验，证据与未测边界真实 |
| R09 状态清楚 | 索引、进度、限制和下一步同步；已编写、质量达标、学习者掌握分开 |

本次审查特别提醒：写“修复已有功能”前先查实际代码；排错要能复现；实验不能只切换标签而目标机制没有变化；迁移后既查Markdown，也查HTML及动态资源；AI审阅不能冒充真实学习者试学。这些都按上表验收，不另加一套评分。

学习时建议先预测结果、再运行并解释，隔一段时间用变体再做一次；不强制固定天数或繁杂打卡。图和颜色应有等价文字，术语清楚；按学习目标接受代码或观察记录等合适产出。无需为了形式给每篇堆同样的段落。

## 5. 执行与收尾

1. **开始**：读取规则与目录，明确编号、前置、产出和可续跑待办。
2. **编写／审查**：先核实依据，分批完成四部分并核对衔接；每批回写剩余事项。
3. **修正／验证**：修复具体问题，运行最小充分检查；能自动发现的实际遗漏补有效失败回归。
4. **验收**：按[阶段验收模板](./templates/STAGE_ACCEPTANCE_TEMPLATE.md)记录逐点结论、R01–R09、问题与证据；分组通过后仍需集成复核公共项目和跨章节内容。
5. **交付**：更新进度与索引，审查差异后按项目规则创建中文本地提交，不自动推送。

```bash
python3 scripts/check_knowledge.py --report
python3 scripts/check_learning_delivery.py
python3 scripts/check_learning_resources.py
python3 -m unittest discover -s scripts/tests -v
# 正式阶段验收，例如：
python3 scripts/check_stage_acceptance.py --stage 0 --stage 1
```

代码改动后复验受影响行为。未改且条件适用的历史证据可注明原日期复用，不重新全量运行；移动模拟不称真机，未做的外网、生产、多浏览器或辅助技术验证不称通过。静态检查只覆盖文件、链接与契约，技术/教学正确性还需逐点审阅。

机器验收记录用 `docs/stages/stage-N-acceptance.json`，逐点记录放 `docs/audits/`。教材、共享资源或总则变化导致来源指纹过期时，先复核受影响内容与必要证据，再刷新；不能只改指纹消除报错。遇到通用失误，适度回写规则或脚本，不无限增加文书要求。

局部缺项或缺必要证据时写“未达标/部分完成”，说明具体缺口并继续可推进工作。全部标准通过表示本轮资料质量在声明范围达标，不保证不存在未知错误，更不等于学习者已掌握。地图复选框由学习者维护；正文完成度仍按实际文件统计。旧迁移脚本仅作历史工具，不反复运行覆盖现行教材。
